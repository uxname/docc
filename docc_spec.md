# docc — Light PRD

**Компилятор и линтер документации на Rust** · имя `docc` · редакция 13 от 17 октября 2026 · **единый релиз**: первый выпуск v0.1.0 содержит все возможности (поэтапных выпусков с частью возможностей нет: каждая возможность либо входит в выпуск, либо не делается)

## 1. Суть

`docc` — утилита командной строки на Rust. ИИ-агенты пишут документацию как **JSON-файлы**, а `docc` проверяет её **так же, как Biome проверяет код**: структуру по JSON Schema, граф ссылок, содержимое и стиль текста. Затем собирает из неё читаемый Markdown для людей.

Данные — источник истины, Markdown — генерируемый вывод. Инструмент универсальный: заметки, требования, решения, разделы бизнес-плана, проектная документация. Встроенных типов документов нет.

`docc` — публичный проект с открытым кодом (лицензия MIT): готовые бинарники в GitHub Releases, установка `install.sh` и `install.ps1`, самообновление `docc update` (проверка SHA-256 по `checksums.txt`), скилл для агентов `npx skills add uxname/docc`. Первые пользователи — команда автора; продаж, тарифов и поддержки по срокам нет.

## 2. Проблема

- Код пишут и читают агенты, а людям нужна понятная документация уровня видения и бизнес-требований.
- Агенты в обычном Markdown ссылаются на несуществующие документы, плодят сирот, дублируют факты, оставляют заглушки, нарушают структуру.
- Нет «линтера и компилятора» для документации с проверкой в CI.

## 3. Цели и не-цели

**Цели**

1. **Строгая проверка как у кода:** невалидная документация не попадает в основную ветку.
2. **Опыт «как у Biome»:** правила с кодами и группами, уровни `error`/`warn`/`off`, пресет `recommended`, `explain`, вывод в JSON для агентов и CI.
3. **Ядро:** нет битых ссылок, сирот, дублей `id` и циклов.
4. **Дружелюбие к агентам:** диагностика в JSON с подсказкой, команда `docc schema`, скилл `docc`.
5. **Детерминизм и один бинарник** на Linux, macOS и Windows.

**Не-цели**

- Wiki, редактор, генератор сайта (страницы с сервером, сборка из нескольких HTML-файлов, настройка вида), замена трекера задач. Один самодостаточный HTML-файл для чтения и согласования (`docc build --html`: шкала времени, комментарии) сайтом не считается и допускается (раздел 10).
- Ядро не вызывает LLM и не проверяет смысл: смысл и читаемость Markdown проверяет ревьюер. Согласованность с кодом (дрейф) вне ядра.
- Пользовательские шаблоны оформления (один универсальный рендер; вид единого HTML-файла один, фиксированный, без своих тем и CSS).
- Команды поиска для агента (`context`, `affected`), переименование `mv`, миграция готового Markdown, переходы статусов, граф Mermaid, глоссарий.
- Команда `trace`; `--changed`, `baseline`; правила, зависящие от истории git (изменения после проверки отслеживает `docc.lock`, а не git).
- Автоисправления (`--fix`), переопределения правил по папкам (`overrides`), словари в отдельных файлах.
- Форматирование исходников (`docc fmt`); отдельные проверки повторов в списках (их ловит встроенная схема); отчёты `sarif` и `github` (добавятся, когда станет известно, где работает CI); подключение базового конфига (`extends`).

## 4. Пользователи и сценарии

| Пользователь | Что делает |
| --- | --- |
| **ИИ-агент** | Пишет и правит JSON-документы, запускает `docc validate` и `docc build`, читает диагностику в JSON, исправляет |
| **Человек** | Читает собранный Markdown, ревьюит смысл и читаемость |
| **CI** | `docc check` блокирует merge при ошибках или устаревшем выводе |
| **Аудитор** | Собирает `docc build --full` и читает всё, с чем работают агенты: скрытые документы, заметки, подавления |

**Главный сценарий:** человек ставит задачу словами → агент правит JSON → `docc validate` ловит ошибки → агент чинит по подсказке → `docc build` → человек читает Markdown и проверяет смысл → merge; CI запускает `docc check`.

**Ревью человеком:** ревьюер читает `out/` и проверяет смысл и читаемость. Правку вносит агент по замечанию ревьюера или человек в `src` (длинный текст — массивом абзацев, см. раздел 6), затем `docc validate` и `docc build`; `out/` руками не правится. Конфликт в `out/` решается пересборкой; конфликт в `src` с маркерами слияния даёт `DOC101`, сначала исправляется `src`. Рекомендация вне `init`: пометить `out/**` как сгенерированные (`linguist-generated`).

## 5. Как это работает

**Конвейер:** загрузка JSON → схема → граф ссылок → правила → рендер → проверка актуальности вывода.

```
docs/
├── src/            # ИСТОЧНИКИ (*.json), любая вложенность
├── schemas/        # <kind>.json, схема для каждого вида документов
├── out/            # СГЕНЕРИРОВАНО (не редактировать; коммитится, если в docc.json не "commitOut": false)
├── out-full/       # полная сборка для аудита (docc build --full), не коммитится
├── out.md, out.html            # необязательно: единые файлы (docc build --single, --html), не коммитятся
└── out-full.md, out-full.html  # то же для полной сборки
docc.json           # конфиг, необязателен
docc.lock           # подтверждённые ссылки и их отпечатки, коммитится (раздел 7)
```

`docc init` создаёт `docc.json`, `docs/schemas/page.json` (схема, требующая `title`, с `"additionalProperties": true`) и `docs/src/index.json` (`{ "title": "Index", "kind": "page" }`), в Git-репозитории без своего хука — ещё `.git/hooks/pre-commit` с `docc check` (коммит с ошибками в документации не проходит), затем собирает `docs/out` и `docc.lock`, чтобы первый `docc check` был зелёным. Хуки агента, шаг CI и инструкцию для агентов `init` не создаёт: их даёт скилл `docc` (раздел 11).

Сгенерированные файлы коммитятся, начинаются с комментария `<!-- GENERATED by docc, DO NOT EDIT -->`. Конфликт в `out/` при merge решается командой `docc build`. Точные определения (файлы и пределы, текстовые правила, граф, рендер, форматы вывода, словари, тесты) — в разделе 17.

## 6. Модель документа

Один документ — один файл `*.json` в `src`. **`id` = имя файла без расширения.** Допустимые символы: `a-z`, `0-9`, `-` (начало и конец — не дефис); зарезервированные имена Windows (`con`, `prn`, `aux`, `nul`, `com1`–`com9`, `lpt1`–`lpt9`) запрещены. Имена папок в `src` подчиняются тем же правилам (иначе `DOC104`). Два файла с одним именем в разных папках — ошибка `DOC201`.

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| `title` | да | непустая строка, заголовок |
| `kind` | да | вид документа; по нему подбирается схема `docs/schemas/<kind>.json` (без вида или схемы — `DOC109`) |
| `status` | нет | строка, допустимые значения задаёт схема вида |
| `parent` | нет | `id` родителя (один) |
| `order` | нет | число: порядок среди соседей по `parent` (без него — по заголовку) |
| `body` | нет | основной текст документа: строка или массив абзацев (элементом может быть поле формы, см. «Поля формы»); выводится сразу под заголовком без собственного раздела |
| `tags` | нет | массив строк; допустимые теги можно задать реестром |
| `notes` | нет | скрытые заметки для агентов: массив строк, в Markdown не выводятся |
| `hidden` | нет | `true`: документ проверяется, но в `out/` не выводится и не требует достижимости от корня |
| `docIgnore` | нет | подавления, см. ниже |
| `$comments` | нет | комментарии читателей — плоский список `[{id, at, quote, fragment?, prefix?, suffix?, text \| input+answer, author, email?, created}]`: `id` уникален в проекте (docc выдаёт `c-` и 10 знаков `a-z2-7`), `at` — JSON Pointer блока (у ответа на поле формы — блока поля), `quote` — текст блока при написании, `fragment`/`prefix`/`suffix` — выделенные слова и знаки вокруг них, ровно одно из `text` или `input` (id поля) с `answer` (массив строк), `author` — имя (может быть пустым), `email` необязателен, `created` — время RFC 3339. Статусов, ответов и внутренних комментариев нет: обработанный комментарий агент удаляет в том же коммите, что и правку. Поле разрешено при любой схеме вида, как `title` (закрытая схема его не отвергает), к нему не применяются текстовые правила, оно не выводится разделом, не входит в блоки истории и в отпечатки ссылок `docc.lock` (комментарий не делает ссылки на документ подозрительными); форма записи — `DOC112`, потерянное место — `DOC215`; пишет поле `docc comments apply` (раздел 8); `docc log` отмечает правку только в нём как `commentsOnly` |
| любые другие | нет | свободные поля (например `statement`, `rationale`; других зарезервированных имён нет), если их разрешает схема вида; проза хранится как Markdown-строки или массивы абзацев |

**Ссылки в тексте:** связь между документами — только ссылка в тексте, отдельного списка связей нет. `[[id]]`, `[[id#поле]]`, `[[id#поле/раздел]]` и `[[id#^якорь]]` внутри строковых значений дают ребро графа (проверка цели, достижимость, раздел «Ссылаются») так же, как `parent`. Блоки кода и строки в обратных кавычках игнорируются. Длинный текст записывается массивом абзацев (по абзацу на строку файла): `"body": ["Первый абзац.", "Второй абзац."]`; внутри абзаца переводы строк пишутся как `\n`, рендер переносит их в Markdown как есть. Правила применяются к каждому элементу массива отдельно, путь вида `/body/1`.

**Вложенные разделы.** Объект со служебным ключом `"$sections": true` в значении свободного поля (или в значении другого раздела) — набор разделов: остальные ключи — заголовки, значение — строка, массив строк, таблица, объект-список или снова такой же набор. Поле выводится как `##`, раздел как `###`, следующий уровень `####` и так далее до `######`, порядок как в файле; раздел без текста остаётся заголовком, чтобы у ссылки была цель. Объект без маркера выводится списком, как раньше; маркер вне значения поля или раздела (в массиве, внутри объекта-списка) ничего не значит. На раздел ссылаются `[[id#поле/раздел]]` (текст ссылки — заголовок раздела, а не название документа; ссылка на поле по-прежнему называется заголовком документа), его вставляют `{{id#поле/раздел}}` (вставляется раздел-лист, набор целиком не текст); путь ищется по ключам, поэтому ключ может содержать `/`. Якорь раздела строится как у поля из его заголовка; одинаковые якоря на странице нумеруются `-1`, `-2` в порядке страницы. Текстовые правила, `docIgnore.path` (указатель `/поле/раздел`) и `DOC209` работают с разделами как с полями. В схеме kind маркер описывается как `"properties": {"$sections": {"const": true}}`. В едином HTML заголовки `h2`–`h4` попадают в оглавление страницы.

**Поля формы.** Элемент массива абзацев (`body`, свободного поля или раздела) может быть объектом `{"$input": "radio", "id": "export", "label": "Нужен экспорт?", "options": ["Да", "Нет"]}`: HTML-файл рисует на его месте поле, на которое читатель отвечает. `$input` — `text` (текстовое поле), `radio` (один вариант, вариантов от двух) или `checkbox` (несколько, вариантов от одного); `id` из `a-z`, `0-9` и `-`, единственный в документе: ответы хранятся по нему; `label` — вопрос; `options` — варианты (у `text` их нет); других ключей нет. Поле `radio` и `checkbox` всегда принимает и свой ответ — строку `answer`, которой нет среди `options` (отдельного ключа для этого нет): у `radio` ответ — ровно одна строка, вариант или свой текст; у `checkbox` — отмеченные варианты и не больше одного своего текста. Свой ответ не даёт ни `DOC112`, ни `DOC215`, но форма ответа проверяется: в `answer` хотя бы одно значение, ни одного пустого (из пробелов) и ни одного повтора — всегда (`DOC112`, такой элемент не выводится); ответ на поле, каким оно стоит сейчас (место `same`), обязан ему подходить — у `text` и `radio` ровно одно значение, у `checkbox` не больше одного значения не из `options` (`DOC112`, ошибка, как и другие ошибки формы `$comments`); ответ на прежнюю версию вопроса (`changed`) не проверяется по нынешнему полю. `docc comments apply` при `add` и `edit` проверяет то же и обрезает пробелы по краям у значений не из `options` (текст поля `text`, свой ответ), как HTML-файл; вариант сохраняется как есть. Поле задаёт автор (обычно через агента) в источнике; в Markdown (`docs/out`, `--single`, `--full`) поля нет совсем, в HTML оно — блок со своим указателем и историей, как абзац; соседние абзацы массива остаются отдельными блоками. Текстовые правила читают только `label` и `options`. Свободное поле с полем формы требует схемы вида, которая разрешает этот объект; встроенная схема разрешает его в `body`. Неверное поле или поле не на месте (значение поля целиком, элемент списка объектов) — `DOC111`. Ответ — комментарий (раздел 10, «Комментарии»).

**Якоря абзацев.** ` ^имя` в конце абзаца, пункта списка или однострочного поля (имя начинается с буквы: `a-z`, `0-9`, `-`) — якорь этого фрагмента: `[[id#^имя]]` ссылается на него, `{{id#^имя}}` вставляет абзац без метки. На странице метка не выводится, вместо неё ставится `<a id>`. Повтор якоря в документе или совпадение с якорем поля либо раздела — `DOC212`, ссылка на несуществующий якорь — `DOC312`.

**Скрытое и вставки.** `notes` — аналог комментариев в коде: агент видит их в исходнике, читатель в Markdown — нет. `[[id]]` и `[[id#поле]]` внутри заметок проверяются на существование (`DOC202`, `DOC312`), но не дают достижимости от корня; правила `text/*`, `markdown/*`, `style/*` к заметкам не применяются (пользовательские — только если `given` указывает на `/notes`). Скрытый документ (`hidden: true`) проверяется как обычный, но страницы в `out/` и записи в `_tree.md` не имеет, не входит в проверку сирот и не даёт путей достижимости; видимый документ не может ссылаться на скрытый через `parent`, `[[id]]` вне заметок или вставку (`DOC210`). **Вставка** `{{id#поле}}` в строке заменяется при сборке текстом поля другого документа (элементы массива — абзацы через пустую строку), чтобы факт хранился один раз; исходник хранит только ссылку. Вставка пропускается в блоках кода и обратных кавычках и допускает вложенные вставки; `{{id}}` без `#поле`, несуществующая цель, цикл, значение не из текста и служебные поля — `DOC211`.

**Подавление:** в JSON нет комментариев, поэтому подавление — поле документа:

```json
"docIgnore": [{ "rule": "text/forbidden-words", "reason": "термин из ТЗ заказчика", "path": "/statement" }]
```

`rule` — имя правила (`text/forbidden-words`), как в ESLint и Biome; код (`DOC301`) тоже работает, но даёт предупреждение `DOC902`; `reason` обязателен (иначе `DOC108`); `path` (JSON-указатель) необязателен: подавляет диагностики внутри указанного значения вместе с вложенными, без него — во всём документе. Ядро (его нельзя ни подавить, ни отключить; остальные правила настраиваются, в том числе `DOC106`, `DOC107`, `DOC312`): `DOC101`–`DOC105`, `DOC108`, `DOC109`, `DOC201`–`DOC205`, `DOC210`–`DOC213`, `DOC401`, `DOC501`, `DOC503` (попытка даёт `DOC108`). Подавление, которое ничего не подавляет, или подавление выключенного правила даёт `DOC901`.

**Схемы обязательны и строги, как типы в TypeScript:** у каждого документа должен быть `kind` и файл `docs/schemas/<kind>.json` (JSON Schema, драфт 2020-12), иначе `DOC109` (ядро, не отключается). На верхнем уровне схема вида обязана задать `additionalProperties` значением `true` (гибкий вид: лишние поля разрешены) или `false` (строгий вид), иначе ошибка загрузки схем (код выхода `2`). Закрытость `docc` проверяет сам: разрешены служебные поля (`title`, `kind`, `status`, `parent`, `order`, `tags`, `body`, `notes`, `hidden`, `docIgnore`), свойства верхнего уровня и свойства веток `allOf` верхнего уровня и локальных `$ref` (не `if`/`then`); лишнее поле — `DOC106` «unknown field X» с подсказкой похожего имени. Схема видит документ целиком, поэтому может требовать `parent` или ограничивать `status`. `"x-docc-target": ["вид", …]` у свойства (в том числе `parent`) ограничивает виды документов, на которые ведут ссылки в нём (`DOC214`); `"x-docc-covered": true` на верхнем уровне требует, чтобы на документы вида был тег в коде (`DOC403`). Документы вида проверяются по схеме своего вида (`DOC106`); схемы не наследуют друг друга. Схема может ссылаться через `$ref` на другие файлы каталога схем. Метасхемы документа и `docc.json` выдаёт `docc schema`. Встроенная схема документа проверяет типы служебных полей и запрещает повторы в `tags` (ошибка `DOC105`), поэтому отдельных правил для повторов нет.

```json
{
  "title": "Блокировка после пяти неверных паролей",
  "kind": "requirement",
  "status": "accepted",
  "parent": "goal-secure-login",
  "order": 1,
  "statement": "Когда пользователь вводит неверный пароль пять раз подряд, система должна заблокировать вход на 15 минут. ^limit",
  "rationale": "См. [[adr-lockout-policy]]."
}
```

## 7. Правила и диагностика

Правила собраны в группы по образцу Biome. Коды `DOCxxx` — публичный контракт и не меняются; выведенные из оборота коды (`DOC206`, `DOC207`, `DOC208`, `DOC302`, `DOC305`–`DOC307`, `DOC311`, `DOC351`, `DOC354`, `DOC355`, `DOC502`) не переиспользуются (`DOC314` выведен раньше и возвращён с новым смыслом). Сообщения на английском, каждое с подсказкой, как исправить. Уровень по умолчанию — из пресета `recommended`, меняется в `docc.json`.

| Код | Правило | Уровень | Что проверяет |

**Формат диагностики:** `файл:строка:колонка: уровень имя-правила (КОД) сообщение` (например, `warn style/hedging (DOC352)`), следом строка `  hint: …`, позиция в исходном JSON. `--format json` выдаёт массив объектов `{code, rule, level, file, line, column, endLine, endColumn, message, hint}`; `endLine` и `endColumn` — конец диапазона, `endColumn` указывает на колонку сразу за последним знаком (если диапазона нет, совпадают с началом), в text-формате выводится только начало. Колонка считается в рунах; позиция внутри строки с экранированием (`\n`, `\"`, `\uXXXX`) вычисляется по исходному тексту токена. Порядок детерминирован: уровень (error раньше warn), путь (с `/`, по байтам), строка, колонка, код, имя правила.

**Сироты:** документ — сирота, если от `roots` до него нет пути по `parent` и ссылкам `[[…]]` в тексте (рёбра в обе стороны). Сам корень сиротой не считается. Скрытые документы в проверку не входят и путей через них нет; ссылки из `notes` достижимости не дают. Проверка достижимости проверяет форму, а не смысл связи.

**Текстовые правила** эвристические. Слова сравниваются по границам Unicode без учёта регистра после приведения к NFC, текст в обратных кавычках не проверяется (идентификаторы вроде `new` пишутся в обратных кавычках), записи точные («быстро»), префикс помечается звёздочкой («быстр*»), морфология не учитывается: формы слова перечисляются явно. Для правил есть список исключений `allow`. Словари `DOC301`, `DOC352`, `DOC353` встроены (русский и английский) и дополняются в `docc.json` (`words`, `allow`).

**Теги в коде:** `// docc: req-lockout#^limit, scenario-login` ищется построчно в файлах из `trace.scan`, без разбора языков (Б3); регион `// docc:begin <цели>` … `// docc:end` дополнительно хранит отпечаток своего кода в `docc.lock`. Если `trace.scan` не задан, `DOC401`–`DOC403` не работают.

**Уточнения к правилам**

- **Позиции:** строки делятся по `\n`, `\r\n` — один перевод строки, BOM не считается; колонка — число рун исходного текста от начала строки; внутри строки с экранированием позиция вычисляется по исходному токену. Пути в диагностике относительные, с `/`.
- **Диагностики без позиции в JSON:** `DOC201` — на каждом документе с занятым `id`, кроме первого по пути (в подсказке путь первого), позиция 1:1; `DOC203` — 1:1 документа; `DOC205` — позиция поля `roots` в `docc.json`, иначе 1:1; `DOC401`–`DOC403` — файл кода, строка и колонка тега; `DOC501` — файл в `out/`, 1:1 (для лишнего файла его путь); `DOC503` — строка `docc.lock` (испорченная, повторная или лишняя), иначе 1:1.
- `DOC209`, `DOC402`, `DOC503` работают по `docc.lock` (подраздел ниже).
- `DOC800` (пользовательские правила): правила из `customRules` (раздел 9) получают код `DOC800`, их имя (`custom/…`) выводится в поле `rule`; блоки кода и обратные кавычки пропускаются так же, как у остальных текстовых правил; подавляются по имени (`custom/…`) или все сразу кодом `DOC800`.
- **Вставки:** правила текста применяются к исходным строкам, `{{…}}` пропускается; `[[id]]` во вставленном тексте проверяется в документе-источнике и для документа-приёмника не считается ни ссылкой, ни достижимостью; вставка, занимающая весь элемент строки, разворачивается в абзацы по элементам цели, вставка внутри строки — в цель, соединённую пробелами.
- **Текстовые правила** (`DOC301`, `DOC303`, `DOC309`, `DOC310`, `DOC313`, `DOC352`, `DOC353`) пропускают блоки кода и строки в обратных кавычках.
- `DOC310`: только известные имена HTML-тегов; `<id>` тегом не считается.
- `DOC312`: «поле» — ключ верхнего уровня документа или путь `поле/подраздел/…` через вложенные разделы (раздел 6, «Вложенные разделы»); `body` даёт ссылку на страницу без якоря, служебные поля якорем быть не могут; `^имя` — якорь абзаца; если самого документа нет, выдаётся только `DOC202`.
- `DOC313`: одинаковые слова подряд через пробел без учёта регистра; исключения в `allow` («и и», «не не»).
- **Исправлений нет:** `--fix` не делается, агент правит источник сам по подсказке.

### Отслеживание изменений (`docc.lock`)

Связь между документами — ссылка в тексте; `docc.lock` помнит, в каком виде была цель, когда связь подтвердили, и сообщает, если цель с тех пор изменилась. Файл лежит рядом с `docc.json` и коммитится.

- **Формат:** одна строка на связь `<источник> <цель> <отпечаток цели> [<отпечаток кода>]`, строки отсортированы. Источник — `id` документа или путь файла кода; цель — как записана в ссылке (`b`, `b#statement`, `b#^limit`); пробелы и `%` в ней пишутся как `%20`, `%25`. Отпечаток — первые 8 шестнадцатеричных знаков SHA-256; отпечаток кода есть только у ссылок из регионов `docc:begin` … `docc:end`. Пример: `req-a adr-b#^limit 1f2e3d4c`.
- **Что входит в связь:** `[[…]]` в тексте и в `notes` всех документов (скрытых тоже) и теги `docc:` в коде; ссылки документа на себя и на несуществующие цели не записываются.
- **Отпечаток цели:** для всего документа — канонический JSON без `notes`, `docIgnore`, `hidden`, `order` и `parent` (перестановка документа в дереве связь не тревожит); для `#поле` и `#поле/раздел` — только это значение; для `#^якорь` — только текст абзаца без метки. Канонический JSON: ключи на всех уровнях по алфавиту (по байтам UTF-8), без пробелов, строки с минимальным экранированием (`\"`, `\\`, управляющие символы как `\u00XX`), числа как в исходном тексте, массивы в исходном порядке. Отпечаток кода — по строкам региона, обрезанным по краям и приведённым к NFC.
- **`docc build`** (если нет ошибок 1xx–2xx) записывает `docc.lock`: новые связи — с текущими отпечатками (новая связь считается подтверждённой), исчезнувшие связи убираются, у остальных сохраняются записанные отпечатки.
- **`docc validate`** сравнивает текущие отпечатки с записанными: изменилась цель — `DOC209` на ссылке (перечитать источник), изменился код региона — `DOC402` на теге (перечитать документ). Если `docc.lock` нет или он пуст, оба правила молчат.
- **`docc ack X…`** подтверждает связи, где `X` — источник, цель или документ цели (`docc ack adr-b` подтверждает и `adr-b#^limit`; `docc ack src/auth.go` — регионы файла); `docc ack --all` — все связи. Подтверждаются только изменившиеся связи (отпечаток отличается от записанного); `ack` печатает каждую подтверждённую связь («confirmed источник -> цель», в json — массив `links`) и итог, так что видно, какие источники подтверждены. Связь без изменений не трогается, повторный `ack` подтверждает 0 связей. Подтверждение — осознанное действие после проверки: `docc` сверяет только отпечатки.
- **`docc check`** дополнительно сверяет `docc.lock` с текущими ссылками и даёт `DOC503`, если файл расходится с тем, что записал бы `docc build` (лечится `docc build`; конфликт в `docc.lock` при merge решается так же).

| `docc comments [list]`, `docc comments apply`, `docc comments import <файл\|->…`, `docc comments rm <id>…` | Комментарии читателей в `$comments` документов (раздел 10). `list` (по умолчанию) — все комментарии с документом, текущим текстом блока и местом (`same`, `changed`, `lost`); `apply` читает из stdin JSON-массив операций `{"op": "add", "doc": <id или путь>, "comment": {…}}` (`id` и `created` заполняются, если их нет), `{"op": "rm", "id"}`, `{"op": "edit", "id", "text"}` (у ответа на поле формы — `{"op": "edit", "id", "answer"}`: ответ остаётся ответом на то же поле, `at` переходит к полю, если оно сдвинулось, `quote` берётся из поля, каким его видит читатель сейчас, `created` остаётся; `text` у ответа и `answer` у комментария — ошибка) и меняет файлы точечно: меняется только `$comments`, остальные байты файла остаются; новое поле `$comments` ставится последним членом объекта с отступом файла и убирается вместе с последним комментарием; комментарий стоит только там, куда смотрит читатель, — одно правило для CLI, импорта и Docspace: `at` равен указателю блока, свойства или (у ответа) поля формы, которые `docc compile` выводит на странице этого документа, поэтому `notes`, `docIgnore`, `hidden`, заголовок и сам `$comments` отклоняются; `quote` всегда берётся из исходного текста этого блока, переданная цитата заменяется; скрытый документ (`hidden: true`) не принимает комментариев, а `rm` и `edit` не трогают его комментарии без флага `--hidden` (для агента, работающего руками; Docspace его не передаёт); `rm` и `edit` отказывают для `id`, который в проекте носят несколько комментариев (`DOC112`); пока в проекте есть ошибки групп 1xx–2xx, читатель не видит страниц и `add` отклоняется; одна плохая операция (неизвестный документ или id, неверный комментарий, место, которого читатель не видит) — код `2`, ничего не записано; с `--format json` печатает `{"$schema": "urn:docc:schema:comments-apply:1", "added": [{id, doc, path}], "removed", "edited", "files"}`; `import` — комментарии HTML-файла (скачанный файл или скопированный текст, `-` — stdin) через тот же `apply`: уже записанные (тот же `id`) пропускаются, комментарий к прошлой сборке переносится к своему блоку; комментарий, который встал бы туда, где читатель не смотрит (скрытый документ или часть, исчезнувший блок), пропускается и перечисляется в выводе (`unseen`); `rm` — удалить через `apply`; `id` можно сократить до однозначного префикса |
| `docc update` | Заменить бинарник новой версией с GitHub Releases (проверка SHA-256 по `checksums.txt`); `--check` только сообщает, есть ли новее; сборка `dev` не обновляется |
| `docc rules` | Список правил с кодом, группой и действующим уровнем (с учётом `docc.json`), включая пользовательские |
| `docc compile [--rev <ревизия>]` | Только чтение, для программы, которая показывает страницы сама (Docspace): печатает в stdout один JSON-объект и ничего не пишет на диск — ни `out/`, ни `docc.lock` (раздел 10, «Вывод compile») |
| `docc log [--rev <ревизия>] [--since <коммит>]` | Только чтение: коммиты первой родительской цепочки, менявшие папку `src`, с изменёнными файлами и числом блоков (раздел 10, «Вывод log и diff») |
| `docc diff <base> <head> [--path <файл>]` | Только чтение: блоки документов двух ревизий, сопоставленные друг с другом (раздел 10, «Вывод log и diff») |
| `docc schema document`, `docc schema config`, `docc schema compile`, `docc schema log`, `docc schema diff` и `docc schema comments-apply` | Метасхема документа, `docc.json` или вывода `docc compile`, `docc log`, `docc diff`, `docc comments apply` (JSON Schema) |

Флаги: `--format text|json`, `--config`, `--full`, `--single`, `--html` (только для `build`), `--rev` (для `compile`, `log` и `build`), `--page` (только для `build`), `--since` (только для `log`), `--path` (только для `diff`), `--all` (только для `ack`), `--max-diagnostics N` (только для text, по умолчанию 20, ошибки выводятся раньше предупреждений, в конце баннер «показано N из M»; json без лимита), `--max-warnings N` (то же задаёт `maxWarnings` в `docc.json`). Формат по умолчанию — `text`. Общие флаги относятся ко всем командам проверки. **Коды выхода:** `0` чисто; `1` есть ошибки или число действующих предупреждений (не `off`, не подавленных) больше `--max-warnings`, флаг важнее `maxWarnings` из конфига; `2` ошибка использования или конфигурации, в том числе отсутствующий каталог `src`; пустой `src` даёт `DOC205`. Ошибки `docc.json` выводятся все сразу; при `--format json` вывод при коде `2` — тот же отчёт `{summary, diagnostics}` с диагностиками `code` `config`, `usage` или `error` (`--max-warnings` меньше `-1` — ошибка использования).

`docc build` не запускается внутри `check`; скилл вызывает по порядку `docc validate`, `docc build`, а хук конца хода — `docc build`, затем `docc check`.

## 9. Конфиг `docc.json`

Все поля необязательны, умолчания встроены. Формат — как у `biome.json`:

```json
{
  "src": "docs/src",
  "out": "docs/out",
  "schemas": "docs/schemas",
  "outFull": "docs/out-full",
  "roots": ["index"],
  "tags": ["draft"],
  "recommended": true,
  "numbering": true,
  "lang": "ru",
  "rules": {
    "text/forbidden-words": { "level": "warn", "words": ["быстро", "удобно", "и т.д."], "allow": [] },
    "style/hedging": "off",
    "markdown/raw-html": "off"
  },
  "customRules": [
    { "id": "custom/no-vague-quantity", "level": "warn", "kind": "requirement", "given": "/statement",
      "forbid": "(?i)(^|[^\\p{L}])несколько($|[^\\p{L}])", "message": "Replace «несколько» with a number", "hint": "State an exact value" }
  ],
  "trace": { "scan": ["tests/**", "src/**"] }
}
```

- `roots` — `id` корней, от которых считается достижимость; по умолчанию `["index"]`; корень, которого нет среди документов, — `DOC205`. В режиме папок не действует.
- `tree` — чем задаётся дерево документов: `"parents"` (по умолчанию) — по `parent` от `roots`; `"folders"` (режим папок) — папками `src`. В режиме папок `roots`, `DOC203` и `DOC205` не действуют (в дереве каждый документ), `parent` остаётся для хлебных крошек и связей, `id` по-прежнему имя файла, единственное во всём проекте (`DOC201`). Своя страница папки — документ с именем папки внутри неё (`decisions/decisions.json`): из неё заголовок и `order` папки; без неё заголовок — имя папки. Своя страница без текста (`body` нет или он пустой, свободных полей нет — только служебные `title`, `kind`, `status`, `priority`, `parent`, `order`, `tags`, `notes`, `hidden`, `docIgnore`, `$comments`) — страница папки только с заголовком: она лишь называет и упорядочивает папку, а страницы в выводе не получает (ни файла в `docs/out`, ни страницы в `--single` и `--html`); папка показывается её заголовком без ссылки, как папка без своей страницы, ссылка `[[id]]` на неё выводится её заголовком без ссылки, а `parent` на неё не даёт ни хлебных крошек, ни раздела Parent. `docc compile` оставляет её в `pages`, а у папки в `tree` — её `id` и заголовок. Соседи (папки и документы вместе) идут по `order` (без него — после), затем по заголовку, как соседи по `parent`, при равных — по имени. Имя `index.json` для своей страницы не подходит: `id` единственны в проекте, а такой файл был бы в каждой папке. Нумерация (`numbering`) в режиме папок идёт по дереву папок, начиная с верхнего уровня (1, 2.1). HTML-файл строит навигацию по тому же дереву папок, что и `tree` у `docc compile`.
- `tags` — реестр допустимых тегов; поле не задано — реестра нет и `DOC107` не работает; пустой массив — ни одного допустимого значения. Реестра видов нет: вид существует, если есть его схема в `docs/schemas`.
- `numbering` — `true`: `docc` нумерует страницы (дети корней — 1, 2…, глубже — 9.1) и разделы `$sections` (9.1.1) в заголовках, дереве, навигации и тексте ссылок; якоря не меняются; по умолчанию `false`.
- `lang` — `"en"` (по умолчанию) или `"ru"`: язык постоянных надписей вывода (Parent, Referenced by, Covered by, дерево документов и т. п.).
- `recommended` — пресет по умолчанию; `false` отключает его целиком.
- Уровень правила: `"error"`, `"warn"`, `"off"` или объект `{ "level": …, параметры }`.
- `trace.scan` — маски от корня проекта: `*` не пересекает `/`, `**` пересекает; `tests/**` — каталог `tests` в корне, `src/**` — каталог `src` в корне, а не `docs/src`.
- `outFull` — каталог полной сборки для аудита (`docc build --full`); по умолчанию `docs/out-full`, в Git не коммитится.
- `maxWarnings` — предел числа предупреждений, после которого код выхода `1` (по умолчанию без предела).
- `commitOut` — коммитится ли `docs/out` (по умолчанию `true`, как раньше): `false` — каталог собирается для чтения, но не хранится в Git (`docc init` пишет `false` и добавляет его в `.gitignore`), `DOC501` не действует. Ключа `changesSince` больше нет: версию, с которой HTML-файл подсвечивает правки, задаёт `docc build --html --since <ревизия>` (неизвестная ревизия, ревизия вне истории `HEAD` или проект вне Git — ошибка при сборке HTML, код `2`, после обычного вывода диагностик; каталог вывода и `docc.lock` при этом собираются, не пишется только HTML-файл); старый ключ в `docc.json` — ошибка настроек с этой подсказкой.
- `customRules` — пользовательские правила: `id` (с префиксом `custom/`), `level`, `message`, необязательные `hint` и `kind` (только для документов этого вида), `given` — JSON-указатель на строковое поле (`*` означает любой элемент массива или любой ключ объекта, например `/acceptance/*/then`) и ровно одно из `forbid` (регулярное выражение, совпадение которого — нарушение) или `require` (регулярное выражение, которое должно встретиться в поле; если поля нет, нарушение). Синтаксис регулярных выражений — RE2 (как в Go) с Unicode; выражение и текст сравниваются после приведения к NFC; позиция диагностики — совпавший фрагмент (для `require` — всё поле). `\b`, `\w`, `\d` и `\s` понимают только ASCII, поэтому границы слов надо задавать через `[^\p{L}]`. Если `given` не находит поле или значение не строка и не массив строк (массив проверяется поэлементно), правило для документа пропускается (для `require` отсутствие поля — нарушение); `*` на пустом массиве ничего не находит; блоки кода и обратные кавычки пропускаются и для `require`. Ошибкой конфигурации (код выхода `2`) считаются: ошибка в регулярном выражении, `forbid` и `require` сразу, повтор `id`, `id` не вида `custom/` + `a-z0-9-`.
- Параметры правил: `text/forbidden-words`, `style/hedging`, `style/time-bound-words` — `words` (дополняет встроенный словарь, Б4) и `allow`; `text/repeated-word` — `allow`; у остальных правил параметров нет, лишний параметр — ошибка настроек. Объект правила без `level` берёт уровень из пресета (для `off` это «выключено»). При `"recommended": false` все правила выключены, кроме ядра, которое остаётся `error`.

## 10. Рендеринг и формат

- **Один универсальный рендер, шаблонов нет:** `title` — заголовок первого уровня, каждое поле — раздел второго уровня (имя поля с заглавной буквы, `_` и `-` заменяются пробелами). Под заголовком одна строка `kind · status · priority · tags` (пустые части пропускаются), затем `body`, затем свободные поля в порядке файла, в конце страницы разделы Parent, Referenced by (кто ссылается через `parent` или `[[…]]`) и Covered by (пути файлов кода с тегом `docc:` на документ, без номеров строк); раздела Links нет; `parent` выводится одной ссылкой; `[[id]]` превращается в относительную ссылку, `[[id#поле]]` — в ссылку на раздел (якорь по заголовку: строчные буквы, пробелы заменяются на `-`, буквы Unicode сохраняются), `[[id#^якорь]]` — в ссылку на `<a id>` абзаца. `body` выводится сразу под заголовком без собственного раздела, элементы массивов — абзацы, разделённые пустой строкой. Скрытые документы (`hidden: true`) страниц и записей в `_tree.md` не имеют. Вставка `{{id#поле}}` заменяется текстом поля (абзацы массива разделяются пустой строкой); относительные ссылки во вставленном тексте считаются от страницы, куда вставлено. Поля `docIgnore`, `notes`, `hidden` и `order` в обычной сборке в Markdown не выводятся.
- **Порядок и номера:** соседи по `parent` идут по `order` (числу), документы без него — после, по заголовку. С `"numbering": true` `docc` сам ставит номера страниц и разделов (раздел 9); номер, набранный вручную в начале `title` или ключа раздела, — `DOC314`.
- **Надписи:** постоянные надписи (Parent, Referenced by, Covered by, дерево документов, служебные разделы) выводятся на языке из `lang` (`en` по умолчанию, `ru`).
- **Картинки и сноски:** `![подпись](путь)` с относительным путём считается от папки документа; файл проверяется (`DOC213`), копируется в `out/` по тому же пути и встраивается в единый HTML и в вывод `docc compile` как `data:`-адрес; адрес SVG (`data:image/svg+xml`) разрешён только как `src` картинки — в ссылке он вырезается, как `javascript:` (скрипты SVG выполняются при открытии ссылкой, но не в `<img>`). Сноски Markdown (`[^1]`) в HTML выводятся сносками.
- **Диаграммы:** блок кода ```` ```mermaid ```` в Markdown и в выводе `docc compile` остаётся кодом (`<pre><code class="language-mermaid">`; программа, которая показывает страницы сама, рисует его сама). Единый HTML-файл рисует его без сети: библиотека mermaid 11.17.2 (`src/render/vendor/mermaid.min.js`, около 3,5 МБ) встраивается в файл, только если на какой-то странице есть такой блок; `securityLevel: 'strict'`, тема светлая или тёмная по теме страницы. Синтаксическая ошибка оставляет исходный текст и пишет под ним ошибку. Блок, в котором показаны правки, остаётся текстом с отметками.
- **Полная сборка для аудита** (`docc build --full`) показывает всё, с чем работают агенты: скрытые документы (с пометкой «скрытый документ»), заметки `notes`, подавления `docIgnore` (правило, причина, путь; отдельными разделами с пометкой «служебное»), а вставки `{{id#поле}}` обрамляет комментариями `<!-- include id#поле -->` … `<!-- /include -->` (видны в исходнике Markdown, не в отображении). Страницы пишутся в `docs/out-full` по тем же путям, `_tree.md` включает скрытые документы. Полная сборка отказывается работать при тех же ошибках 1xx–2xx, что и обычная, и удаляет лишние файлы в `out-full`. Каталог `out/` полная сборка не меняет, `docc check` и `DOC501` её не проверяют; в Git её не коммитят.
- Страница документа лежит по пути источника: `docs/src/a/b.json` даёт `docs/out/a/b.md`. Дерево по `parent` (в режиме папок — дерево папок) выводится в `docs/out/_tree.md`. `docc build` удаляет в `out/` только то, что создал сам: страницы с меткой `GENERATED by docc`, копии картинок, чьё место есть в `src`, и мусор файловых менеджеров (`.DS_Store`, `Thumbs.db`, `desktop.ini`). Если в `out/` лежит что-то ещё, `build` отказывается работать (код 2), ничего не пишет и не удаляет и перечисляет эти файлы; `DOC501` в `check` называет их тоже.
- **Единые файлы** (`docc build --single`, `docc build --html`; флаги независимы и сочетаются с `--full`) пишутся рядом с каталогом вывода: имя каталога плюс `.md` или `.html` (`docs/out.md`, `docs/out.html`; с `--full` — `docs/out-full.md`, `docs/out-full.html`). Программа, которая показывает страницы сама, читает `docc compile`. Однажды созданный файл пересобирает каждый `docc build` и без флага, чтобы не отправить устаревший; файл, который docc не писал (Markdown без метки, HTML без острова данных), остаётся как есть с сообщением в stderr, заменить его можно явным `--single` или `--html`. Это дополнительный вывод для чтения: каталог Markdown собирается всегда как раньше, единые файлы в Git не коммитятся, `docc check` и `DOC501` их не проверяют. Файл пишется, только если изменилось содержимое; при ошибках 1xx–2xx не пишется ничего; путь, попадающий внутрь `src`, `schemas` или на конфиг, — ошибка использования (код 2). Страницы идут в порядке дерева (с учётом `order`): сначала корни и потомки по `parent`, затем документы без родителя. Ссылки между страницами — внутрифайловые якоря: страница `<id>`, поле `<id>--<якорь поля>`. Единый Markdown: комментарий-метка, дерево документов, затем страницы через `---`; для точных якорей перед страницей и перед каждым полем стоит `<a id="…"></a>`; строка про `_tree.md` не выводится. Единый HTML — одностраничное приложение в одном файле (запросов в сеть нет): Preact с htm (встроен, около 13 КБ, без сборки на Node), стили и JSON-остров с данными страниц внутри. Markdown каждого блока разбирает библиотека comrak (расширения GFM), HTML пишет свой код docc, сырой HTML из текста документов отбрасывается, сохраняется только `<br>` в ячейках таблиц. Приложение показывает одну страницу за раз (адрес `#<id>` или `#<id>--<поле>` открывает страницу и прокручивает к полю, `#<id>/<JSON Pointer>` — к абзацу; неизвестный адрес открывает первую страницу с сообщением «По этой ссылке ничего не найдено»; «Назад» браузера возвращает к месту чтения). Режим один, переключателей режимов нет. Шапка: название проекта, кнопка шкалы времени, на узком экране «☰» и «Поиск», меню «⋯» с одним пунктом «Сбросить всё…»; до 600 px название скрыто, а кнопка шкалы занимает свободное место. Левая колонка: поиск (находит абзацы: все слова в абзаце или в названии его страницы; число найденного, первые 30, переход к абзацу; клавиши `/` и Ctrl+K) и вкладки «Страницы / Правки / Комментарии». На вкладке «Страницы» дерево документов с заголовками текущей страницы под ней: верхний уровень всегда раскрыт и не сворачивается, ниже свёрнуто и раскрыт только путь к текущей странице; заголовки страниц одного уровня стоят на одной вертикали за иконкой вида документа (у вида без своей иконки — значок файла), стрелка раскрытия справа; заголовки текущей страницы, каждый со значком `#`, стоят с ней в одной рамке; документы без родителя идут после дерева на верхнем уровне; длинные списки показывают окно вокруг текущего элемента и кнопки «ещё». У страницы хлебные крошки по `parent`, однострочные поля собраны в список свойств, дочерние страницы — списком с началом текста (до 300 знаков), внизу соседние страницы по порядку дерева. Бейджей вида, статуса, приоритета и тегов и блока связей в HTML нет (в Markdown они есть); в полной сборке скрытый документ помечен «скрыт». Левая колонка закреплена от 1280 px, уже — выезжает модальным окном по кнопке ☰ (закрывается «Закрыть», Esc или касанием вне его); поле для карточек комментариев справа появляется от 1024 px, только когда у страницы есть комментарии или открыт редактор, на более узком экране карточки стоят под абзацем; на сенсорном экране и уже 820 px все кнопки не меньше 44 px. «Сбросить всё…» после подтверждения удаляет всё, что файл хранит в этом браузере: имя, положение шкалы, открытую вкладку и комментарии. Без скриптов показывается сообщение. Светлая и тёмная тема по настройке системы, печать (Ctrl+P) — текущая страница. Вид один, шаблонов и своих стилей нет.
- **Блоки и история.** Блок — элемент документа: строка массива строк или значение другого поля или раздела целиком (таблица и список — один блок); адрес блока — `id` документа и JSON Pointer элемента (`/body/2`). Перед каждым блоком docc ставит маркер, по которому режет страницу; имя маркера выбирается так, чтобы его не было в тексте страницы. История берётся из Git при сборке (`git log --first-parent` по `src` и `git cat-file`; слияние — одно изменение основной линии): у блока — все коммиты, менявшие его текст (дата и разница по словам), последним идёт незакоммиченное состояние рабочей копии. Файл читают и вне команды (документация бывает технической, внутренней, для заказчика, книгой), поэтому в обычной сборке в истории нет скрытого (`notes`, `docIgnore`, `hidden`), версий, в которых документ был скрыт (`hidden: true`; такой версии для истории нет, как нет файла: документ, написанный скрытым, появляется в истории, когда его показали, а скрытый на время продолжает историю от последней показанной версии), авторов и сообщений коммитов; с `--since` нет и истории до этой ревизии: состояние на ней — первая версия, подписанная датой ревизии. Полная сборка (`--full`) хранит всё. Строки массива сопоставляются между версиями по равному тексту, затем по похожему (коэффициент Дайса по парам букв не ниже 0,3), поэтому вставка абзаца не сдвигает историю соседей; пары не пересекают порядок: абзац, удалённый в одном месте, и абзац, добавленный в другом, — удаление и добавление, а не одна переписанная строка; переименованное поле начинает историю заново. **Шкала времени** открывается кнопкой в шапке с итогом («Правки: 11 дн. назад → сейчас»; момент в прошлом — точным временем, одно выбранное сохранение — его временем; пока T в прошлом, кнопка жёлтая): на широком экране панелью под шапкой, уже 820 px — шторкой снизу, высота шапки не меняется. В ней сохранения документации (коммиты, последней — несохранённая рабочая копия) точками на одной линии с двумя концами: «Правки с:» (S) и «Текст на:» (T), у каждого конца относительное время («11 дней назад», «сейчас»; `Intl.RelativeTimeFormat`) и точное («14 окт. 2026 г., 21:38»; `Intl.DateTimeFormat`). Точки стоят на равных расстояниях, потому что сохранения идут пачками; точки, менявшие текущую страницу, темнее, а при числе сохранений больше 120 точки есть только у них. Под линией поле «Текст на дату» (T — последнее сохранение этого дня или раньше) и, если страницу меняли, флажок «Только сохранения, менявшие эту страницу (N)», при числе сохранений больше 120 включённый сразу. Ниже — список сохранений по дням, новые сверху: день свёрнут в строку «Пт, 17 октября 2026 г. · Сохранений: 35 · эта страница: 4», раскрыты день с T и последний; дни и сохранения дня идут по 15 («Показать ещё»). У сохранения точное время, относительное, пометка «эта страница», в полной сборке автор и сообщение; сохранения между S и T подсвечены. Нажатие на сохранение показывает, что оно изменило (S — предыдущее сохранение, T — оно), как история версий Google Документов; у выбранного сохранения кнопка «Правки после этого сохранения» ставит S на него, а T — на «сейчас». Уже 820 px шторка закрывается после выбора сохранения или даты, у неё есть кнопка «Закрыть», а верх шторки с концами, датой и флажком не уезжает при прокрутке списка. На сенсорном экране при числе сохранений больше 120 линии с ползунками нет (пальцем не попасть в одно из тысяч сохранений): выбор — днями и датой. Ползунки тянет сама шкала, а не стандартные ползунки браузера (они остаются для клавиатуры): нажатие мышью или пальцем берёт ближайший ползунок, нажатие на пустую линию переносит его туда, а у двух ползунков ближе ширины ползунка (например, после выбора сохранения) первое движение решает, какой взят: влево — «Правки с», вправо — «Текст на». Длинный список рисуется, только пока шкала открыта. На сенсорном экране ползунки и строки не меньше 44 px. По умолчанию S — ревизия `--since`, без неё — «сейчас» (правки не подсвечены), T — «сейчас»; S запоминается в браузере, T при каждом открытии «сейчас». Страница показывает текст на момент T: для старых версий строковых блоков сборка кладёт в файл их HTML (таблицы, списки и объекты прошлых версий показываются простым текстом; вставки и ссылки в старом тексте разворачиваются по нынешним документам), блоков, которых на момент T ещё не было, нет, а блоки, удалённые после T, стоят на прежнем месте со своим последним текстом. Пока T в прошлом, над страницей плашка «Вы смотрите страницу такой, какой она была …» с кнопкой «Вернуться к сейчас», комментарии не показываются и не оставляются. Правки между S и T нарисованы прямо в тексте, как в diff Git и IDE: слова старой версии сопоставляются со словами отрисованного абзаца (ссылки, списки и таблицы сохраняются), добавленные подчёркнуты на зелёном, удалённые зачёркнуты на красном, для экранного диктора с подписями «добавлено:»/«удалено:»; если совпадает меньше 40 % слов, а также у блоков кода, над абзацем свёрнут «Прежний текст» (у кода раскрыт). Слева от абзаца полоса: синяя — изменён, зелёная с «+» — новый; удалённый абзац стоит свёрнутой строкой «Удалён абзац: “…”» на своём прежнем месте (место угадывается по старому указателю: перед блоком с тем же указателем, иначе после последнего блока того же массива). Вкладка «Правки» — правки между S и T по разделам дерева (раздел — страница первого уровня под корнем вместе с потомками), как файлы в pull request: сверху «Правки: N · 11 дней назад → сейчас» и фильтр «Все / Изменено / Добавлено / Удалено» с числами, ниже свёрнутые группы с названием раздела, числом и подписанными счётчиками; раздел текущей страницы раскрыт. В группе строки идут с подписями страницы и заголовка, под которым стоит абзац; у строки пометка «изменён», «новый» или «удалён» и начало текста в одну строку, строка открывает страницу на абзаце; группа показывает по 15 строк («Показать ещё»). Фильтр и раскрытые группы сохраняются при переключении вкладок. Абзац, появившийся после S и снова удалённый до T, не показывается. Тексты версий показываются для чтения: ссылки `[[id]]` — названиями, без разметки Markdown. Вне Git-репозитория истории и шкалы нет.
- **Комментарии.** Комментарий оставляется к выделенным словам: под выделением появляется кнопка «Комментировать выделенное» (на сенсорном экране — в нижней полосе); кнопок у абзацев нет. Карточка стоит на поле справа (на узком экране — под абзацем; у абзаца видны две, остальные за «Ещё комментариев: N», текст карточки до 4 строк); фрагмент подсвечен в тексте и хранится с 32 знаками до и после, чтобы найти его среди повторов, а если его уже нет — карточка помечена «Фрагмент изменён». Комментарий браузера, оставленный в прошлой сборке, ищет свои слова: если в его абзаце их нет (выше вставили абзац и указатель сдвинулся), он показывается у ближайшего абзаца, где они есть. Комментарии документов (`$comments`) сборка кладёт в файл как есть: у своего блока, а потерявшие место (`DOC215`) — небольшим списком «Комментарии, потерявшие своё место» вверху страницы; ответ на поле формы стоит у поля, где бы оно ни было. Новый комментарий браузера получает `id` вида `c-` и 10 знаков, как у `docc comments apply`. На сенсорном экране кнопки «Изменить», «Удалить» и «Вернуть» не ниже 44 px, нижняя полоса прячется, пока фокус в редакторе, поле текста растёт не выше 40 % экрана, а кнопка «Сохранить» остаётся видна под ним; область просмотра сжимается под экранную клавиатуру (`interactive-widget=resizes-content`, Chrome на Android). Текст или голос: кнопка «Надиктовать» включает распознавание речи браузера (Web Speech API; Chrome и Edge отправляют звук своему сервису), запись идёт до повторного нажатия («● Идёт запись — нажмите, чтобы остановить»), после паузы распознавание запускается снова; без распознавания кнопки нет. При первом открытии файл спрашивает имя в небольшом окне «Как вас зовут?» («Пропустить» оставляет его пустым, тогда редактор сначала просит имя); имя подставляется в поле «От кого», видно и меняется в «⋯», а «Сбросить всё» спрашивает снова. Поле «От кого» можно изменить у отдельного комментария (на созвоне можно записать комментарий от другого участника). Свой комментарий можно изменить и удалить, удаление отменяется кнопкой «Вернуть». Закрытие редактора с несохранённым текстом требует подтверждения. Комментарии хранятся в браузере (`localStorage`), первый сохранённый напоминает, что он лежит только в этом браузере. Вкладка «Комментарии» — плоский список комментариев браузера и документов (страница и фрагмент, текст, автор, без статусов; комментарий без места помечен «страница удалена» или «абзац удалён»; обработанные комментарии из документов удалены и в файл не попадают) и две кнопки: «Скопировать комментарии» кладёт в буфер текст для мессенджера (список комментариев и в конце строка `docc-comments:<base64 файла>`; импорт берёт последнюю такую строку и терпит перенос base64 на несколько строк), «Скачать файлом» сохраняет `{"docc": "comments", "version": 1, "comments": [{id, doc, path, quote, fragment, prefix, suffix, text, author, created, build}]}` (`fragment`, `prefix`, `suffix` — только у комментария к фрагменту). Отметок «отправлено» нет: комментарий остаётся в браузере, пока его не импортируют в проект. `docc comments import` принимает и файл, и скопированный текст (`-` — со стандартного ввода) и записывает комментарии в `$comments` их документов через `docc comments apply` (меняется только это поле); импорт коммитят вместе с документами. Комментарий к прошлой сборке (`build` — короткий хеш коммита, из которого собран файл) переносится к своему блоку: документ на том коммите читается из Git и сопоставляется с нынешним тем же выравниванием блоков, что у истории и `docc diff` (`history::ops`); ответ встаёт к своему полю по `id`; комментарий к удалённой странице не записывается и называется в выводе. Записанные комментарии видны в HTML на своих абзацах и во вкладке «Комментарии»; комментарий браузера, который уже есть в документах, из браузера убирается. Сам docc текст по комментариям не меняет: агент читает `$comments` (или `docc comments`), исправляет текст и в том же коммите удаляет обработанный комментарий (`docc comments rm <id>`). **Ответы на поля формы.** Поле формы («Поля формы», раздел 6) стоит в тексте: вопрос, варианты (радиокнопки или галочки) или текстовое поле и кнопка «Сохранить»; последним вариантом радиокнопок и галочек идёт «Свой ответ» с полем для текста (у радиокнопок — вместо вариантов, у галочек — вместе с ними), и сохранённый свой ответ показывается в нём; без сохранённого имени рядом поле «От кого». Ответ сохраняется в браузере как комментарий с `input` (`id` поля), `answer` (данный ответ: текст, выбранный вариант или отмеченные варианты), `text` (то же словами) и `quote` (поле, каким оно было при ответе); в документ он записывается с `input` и `answer` без `text`; у одного браузера один ответ на поле, новый занимает место прежнего. Карточек на поле у ответов нет: под полем список «Ответы» — последний ответ каждого автора (ответы без имени — каждый отдельно), с пометкой «на прежний вопрос», если вопрос или варианты изменились после ответа, и у своего ответа «в этом браузере · Удалить». Ответы уходят вместе с комментариями той же кнопкой и тем же импортом; файл с ответами пишется версией 2 (старый docc отвечает `unsupported version 2`, а не теряет ответы), без ответов — версией 1, как раньше. Импортированный ответ встаёт к своему полю по `id`; если текст поля другой, место `changed`, если по `at` поля нет — `lost` (`DOC215`). `docc comments` печатает у ответа «answers form field <id>» и поле вместо блока; в Markdown ответ стоит на месте поля строкой «💬 **Автор**, дата, ответ на «вопрос»: ответ». Поле в прошлом (шкала времени) недоступно, а изменённое поле показано прежним текстом. Выделение внутри поля комментарий не открывает. Принятый ответ агент записывает в текст, убирает поле и удаляет ответы; отдельного состояния «поле закрыто» нет. **В Markdown** (`docs/out`, `out.md`) комментарий стоит под своим блоком цитатой «> 💬 **Автор**, дата, к словам «…»: текст», комментарии без места — списком вверху страницы; `--no-comments` убирает их.
- **Вывод compile.** `docc compile [--rev <ревизия>] --format json` печатает в stdout ровно одну строку — JSON-объект — и ничего не пишет на диск. Объект печатается всегда, в том числе при сломанных источниках и при сбое (неверный `docc.json`, неизвестная ревизия, флаг): `{"$schema": "urn:docc:schema:compile:1", "ok", "summary", "diagnostics", "project", "tree", "pages"}`. `summary` и `diagnostics` — как у `docc validate --format json`, но список полный (без `--max-diagnostics`); сбой — одна диагностика с кодом `config`, `usage` или `error`. `ok` — нет ошибок и предупреждений не больше `maxWarnings` (`--max-warnings`); код выхода как у `validate`: `0`, `1` (ошибки или лишние предупреждения), `2` (сбой). При ошибках групп 1xx–2xx `tree` и `pages` пустые. `project` — `{title, lang, brand}`: заголовок первой страницы дерева, `lang` и `branding` (`{name, url, logo, accent, accentLight, header}`, логотип — `data:`-адрес; без `branding` — `null`). `tree` — дерево: `{"type": "page", "id", "path", "title", "children"?}` (дети по `parent`, затем страницы без родителя), в режиме папок ещё `{"type": "folder", "path", "title", "id"?, "children"}` (`id` — своя страница папки, в том числе страница только с заголовком: она есть и в `pages`). `pages` — страницы для читателя в порядке дерева, без скрытых документов и заметок: `{id, path (от src, «decisions/monolith.json»), title (с номером), kind, status, tags, parent, crumbs, props, sections, blocks}`. `sections` — заголовки полей и разделов `$sections` в порядке страницы `[{id, title, level}]`, `id` — якорь заголовка, тот же, на который ведут `[[id#поле]]` (в HTML блоков ссылка `#<страница>--<id>`). `blocks` — блоки страницы `[{p, s, h, sec, i?}]`: указатель JSON Pointer (пустой у блока сносок), исходный текст, HTML (тот же, что у блока в HTML-файле; ссылки `#<id>` и `#<id>--<якорь>`, картинки — `data:`-адреса), `sec` — `id` раздела, под которым стоит блок (`null` выше первого заголовка; заголовок раздела стоит перед первым блоком с его `id`, после блоков предыдущих разделов), `i` — поле формы. `props` — однострочные поля списка свойств `[{k, id, p, s, h}]`. `comments` — комментарии страницы из `$comments` в порядке файла, без `email` (вывод для читателя): `{id, at, quote, fragment?, prefix?, suffix?, text | input+answer, author, created, place}`, `place` — `same` (блок читается как в `quote`), `changed` (блок правили) или `lost` (`DOC215`; показывается вверху страницы). Истории в выводе нет; `docc diff` комментарии не показывает. `--rev` (коммит, ветка, тег, любое tree-ish) читает проект из дерева ревизии через `git ls-tree -r` и `git cat-file --batch`, без checkout: `docc.json`, схемы, документы, `docc.lock`, картинки, логотип и файлы `trace.scan` — те, что в ревизии, вставки и ссылки разрешаются в ней же, позиции диагностик — в её файлах. Корень проекта ищется как обычно (ближайший `docc.json` на диске или `--config`), но на диске его может не быть: в голом зеркале `docc compile --rev <sha> --config docs/docc.json` читает проект из папки `docs` ревизии; `docc.json`, которого нет в ревизии, означает умолчания. Форму объекта описывает `docc schema compile` (JSON Schema 2020-12, `$id` равен `$schema` вывода; при смене формы меняется номер). `--format text` печатает отчёт `validate` и строку `compiled N pages`.
- **Вывод log и diff.** Обе команды читают Git без checkout (в голом зеркале — с `--config`), печатают с `--format json` ровно одну строку JSON и ничего не пишут; полные 40-символьные хеши. Сбой (неизвестная ревизия, не Git) — отчёт с диагностикой `usage` и код `2`, иначе код `0`. `docc log [--rev R] [--since SHA]` — `{"$schema": "urn:docc:schema:log:1", "commits": [...]}`: коммиты первой родительской цепочки `R` (по умолчанию `HEAD`), которые меняли что-либо в папке `src`, от новых к старым, до `SHA` не включая (`SHA` вне этой цепочки — ошибка); слияние — его изменение относительно первого родителя. Коммит — `{sha, parents, author: {name, email}, committer: {name, email}, date (дата автора, RFC 3339), subject, body, commentsOnly, files}`; файл — `{status: A|M|D|R, path (от src), oldPath? (у R), id?, title?, blocks: {add, ch, rm}, commentsOnly, broken?, hidden?}`. `id` и `title` есть у JSON-файла (документа); у удалённого — последний заголовок; копия — `A`, смена типа — `M`; файл, перенесённый в `src` или из неё, — `A` или `D`. `blocks` считает блоки страницы (`body` и свободные поля; не заголовок, метаданные, `notes`, `$comments`; пустые не считаются) тем же сопоставлением, что у `diff` и истории HTML: новый документ — все блоки `add`, удалённый — `rm`. `broken: true` — версия не JSON-объект: счётчики `0`, следующая исправная считается от последней исправной. `hidden: true` — документ скрыт от читателя в этой версии (счётчики — как у любой версии); версия, в которой скрытый документ показан, считает все его блоки `add`, как `diff`, где у прежней стороны страницы нет. `commentsOnly` у файла — `M`, где обе версии после удаления верхнего `$comments` равны как JSON, а сами `$comments` различаются; у коммита — все его файлы такие. Один `git log` и один `git cat-file --batch`; с `--since` файлы начинают с версии в `SHA`. `docc diff <base> <head> [--path P]` — `{"$schema": "urn:docc:schema:diff:1", base, head, files}`; `base` и `head` — любые tree-ish (пустое дерево `4b825dc642cb6eb9a060e54bf8d69288fbee4904` для корневого коммита), каждая сторона собирается из своей ревизии, как `docc compile --rev` (ссылки и вставки — в ней же; скрытые документы не показываются). Файл — `{status: A|M|D|R|=, path, oldPath?, id, title, sections: {old, new}, blocks: [{op: same|add|rm|ch, old, new}], broken?}`; блок стороны — как блок `compile` (`{p, s, h, sec, i?}`), у однострочного поля списка свойств ещё `k`, свойства идут перед блоками. Без `--path` — изменённые документы (по Git), в `blocks` только `add`, `rm`, `ch` по порядку документа; с `--path` (путь любой из сторон) — один этот документ со всеми блоками, включая `same`: новые блоки по порядку, удалённый стоит перед следующим блоком, который шёл за ним, — так ряд читается как две колонки; `=` — документ не менялся. `op` сравнивает исходный текст `s` (у блока сносок — HTML): при изменённой цели ссылки или вставки `h` в `same` может различаться. `broken: true` — сторона файла в ревизии, которая не собирается (ошибки 1xx–2xx или неверный `docc.json`): `blocks` пуст. Схемы: `docc schema log`, `docc schema diff`.
- **Детерминизм:** стабильная сортировка, без меток времени, переводы строк только `\n`, UTF-8 без BOM (так же для единых файлов).

## 11. Windows, Git и скилл для агентов

- **Windows:** CRLF и BOM во входных файлах и в `out/` нормализуются при чтении и при сравнении (`DOC501`), поэтому `.gitattributes` не нужен. Файлы пишутся с `\n`. Регистронезависимые файловые системы: `id` и имена папок только строчные, зарезервированные имена Windows запрещены; пути сортируются как строки с `/`.
- **Git:** две ветки, создавшие файл с одним именем, дают конфликт «both added» (верный сигнал о занятом `id`). Конфликт в `out/` или `docc.lock` решается `docc build`. После merge CI запускает `docc check` на целевой ветке (лучше в очереди merge); расхождение `out/` и `_tree.md` без конфликта лечится `docc build`.
- **Скилл `docc` (лежит в репозитории `docc` как `skills/docc/SKILL.md`; ставится командой `npx skills add uxname/docc`):** формат документа (отсылает к `docc schema document`; схемы видов агент пишет в `docs/schemas` сам, скилл набор видов не навязывает), цикл «правка → `docc validate` → `docc build`», чтение JSON-диагностики и `docc explain <код>`, заметки `notes` (читать при правке; ссылки в них проверяются), скрытые документы, вставки `{{id#поле}}`, `docc build --full` для аудита, примеры трёх хуков Claude Code (запрет правок `docs/out`; после правки файла — только ошибки синтаксиса и схемы этого файла; в конце хода — `docc build` и `docc check --max-warnings 0`, чтобы пачка новых документов со ссылками друг на друга не блокировалась на полпути), пути хуков через `$CLAUDE_PROJECT_DIR`, пример шага CI (`docc check`), правила для агента: не подавлять ошибку через `docIgnore` вместо исправления, ссылаться только на существующие `id`, при `DOC209` и `DOC402` перечитать источник и подтвердить связь `docc ack` (читать все источники из списка, который печатает `ack`), коммитить только по просьбе пользователя. О формальной связи с `index` скилл только предупреждает: проверка достижимости проверяет форму, смысл связи остаётся ревьюеру. Как вернуть диагностику модели после правки, скилл описывает отдельно (для Claude Code это зависит от кода выхода хука). Хуки агента и CI `init` не создаёт (только Git-хук `pre-commit`).
- **Распространение:** готовые бинарники для Linux, macOS и Windows в GitHub Releases (`install.sh`, `install.ps1`, `docc update`); сборка из исходников `cargo install --git`; скилл — `npx skills add uxname/docc`.

## 12. Архитектура

Модули (`src/`): `cli` (команды и разбор флагов), `config`, `loader` (свой рекурсивный разбор JSON около 250 строк: дерево узлов с указателем, смещениями и позициями, ключи с дублями; из него строится значение для схемы), `schema` (JSON Schema), `mdscan` (свой сканер блоков кода, заголовков, HTML-тегов и ссылок), `engine` (граф ссылок, правила, подавления), `source` (откуда читаются файлы проекта: диск или дерево ревизии Git для `docc compile --rev`), `rules` (реестр правил: код, имя, группа, уровень по умолчанию, признак ядра, текст для `explain`), `render`, `trace`, `report` (text, json), `history` (история из Git и одно сопоставление блоков между версиями — `ops`, общее для истории HTML, `log` и `diff`), `changes` (вывод `log` и `diff`), `comments` (комментарии из HTML); `docc.lock` ведёт модуль `engine`.

**Зависимости:** `jsonschema` для схем, `regex`, `unicode-normalization`, `serde_json`, `comrak` (разбор Markdown для HTML), `icu_collator` (сортировка заголовков), `zip`, `tar`, `flate2` и `ureq` с rustls (для `docc update`). Разбор флагов свой и повторяет пакет `flag` из Go, на котором docc был написан сначала. YAML-библиотек нет. Схема вида видит документ целиком, служебные поля для неё всегда разрешены (форму `docIgnore` проверяет `DOC108`, форму остальных служебных — `DOC105`); `$ref` в схемах разрешён только на другие файлы внутри каталога схем (удалённые и выходящие за каталог запрещены), некорректный файл схемы — ошибка настроек (код выхода `2`); ошибки схемы сопоставляются с позициями по таблице «указатель → позиция» (`required` — позиция объекта, `additionalProperties` — позиция ключа, `oneOf` и `anyOf` схлопываются в одну диагностику). `docc explain`, `docc rules` и скилл строятся из реестра правил, поэтому не расходятся с кодом.

**Принципы:** golden-тесты (вход → диагностики), чистое ядро, ввод-вывод на границах, стабильные коды.

## 13. Нефункциональные требования

- Один статический бинарник без сети.
- `docc check` и `docc build` на 1000 документов не дольше 300 мс каждая (цель; замер на Linux — около 250 мс). Замер: 1000 файлов по 5–20 КБ русского текста, холодный и тёплый кэш, Linux и Windows с антивирусом; загрузка, схемы, правила и сравнение `out/` измеряются отдельно.
- Детерминизм вывода и порядка диагностик на трёх ОС.
- Понятные сообщения с подсказкой, как исправить.

## 14. План реализации (один релиз, этапы без версий)

0. **Спайк:** позиции токенов JSON (строка и колонка в рунах, включая внутренность строк с экранированием), обнаружение дублей ключей, замер скорости на 1000 синтетических документов. Выход из этапа: позиции верны на тестовых строках с `\n`, `\uXXXX`, суррогатными парами, BOM и CRLF; дубли ключей находятся; замер выполнен, иначе цели скорости пересматриваются.
1. **Загрузка, граф, отчёт:** `DOC101`–`DOC105`, `DOC112`, `DOC201`–`DOC205`, `DOC210`, `DOC211`, `DOC215`; загрузка `docc.json` (пути, `roots`, реестры, `rules` с уровнями и параметрами, `recommended`); `validate` в text и json.
2. **Схемы и реестры:** `DOC106`–`DOC108`, `docc schema`.
3. **Содержимое, Markdown, стиль:** `DOC212`–`DOC214`, `DOC301`–`DOC314`, `DOC352`, `DOC353`.
4. **`build` (включая вставки, картинки, `order`, `numbering`, `lang` и `--full`), `check`, `docc.lock` и `ack`:** `DOC209`, `DOC501`, `DOC503`, `DOC901`.
5. **Механики:** `explain`, `rules` (с действующими уровнями), пользовательские правила (`DOC800`), `--max-diagnostics`, `--max-warnings`, теги в коде (`DOC401`–`DOC403`).
6. **Скилл `docc`** и сборка бинарников.

**Готово, когда:**

- на каждый код из таблицы раздела 7 есть golden-тест «красный» и «зелёный» (для `DOC800` — на правилах `forbid` и `require`);
- встроенная схема документа ловит повтор в `tags` (тест);
- схема вида без `additionalProperties` на верхнем уровне даёт код выхода `2`, лишнее поле в строгом виде — `DOC106` (тест);
- есть тесты на эталонные отпечатки `docc.lock`, на `docc ack`, на `endLine` и `endColumn`;
- `docc build --full` показывает скрытые документы, заметки, подавления и границы вставок и не меняет `out/` (тест);
- `docc build --single --html` пишет `docs/out.md` и `docs/out.html`: ссылки только внутрифайловые, порядок страниц как в дереве, скрытое только с `--full`, `<script>` из текста не попадает в HTML, `<br>` в ячейке таблицы сохраняется, повторная сборка не меняет файл, при ошибках 1xx–2xx файлов нет (тесты и golden);
- некорректный файл схемы и `$ref` вне каталога схем дают код выхода `2` (тест);
- позиции верны для строк с экранированием и многострочных значений (тест);
- `docc check` и `docc build` на 1000 синтетических документов укладываются в 300 мс на Linux (выполнено: около 250 мс); на Windows не замерялось;
- два прогона `docc build` на трёх ОС дают побайтово одинаковый `out/`;
- `docc init` в пустом каталоге создаёт проект, проходящий `docc check`, а в Git-репозитории — хук `pre-commit`;
- сам проект `docc` описан своими документами и проходит `docc check` в CI;
- по скиллу агент исправляет не менее 9 из 10 синтетических ошибок за две итерации.

## 15. Метрики успеха

- Доля синтетических ошибок, исправленных агентом за две итерации, не ниже 9 из 10 (критерий готовности выше).
- Ошибки структуры и ссылок, которые ревьюер нашёл руками, а `docc` пропустил: 0.
- Доля подавлений через `docIgnore` среди всех исправлений агента (контроль).
- Время `docc check` на реальной документации.

## 16. Принятые решения и умолчания

**Решено владельцем (HTML-приложение, 2026-10-15):** HTML-сборка становится одностраничным приложением на Preact + htm без сборки на Node; история блоков из Git, блок — элемент JSON; нужны история блока, подсветка изменённого с выбранной версии и история страницы; комментарии к блокам текстом и голосом (Web Speech API, звук уходит в Google — допустимо), выгрузка в JSON, импорт в репозиторий со статусом «обработан / не обработан» и командой списка необработанных для агента; экспорт: страница, всё одним .md, всё в .zip; на звонке экран показывает один человек.

**Решено владельцем (единые файлы, 2026-10-04):** рядом с каталогом Markdown, не вместо него; флаги `--single` (один .md) и `--html` (один .html); не в Git и не под `check`; скрытое только с `--full`; единый .md для чтения человеком; HTML с деревом, поиском, тёмной темой и печатью; конвертер Markdown в HTML (сначала goldmark, после перехода на Rust — разбор comrak с тем же HTML); имена из `out` и `outFull` без новых настроек.

**Решено владельцем (типы, связи, номера):** схемы обязательны и строги (как TypeScript): у каждого документа есть вид со схемой, схема явно говорит, разрешены ли лишние поля; связь — только ссылка в тексте (поля `links` нет); `docc.lock` вместо `reviewed`: изменения после подтверждения отслеживает файл рядом с `docc.json`, а не поле документа; номера ставит `docc` (`numbering`), вручную их не пишут; виды документов не навязываются скиллом: проект заводит свои виды сам; правила `nursery`, `--fix`, `overrides`, реестр `kinds`, `wordsFile` и `allowFile` убраны.

**Решено владельцем:** внутренний инструмент; единый релиз (все возможности в первом выпуске); формат источников JSON; YAML нет; `id` = имя файла; корни `roots` (по умолчанию `["index"]`); сирота = недостижим от корня, смысл связи на ревьюере; схемы JSON Schema, правила текста с подавлениями, теги `docc:` в коде; гигиена связей, содержимого и стиль; пресет, `explain`, `rules`, вывод text и json; `init` создаёт `docc.json`, схему `page`, `index.json` и хук `pre-commit`; формат агенту даёт скилл и `docc schema`; `build` отдельной командой; без `--changed`; без шаблонов; без `context`, `mv`, миграции, переходов статусов, Mermaid, глоссария; Linux, macOS, Windows; имя `docc`; без `fmt`; повторы в `tags` ловит встроенная схема; отчётов `sarif` и `github` пока нет (решение откладывается до выбора CI). Решено также: поле `body` и текст массивом абзацев; скрытые заметки `notes`; скрытые документы `hidden`; вставка текста `{{id#поле}}`; общие части схем через `$ref`; полная сборка для аудита `docc build --full`. Сравнение с аналогами (Spectral, ESLint и Biome, Vale и markdownlint, Sphinx-Needs, StrictDoc, Doorstop, Backstage) готового решения не нашло: пишем своё (сначала на Go, с 2026-10-17 на Rust). Заимствовано: подозрительные ссылки (Doorstop), свои правила в конфиге (Spectral), конечная позиция ошибки (ESLint).

**Решено владельцем (переход на Rust, 2026-10-17):** docc переписан с Go на Rust ради скорости и надёжности типов. Поведение сохранено; каждое отличие от Go-версии записано в `docs/rust-port/` (было, стало, почему). Совместимость со старым `docc.lock` не требуется. Цель скорости — `docc check` и `docc build` на 1000 документов не дольше 300 мс (Go-версия — около 600 мс).

**Решения редакции 6 (после аудита продукта, 15 октября 2026):** `ack` подтверждает только изменившиеся связи и печатает их; `docc init` пишет `maxWarnings: 0`; `DOC209` объединяется по документу-цели; новое правило `DOC110` (предупреждение); `DOC202` называет ближайшие `id`; `build` не удаляет файлы, созданные не им, а отказывается работать; ошибки запуска и конфигурации в json — отчёт `{summary, diagnostics}`; `docc` — публичный проект с открытым кодом. Не делались: защита `out/` через файл-маркер и `--dry-run`, вынос скилла в несколько файлов, переупорядочивание диагностик по позиции (ошибки по-прежнему выводятся раньше предупреждений).

**Решения редакции 8 (после UX-аудита HTML-файла, 15 октября 2026):** HTML-файл отправляется заказчику, поэтому в обычной сборке в нём нет `notes`, `docIgnore`, `hidden`, авторов и сообщений коммитов, внутренних замечаний и истории до `changesSince`; точка отсчёта изменений задаётся сборкой (`changesSince`), а не выбором коммита; изменения обходятся по одному со счётчиком и сводкой по страницам, удалённое показано; замечания уходят текстом для мессенджера или файлом, импорт принимает оба вида, у замечания есть ответ команды и признак «внутреннее»; поиск находит абзацы, у абзаца есть адрес; `build` пересобирает существующие единые файлы. Не делались: стартовый экран-обзор согласования, режим чистого чтения, перевод видов документов, статическая разметка для просмотра без скриптов, отдельная модель адаптива для планшета.

**Решения редакции 9 (переделка интерфейса HTML-файла, 15 октября 2026):** два режима, «Чтение» (только итоговый текст) и «Работа» (правки, замечания, инструменты), переключатель в шапке, первый запуск — «Чтение»; правки рисуются прямо в тексте по словам, как в diff Git и JetBrains, с полосой на полях, удалённые абзацы стоят на своём месте; плавающий навигатор и вкладки левой колонки «Страницы / Правки / Замечания» вместо панелей над статьёй, которые после прокрутки открывались за краем экрана; замечания — карточками на поле, в том числе к выделенному фрагменту; отметка «просмотрено», стартовый обзор правок, окно «Клавиши и цвета»; экспорт, печать, точка отсчёта и истории убраны в «⋯». Интерфейс выработан дискуссией трёх дизайнеров и судьи с внешним мнением, проверен тремя независимыми аудиторами на o2. Карточки на широком экране не меняют высоту абзаца, а наложившаяся карточка сдвигается ниже соседней. Не делались: перевод видов документов, группировка подряд идущих удалённых абзацев, статическая разметка без скриптов.

**Решения редакции 13 (имена правил, 17 октября 2026):** правила в `docc.json` и `docIgnore` называются именами, как в ESLint и Biome (`style/hedging`); код остаётся рабочим псевдонимом, его использование даёт предупреждение `DOC902` с именем в подсказке; три неточных имени заменены (`style/timeless-words` → `style/time-bound-words`, `schema/unregistered` → `schema/unregistered-tag`, `trace/unknown-id` → `trace/bad-code-tag`), прежние работают так же, как код; диагностика, `docc rules` и `docc explain` ставят имя перед кодом; HTML-файл при первом открытии спрашивает имя редактора; вкладка «Правки» сгруппирована по разделам со свёрнутыми группами.

**Решения редакции 15 (комментарии в документах, 22 октября 2026):** комментарии читателей живут в самих JSON-документах — плоский список в зарезервированном поле `$comments` (ADR-0023 Docspace); статусов, ответов, внутренних комментариев и `docc.comments.json` больше нет, вместе с ними ушли `docc comments done`, `--reply`, `--internal`, `--all` и «Архив» HTML-файла; обработанный комментарий агент удаляет в том же коммите, что и правку, заметка только для агентов — в `notes`. Поле пишет только docc: `docc comments apply` (add, edit, rm из stdin, всё или ничего, точечная правка файла); через него идут CLI, импорт HTML-файла и Docspace. Комментарий к прошлой сборке переносится к своему блоку тем же выравниванием, что у истории и `docc diff` (прежний поиск по цитате `comments::locate` удалён). Комментарии видны под блоками в Markdown, HTML и `docc compile`, без места — вверху страницы; `--no-comments` их убирает. `changesSince` из `docc.json` убран (история читается в Docspace и на шкале HTML-файла), версию для подсветки правок задаёт `docc build --html --since`. `"commitOut": false` — `docs/out` не коммитится (`docc init` так и пишет), `DOC501` не действует. В режиме папок дерево HTML-файла — дерево папок, как у `docc compile`.

**Решения редакции 14 (поля формы, 19 октября 2026):** в HTML-файл можно вставлять текстовые поля, радиокнопки и галочки; ответ хранится как комментарий. Работа над документом и просмотр разделены по ролям, а не переключателем: поля пишет автор через агента в JSON-источнике, читатель только отвечает в HTML (режимы «Чтение / Работа», убранные в редакции 12, не возвращаются). Поле — отдельный блок между абзацами, не внутри предложения; в Markdown его нет; чужие ответы видны всем с именами; принятое поле агент убирает сам. Ответ на изменённый вопрос не засчитывается молча: его `quote` сравнивается с текущим полем. Не делались: поле внутри строки текста, обязательные поля, свои варианты «Другое», состояние «поле закрыто».

**Решения редакции 12 (упрощение HTML-файла, 17 октября 2026):** документация бывает любой (техническая, внутренняя, для заказчика, книга), поэтому интерфейс не говорит о заказчике, команде и «отправленной версии», а «Замечания» называются «Комментарии»; режимы «Чтение / Работа» убраны, вместо «Точки отсчёта» и «Истории страницы» одна шкала времени с двумя концами («Правки с» и «Текст на») и относительными подписями, страницу можно посмотреть такой, какой она была (как в Google Документах); убраны история абзаца, кнопки «Замечание» и «История» у абзацев (комментарий — только к выделенному), отметки «просмотрено», навигатор правок с клавишами J/K/F7/V/C, метки правок у края окна, стартовый обзор правок, окно «Клавиши и цвета», статусы «отправлено» и предупреждение при закрытии, статусы «учтено / команда разбирает», бейджи и связи, группы «Без родителя» и «Без покрытия кодом», скачивание Markdown и zip и печать из меню; корень дерева не сворачивается; «Сбросить всё» очищает данные файла в браузере; диктовка идёт до повторного нажатия. Вкладка «Правки» подписывает все числа словами. Шкала стоит в шапке за кнопкой с итогом и открывает список сохранений с точным временем; на телефоне она — шторка снизу.

**Умолчания, выбранные при написании PRD (можно заменить):** `roots` по умолчанию `["index"]` и `id` = имя файла (решены владельцем в первом раунде вопросов); достижимость считается по рёбрам в обе стороны; `_tree.md` сохраняется; `baseline` не делается (готовых документов нет); уровни по умолчанию для правил, которых владелец не называл: `DOC107`, `DOC214` и `DOC312` — error, `DOC209`, `DOC314`, `DOC352`, `DOC353`, `DOC402`, `DOC403` — warn; `DOC401`–`DOC403` не работают без `trace.scan`; повтор в `tags` — ошибка ядра `DOC105` (агент убирает повтор сам); новая связь при `docc build` считается подтверждённой; поле `tags`, `docIgnore.path`, `--max-diagnostics` 20 для text, встроенные словари на русском и английском, драфт JSON Schema 2020-12, `docs/schemas/<kind>.json`, содержимое скилла, сборка из исходников (`cargo install --git`), параметры правил по умолчанию, запрет подавлять и отключать ядро, сборка `out/` при `init` и удаление лишних файлов `build` выбраны при написании PRD; так же выбраны синтаксис вставки `{{id#поле}}`, поле `hidden`, `DOC210` и `DOC211` в ядре, правило «к заметкам текстовые правила не применяются», каталог `docs/out-full` для полной сборки, формат `docc.lock` и отпечатков, синтаксис `customRules`, ключ `maxWarnings`, цели «300 мс на 1000 документов» (до перехода на Rust — секунда) и «9 из 10 ошибок за две итерации» и поставка скилла в архивах релиза рядом с бинарниками.

## 17. Приложение: точные определения

Приложение уточняет разделы 5–11 там, где реализации иначе пришлось бы придумывать поведение.

### А1. Проект и файлы

- **Корень проекта** — каталог ближайшего `docc.json`: он ищется в текущем каталоге, затем в родительских, до первого найденного (как у git и biome, поэтому хук и агент могут запускать docc из подкаталога); если файла нет нигде, корнем остаётся текущий каталог и действуют умолчания; `--config <путь>` задаёт файл конфигурации без поиска, корнем проекта становится его каталог. `docc init` вверх не ищет и создаёт файлы в текущем каталоге. Все пути в конфиге и в диагностиках отсчитываются от корня проекта, в диагностиках записываются с `/`.
- В `src` читаются только файлы `*.json` (расширение строчными). Обход `src` рекурсивный; остальные файлы, а также каталоги и файлы с именем на точку и символические ссылки пропускаются. Имя каталога, не подходящее под `id`, даёт `DOC104` (один на каталог, позиция 1:1 на его путь), файлы внутри читаются как обычно.
- **Файл документа:** UTF-8 (BOM допускается и отбрасывается), строгий JSON по RFC 8259 (без комментариев и висящих запятых), корень — объект; иначе `DOC101`. Пределы: размер файла не более 5 МБ, вложенность не более 64; превышение — `DOC101`.
- **`docc.json`:** тот же строгий JSON, допускается ключ `$schema`; неизвестные ключи и неверные типы — ошибка настроек (код выхода `2`, сообщение в stderr вида `docc.json:3:5: config error: …`). Диагностики и вывод `rules`, `explain`, `schema` идут в stdout, ошибки использования и настроек — в stderr. Цвета (ANSI) не используются.
- В `rules` ключ — имя правила (`text/forbidden-words`); код (`DOC301`) остаётся псевдонимом для старых конфигов и даёт `DOC902`; `docc explain`, `docc rules` и подсказки показывают имя первым; пользовательское правило переопределяется по имени `custom/…`; ключ группы (`text`, `style` и т. п.) задаёт уровень сразу всей группе.
- **`kind`** — строка из `a-z`, `0-9`, `-`, иначе `DOC105`. Если файла `docs/schemas/<kind>.json` нет, документ получает `DOC109` и проверяется только встроенной схемой. Ключевое слово `format` в схемах проверяется как утверждение.
- `docc init` не перезаписывает существующие `docc.json`, `docs/schemas/page.json`, `docs/src/index.json` и `.git/hooks/pre-commit` (пропускает с сообщением; чужой хук не трогает), затем всегда выполняет сборку. `docc --version` и `docc --help` работают как обычно.

### А2. Что проверяют текстовые правила

- **Какие строки:** значения `title`, `body` и всех свободных полей на любой глубине (элементы массивов, значения вложенных объектов). Не проверяются `kind`, `status`, `parent`, `order`, `tags`, служебные поля (`docIgnore`, `notes`, `hidden`) и ключи объектов. Строка делится на фрагменты вне блоков кода и обратных кавычек и приводится к NFC.
- **Слово** — максимальная последовательность букв Unicode, цифр, `_`, дефиса и апострофа внутри слова; сравнение без учёта регистра по границам слов, `быстр*` — префикс.
- `DOC303`: слова и фразы `TODO`, `TBD`, `FIXME`, `lorem`, `N/A`, «см. выше», «работает корректно», «по необходимости», «see above», «works correctly» и последовательность `???` без учёта регистра как отдельные слова; значение, состоящее только из тире («—», «–», «-»).
- `DOC304`: значение пусто или состоит из пробелов (для `title` действует `DOC103`).
- `DOC308`: открывающее ограждение (три и более обратных кавычек или тильд в начале строки) без закрывающего до конца значения.
- `DOC309`: строка вне блока кода, начинающаяся с 1–6 символов `#` и пробела.
- `DOC310`: открывающий тег с именем из списка элементов HTML5 или `script`, `style`, `iframe`.

### А3. Граф

- **Рёбра** для `DOC202` и `DOC203`: `parent`, `[[id]]`, `[[id#поле]]` и `[[id#^якорь]]` в видимых строковых значениях (не в `notes`, не в блоках кода). Для достижимости те же рёбра в обе стороны, кроме ссылок из `notes` и ссылок от скрытых документов и к ним.
- `DOC204`: диагностика на каждом документе цикла, позиция на значении `parent`; `parent` на самого себя даёт `DOC204`; `[[id]]` документа на себя в тексте не ошибка и в `docc.lock` не записывается.
- Корень, который скрыт или отсутствует, — `DOC205`.
- В `{{id#поле}}` и `[[id#поле]]` «поле» — ключ верхнего уровня или путь `поле/подраздел`; для вставки допустимо значение-строка или непустой массив строк.

### А4. Работа с файлами

- Каталог `out/` целиком принадлежит `docc`: `build` удаляет всё, что не создал сам, в том числе чужие файлы и папки.
- `DOC501` сравнивает ожидаемое содержимое каждого файла с фактическим после нормализации переводов строк и различает «отсутствует», «устарел», «лишний».

### А5. Дополнения

- **Корень проекта:** `docc.json` ищется в текущем каталоге и выше, берётся ближайший (А1). `roots` — непустой массив, пустой — ошибка настроек.
- **Ошибки использования и настроек** идут в stderr: `docc: error: …` (использование) и `docc.json:строка:колонка: config error: …` (настройки), не в JSON, код выхода `2`. `docc schema` без аргумента — ошибка использования (код `2`); `docc schema config` описывает `docc.json` с `additionalProperties: false`.
- **Ключи `rules`:** код, имя или группа (`syntax`, `schema`, `graph`, `text`, `markdown`, `style`, `trace`, `build`, `meta`, `custom`; другое — ошибка настроек). Приоритет: запись правила точнее записи группы, та точнее пресета. Запись группы ядро не меняет (молча пропускает); изменить уровень ядра прямой записью правила или записать одно правило и кодом, и именем — ошибка настроек (код `2`).
- **Файл документа:** пустой файл, не-UTF-8, корень не объект — `DOC101`. Файл `*.json`, имя которого без расширения не подходит под `id` (например `a.b.json`), — `DOC104`.
- **Каскад ошибок:** документ с `DOC101` остаётся в графе узлом без рёбер (его `id` занят) и не получает `DOC202` и `DOC203`; файл с неверным именем (`DOC104`) в граф не входит. При дубле `id` в граф входит первый документ по пути (по байтам), остальные получают `DOC201` и в граф не входят. Скрытые документы проверяются на `DOC202` и `DOC204` так же, как видимые. Поле с неверным типом (`DOC105`) при построении графа игнорируется, `hidden` неверного типа считается `false`.
- **Схемы:** все файлы `*.json` каталога схем загружаются при старте, любой некорректный — ошибка настроек. Ключевое слово `format` проверяется как утверждение (форматы библиотеки JSON Schema, в том числе `date`, `date-time`, `uri`, `email`; неизвестные игнорируются).
- **Ссылки `[[…]]`:** любое `[[…]]` вне блоков кода считается ссылкой; содержимое должно подходить под `id`, `id#поле` или `id#^якорь`, иначе `DOC202` с подсказкой о формате `id`. Ссылки ищутся в `title`, `body`, свободных полях (любая глубина) и `notes`; в `kind`, `status`, `tags`, `parent` и `docIgnore` не ищутся. Якорь строится как на GitHub (строчные буквы, пробелы в `-`, знаки препинания убираются).
- **Вставки** раскрываются только в `body` и свободных полях; в `title`, `kind`, `status`, `tags`, `parent`, `notes` запись `{{…}}` остаётся обычным текстом. Цель — поле верхнего уровня (в том числе `title`, `body`), значение — строка (пустая допустима) или непустой массив строк. Способа записать литерал `{{` нет, используется блок кода или обратные кавычки.
- **Подавление:** `path` подавляет диагностики с позицией внутри указанного значения; диагностики без позиции в значении подавляются только записью без `path`; несуществующий `path` ничего не подавляет (`DOC901`).
- **Словари:** в записи `words` `*` допустима только в конце слова.
- Постоянные заголовки в Markdown (`Document tree` / `Дерево документов`, `Without parent` / `Без родителя`, служебные разделы полной сборки) выводятся на языке из `lang` (по умолчанию английский); сообщения и подсказки диагностик на английском.

### Б1. Рендер значений

- Страница: первая строка `<!-- GENERATED by docc, DO NOT EDIT -->`, пустая строка, `# title`, затем `body`, затем разделы в порядке из раздела 10. Заголовок раздела — ключ поля: первая буква заглавная, `_` и `-` заменяются пробелами (`kind` → «Kind»).
- **Строка** — абзацы (переводы строк внутри как есть). **Массив строк** — абзацы через пустую строку (для всех полей, кроме `parent`, `tags`). **Число, `true`, `false`** — текстом. **`null`, пустая строка, пустой массив и объект** раздела не создают.
- `kind`, `status` — раздел со значением; `tags` — одна строка тегов в обратных кавычках через запятую; `parent` — одна ссылка; `order` не выводится.
- **Набор разделов** (объект с `"$sections": true`) — заголовки следующего уровня (`###`…`######`) с содержимым под каждым.
- **Объект** — маркированный список `- **ключ:** значение` (ключи в порядке файла); вложенные объекты и массивы — вложенные списки с отступом в два пробела; **массив объектов** — нумерованный список, элемент — вложенный список ключей; переводы строк внутри значения списка продолжаются с отступом.
- **Ссылка на документ:** `[title цели](относительный/путь.md)`, путь относительный от каталога страницы, с `/`; `[[id#поле]]` — `[title цели](путь.md#якорь)`, для `body` без якоря; `[[id#поле/раздел]]` — `[заголовок раздела](путь.md#якорь)`; `[[id#^якорь]]` — `[title цели](путь.md#якорь)`; текст `[[id]]` — `title` цели (с номером, если включён `numbering`). Ссылок на скрытые документы в обычной сборке не бывает (`DOC210`); в `--full` ссылки ведут на их страницы. `[[id]]` на страницу папки только с заголовком (раздел 9, `tree`) — её `title` без ссылки: такой страницы в выводе нет.
- **`_tree.md`:** в режиме папок (`"tree": "folders"`) — вложенный список папок и документов в порядке раздела 9 (`tree`): документ и папка со своей страницей — ссылка, папка без неё — имя папки, папка со страницей только с заголовком — этот заголовок без ссылки; раздела «Без родителя» нет. Иначе — заголовок `# Дерево документов`, вложенный маркированный список по `parent`: сначала корни из `roots` в порядке записи, затем раздел «Без родителя» (остальные документы без `parent`); потомки и документы раздела «Без родителя» сортируются по `order` (документы без него — после), затем по заголовку (без учёта регистра, числа по значению, латиница раньше кириллицы, правила Unicode без привязки к локали системы; при равных заголовках — по `id`); пункт — ссылка `[title](путь.md)`; документ, чей `parent` скрыт, попадает в «Без родителя»; корень из `roots` остаётся корнем, его `parent` игнорируется.
- **Полная сборка (`--full`):** служебные разделы называются «Notes (hidden)» и «Suppressions (docIgnore)» (с `"lang": "ru"` — «Заметки (скрыто)» и «Подавления (docIgnore)»); у скрытого документа сразу после заголовка строка `> Hidden document.` (`> Скрытый документ.`); в `_tree.md` скрытые документы помечены; вставка обрамлена `<!-- include id#поле -->` и `<!-- /include -->`.

### Б2. Вывод команд

- **text:** диагностики, затем итоговая строка `N errors, M warnings in K files` (и при нуле), где `K` — число файлов с диагностиками; баннер «показано N из M» стоит перед ней. Поля JSON-диагностики описаны в разделе 7. **json:** массив объектов (пустой — `[]`), итоговой строки нет.
- `docc rules`: text — таблица «код, имя, группа, уровень»; json — массив объектов с теми же полями.
- `docc explain <код или имя>`: text — заголовок (код, имя, группа, уровень по умолчанию), описание, пример нарушения, пример исправления; json — объект с теми же полями.
- `docc schema document|config|compile|log|diff|comments-apply`: JSON Schema (драфт 2020-12) в stdout; для документа лишние поля разрешены; `compile`, `log`, `diff`, `comments-apply` — формы вывода `docc compile`, `docc log`, `docc diff`, `docc comments apply`.
- `message` и `hint` — короткие английские предложения, `hint` в повелительном наклонении. Для каждого кода текст стабилен, но не входит в публичный контракт: контракт составляют код, имя правила и позиция.

### Б3. Теги в коде

- Грамматика: `docc:`, пробелы, цель (`id`, `id#поле[/раздел]` или `id#^якорь`), далее при необходимости запятая, пробелы и ещё цель. Тег считается, только если перед ним в строке лишь пробелы и знаки комментария (`//`, `#`, `--`, `/*`, `*`, `;`, `<!--`, `%`, `'`), поэтому `docc:` в строке кода тегом не является. В строке учитывается один тег.
- Регион: строка `docc:begin <цели>` открывает, `docc:end` закрывает; строки между ними (обрезанные по краям, NFC) дают отпечаток кода в `docc.lock`. Регион без конца, вложенный регион, `docc:end` без начала и неразрешимая цель — `DOC401`.
- Раздел Covered by страницы перечисляет пути файлов с тегами на документ, без номеров строк.
- Просматриваются текстовые файлы под масками `trace.scan` (от корня проекта). В Git-репозитории список файлов берётся из `git ls-files -co --exclude-standard` (учитывается `.gitignore`), иначе обходится дерево без `.git`, `node_modules` и `vendor`. Файлы с нулевым байтом и больше 1 МБ пропускаются, символические ссылки не открываются, каталоги `src`, `out`, `outFull` самого `docc` не просматриваются.

### Б4. Встроенные словари (начальные, дополняются в `docc.json`)

- `DOC301` (запрещённые): быстро, удобно, интуитивно, «и т.д.», «и т.п.»; fast, easy, intuitive, user-friendly, etc.
- `DOC352` (оговорки): возможно, вероятно, «как правило», «по-видимому», «в некоторых случаях», наверное, «скорее всего», несколько (и формы), некоторые (и формы), различные (и формы); maybe, probably, usually, might, perhaps, several, various.
- `DOC353` («временные»): сейчас, недавно, пока, «в настоящее время», скоро, «в будущем», новый, новая, новое, новые; currently, recently, soon, new, «at the moment».

### Б5. Тесты

Каждый тест — каталог `testdata/<код>/red` или `green` со своим `docs/src/`, при необходимости `docc.json`, и файлом `expected.json` (ожидаемый вывод `--format json`). Сборка — стабильный Rust (edition 2024).
