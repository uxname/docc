# docc — Light PRD

**Компилятор и линтер документации на Go** · имя `docc` · редакция 8 от 15 октября 2026 · **единый финальный релиз** (версий v0.1 и v0.2 нет: каждая возможность либо входит в релиз, либо не делается)

## 1. Суть

`docc` — утилита командной строки на Go. ИИ-агенты пишут документацию как **JSON-файлы**, а `docc` проверяет её **так же, как Biome проверяет код**: структуру по JSON Schema, граф ссылок, содержимое и стиль текста. Затем собирает из неё читаемый Markdown для людей.

Данные — источник истины, Markdown — генерируемый вывод. Инструмент универсальный: заметки, требования, решения, разделы бизнес-плана, проектная документация. Встроенных типов документов нет.

`docc` — публичный проект с открытым кодом (лицензия MIT): готовые бинарники в GitHub Releases, установка `install.sh` и `install.ps1`, самообновление `docc update` (проверка SHA-256 по `checksums.txt`), скилл для агентов `npx skills add uxname/docc`. Первые пользователи — команда автора; продаж, тарифов и поддержки по срокам нет.

## 2. Проблема

- Код пишут и читают агенты, а людям нужна понятная документация уровня видения и бизнес-требований.
- Агенты в обычном Markdown ссылаются на несуществующие документы, плодят сирот, дублируют факты, оставляют заглушки, нарушают структуру.
- Нет «линтера и компилятора» для документации с проверкой в CI.

## 3. Цели и не-цели

**Цели**

1. **Строгая проверка как у кода:** невалидная документация не попадает в основную ветку.
2. **Опыт «как у Biome»:** правила с кодами и группами, уровни `error`/`warn`/`off`, пресет `recommended`, `explain`, вывод в JSON для агентов и CI.
3. **Ядро:** нет битых ссылок, сирот, дублей `id` и циклов.
4. **Дружелюбие к агентам:** диагностика в JSON с подсказкой, команда `docc schema`, скилл `docc`.
5. **Детерминизм и один бинарник** на Linux, macOS и Windows.

**Не-цели**

- Wiki, редактор, генератор сайта (страницы с сервером, сборка из нескольких HTML-файлов, настройка вида), замена трекера задач. Один самодостаточный HTML-файл для чтения и согласования (`docc build --html`: история блоков, комментарии, экспорт) сайтом не считается и допускается (раздел 10).
- Ядро не вызывает LLM и не проверяет смысл: смысл и читаемость Markdown проверяет ревьюер. Согласованность с кодом (дрейф) вне ядра.
- Пользовательские шаблоны оформления (один универсальный рендер; вид единого HTML-файла один, фиксированный, без своих тем и CSS).
- Команды поиска для агента (`context`, `affected`), переименование `mv`, миграция готового Markdown, переходы статусов, граф Mermaid, глоссарий.
- Команда `trace`; `--changed`, `baseline`; правила, зависящие от истории git (изменения после проверки отслеживает `docc.lock`, а не git).
- Автоисправления (`--fix`), переопределения правил по папкам (`overrides`), словари в отдельных файлах.
- Форматирование исходников (`docc fmt`); отдельные проверки повторов в списках (их ловит встроенная схема); отчёты `sarif` и `github` (добавятся, когда станет известно, где работает CI); подключение базового конфига (`extends`).

## 4. Пользователи и сценарии

| Пользователь | Что делает |
| --- | --- |
| **ИИ-агент** | Пишет и правит JSON-документы, запускает `docc validate` и `docc build`, читает диагностику в JSON, исправляет |
| **Человек** | Читает собранный Markdown, ревьюит смысл и читаемость |
| **CI** | `docc check` блокирует merge при ошибках или устаревшем выводе |
| **Аудитор** | Собирает `docc build --full` и читает всё, с чем работают агенты: скрытые документы, заметки, подавления |

**Главный сценарий:** человек ставит задачу словами → агент правит JSON → `docc validate` ловит ошибки → агент чинит по подсказке → `docc build` → человек читает Markdown и проверяет смысл → merge; CI запускает `docc check`.

**Ревью человеком:** ревьюер читает `out/` и проверяет смысл и читаемость. Правку вносит агент по замечанию ревьюера или человек в `src` (длинный текст — массивом абзацев, см. раздел 6), затем `docc validate` и `docc build`; `out/` руками не правится. Конфликт в `out/` решается пересборкой; конфликт в `src` с маркерами слияния даёт `DOC101`, сначала исправляется `src`. Рекомендация вне `init`: пометить `out/**` как сгенерированные (`linguist-generated`).

## 5. Как это работает

**Конвейер:** загрузка JSON → схема → граф ссылок → правила → рендер → проверка актуальности вывода.

```
docs/
├── src/            # ИСТОЧНИКИ (*.json), любая вложенность
├── schemas/        # <kind>.json, схема для каждого вида документов
├── out/            # СГЕНЕРИРОВАНО (не редактировать, коммитится)
├── out-full/       # полная сборка для аудита (docc build --full), не коммитится
├── out.md, out.html            # необязательно: единые файлы (docc build --single, --html), не коммитятся
└── out-full.md, out-full.html  # то же для полной сборки
docc.json           # конфиг, необязателен
docc.lock           # подтверждённые ссылки и их отпечатки, коммитится (раздел 7)
docc.comments.json  # комментарии из HTML-файла после docc comments import, коммитится (раздел 10)
```

`docc init` создаёт `docc.json`, `docs/schemas/page.json` (схема, требующая `title`, с `"additionalProperties": true`) и `docs/src/index.json` (`{ "title": "Index", "kind": "page" }`), в Git-репозитории без своего хука — ещё `.git/hooks/pre-commit` с `docc check` (коммит с ошибками в документации не проходит), затем собирает `docs/out` и `docc.lock`, чтобы первый `docc check` был зелёным. Хуки агента, шаг CI и инструкцию для агентов `init` не создаёт: их даёт скилл `docc` (раздел 11).

Сгенерированные файлы коммитятся, начинаются с комментария `<!-- GENERATED by docc, DO NOT EDIT -->`. Конфликт в `out/` при merge решается командой `docc build`. Точные определения (файлы и пределы, текстовые правила, граф, рендер, форматы вывода, словари, тесты) — в разделе 17.

## 6. Модель документа

Один документ — один файл `*.json` в `src`. **`id` = имя файла без расширения.** Допустимые символы: `a-z`, `0-9`, `-` (начало и конец — не дефис); зарезервированные имена Windows (`con`, `prn`, `aux`, `nul`, `com1`–`com9`, `lpt1`–`lpt9`) запрещены. Имена папок в `src` подчиняются тем же правилам (иначе `DOC104`). Два файла с одним именем в разных папках — ошибка `DOC201`.

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| `title` | да | непустая строка, заголовок |
| `kind` | да | вид документа; по нему подбирается схема `docs/schemas/<kind>.json` (без вида или схемы — `DOC109`) |
| `status` | нет | строка, допустимые значения задаёт схема вида |
| `parent` | нет | `id` родителя (один) |
| `order` | нет | число: порядок среди соседей по `parent` (без него — по заголовку) |
| `body` | нет | основной текст документа: строка или массив абзацев; выводится сразу под заголовком без собственного раздела |
| `tags` | нет | массив строк; допустимые теги можно задать реестром |
| `notes` | нет | скрытые заметки для агентов: массив строк, в Markdown не выводятся |
| `hidden` | нет | `true`: документ проверяется, но в `out/` не выводится и не требует достижимости от корня |
| `docIgnore` | нет | подавления, см. ниже |
| любые другие | нет | свободные поля (например `statement`, `rationale`; других зарезервированных имён нет), если их разрешает схема вида; проза хранится как Markdown-строки или массивы абзацев |

**Ссылки в тексте:** связь между документами — только ссылка в тексте, отдельного списка связей нет. `[[id]]`, `[[id#поле]]`, `[[id#поле/раздел]]` и `[[id#^якорь]]` внутри строковых значений дают ребро графа (проверка цели, достижимость, раздел «Ссылаются») так же, как `parent`. Блоки кода и строки в обратных кавычках игнорируются. Длинный текст записывается массивом абзацев (по абзацу на строку файла): `"body": ["Первый абзац.", "Второй абзац."]`; внутри абзаца переводы строк пишутся как `\n`, рендер переносит их в Markdown как есть. Правила применяются к каждому элементу массива отдельно, путь вида `/body/1`.

**Вложенные разделы.** Объект со служебным ключом `"$sections": true` в значении свободного поля (или в значении другого раздела) — набор разделов: остальные ключи — заголовки, значение — строка, массив строк, таблица, объект-список или снова такой же набор. Поле выводится как `##`, раздел как `###`, следующий уровень `####` и так далее до `######`, порядок как в файле; раздел без текста остаётся заголовком, чтобы у ссылки была цель. Объект без маркера выводится списком, как раньше; маркер вне значения поля или раздела (в массиве, внутри объекта-списка) ничего не значит. На раздел ссылаются `[[id#поле/раздел]]` (текст ссылки — заголовок раздела, а не название документа; ссылка на поле по-прежнему называется заголовком документа), его вставляют `{{id#поле/раздел}}` (вставляется раздел-лист, набор целиком не текст); путь ищется по ключам, поэтому ключ может содержать `/`. Якорь раздела строится как у поля из его заголовка; одинаковые якоря на странице нумеруются `-1`, `-2` в порядке страницы. Текстовые правила, `docIgnore.path` (указатель `/поле/раздел`) и `DOC209` работают с разделами как с полями. В схеме kind маркер описывается как `"properties": {"$sections": {"const": true}}`. В едином HTML заголовки `h2`–`h4` попадают в оглавление страницы.

**Якоря абзацев.** ` ^имя` в конце абзаца, пункта списка или однострочного поля (имя начинается с буквы: `a-z`, `0-9`, `-`) — якорь этого фрагмента: `[[id#^имя]]` ссылается на него, `{{id#^имя}}` вставляет абзац без метки. На странице метка не выводится, вместо неё ставится `<a id>`. Повтор якоря в документе или совпадение с якорем поля либо раздела — `DOC212`, ссылка на несуществующий якорь — `DOC312`.

**Скрытое и вставки.** `notes` — аналог комментариев в коде: агент видит их в исходнике, читатель в Markdown — нет. `[[id]]` и `[[id#поле]]` внутри заметок проверяются на существование (`DOC202`, `DOC312`), но не дают достижимости от корня; правила `text/*`, `markdown/*`, `style/*` к заметкам не применяются (пользовательские — только если `given` указывает на `/notes`). Скрытый документ (`hidden: true`) проверяется как обычный, но страницы в `out/` и записи в `_tree.md` не имеет, не входит в проверку сирот и не даёт путей достижимости; видимый документ не может ссылаться на скрытый через `parent`, `[[id]]` вне заметок или вставку (`DOC210`). **Вставка** `{{id#поле}}` в строке заменяется при сборке текстом поля другого документа (элементы массива — абзацы через пустую строку), чтобы факт хранился один раз; исходник хранит только ссылку. Вставка пропускается в блоках кода и обратных кавычках и допускает вложенные вставки; `{{id}}` без `#поле`, несуществующая цель, цикл, значение не из текста и служебные поля — `DOC211`.

**Подавление:** в JSON нет комментариев, поэтому подавление — поле документа:

```json
"docIgnore": [{ "rule": "DOC301", "reason": "термин из ТЗ заказчика", "path": "/statement" }]
```

`rule` — код (`DOC301`) или имя (`text/forbidden-words`); `reason` обязателен (иначе `DOC108`); `path` (JSON-указатель) необязателен: подавляет диагностики внутри указанного значения вместе с вложенными, без него — во всём документе. Ядро (его нельзя ни подавить, ни отключить; остальные правила настраиваются, в том числе `DOC106`, `DOC107`, `DOC312`): `DOC101`–`DOC105`, `DOC108`, `DOC109`, `DOC201`–`DOC205`, `DOC210`–`DOC213`, `DOC401`, `DOC501`, `DOC503` (попытка даёт `DOC108`). Подавление, которое ничего не подавляет, или подавление выключенного правила даёт `DOC901`.

**Схемы обязательны и строги, как типы в TypeScript:** у каждого документа должен быть `kind` и файл `docs/schemas/<kind>.json` (JSON Schema, драфт 2020-12), иначе `DOC109` (ядро, не отключается). На верхнем уровне схема вида обязана задать `additionalProperties` значением `true` (гибкий вид: лишние поля разрешены) или `false` (строгий вид), иначе ошибка загрузки схем (код выхода `2`). Закрытость `docc` проверяет сам: разрешены служебные поля (`title`, `kind`, `status`, `parent`, `order`, `tags`, `body`, `notes`, `hidden`, `docIgnore`), свойства верхнего уровня и свойства веток `allOf` верхнего уровня и локальных `$ref` (не `if`/`then`); лишнее поле — `DOC106` «unknown field X» с подсказкой похожего имени. Схема видит документ целиком, поэтому может требовать `parent` или ограничивать `status`. `"x-docc-target": ["вид", …]` у свойства (в том числе `parent`) ограничивает виды документов, на которые ведут ссылки в нём (`DOC214`); `"x-docc-covered": true` на верхнем уровне требует, чтобы на документы вида был тег в коде (`DOC403`). Документы вида проверяются по схеме своего вида (`DOC106`); схемы не наследуют друг друга. Схема может ссылаться через `$ref` на другие файлы каталога схем. Метасхемы документа и `docc.json` выдаёт `docc schema`. Встроенная схема документа проверяет типы служебных полей и запрещает повторы в `tags` (ошибка `DOC105`), поэтому отдельных правил для повторов нет.

```json
{
  "title": "Блокировка после пяти неверных паролей",
  "kind": "requirement",
  "status": "accepted",
  "parent": "goal-secure-login",
  "order": 1,
  "statement": "Когда пользователь вводит неверный пароль пять раз подряд, система должна заблокировать вход на 15 минут. ^limit",
  "rationale": "См. [[adr-lockout-policy]]."
}
```

## 7. Правила и диагностика

Правила собраны в группы по образцу Biome. Коды `DOCxxx` — публичный контракт и не меняются; выведенные из оборота коды (`DOC206`, `DOC207`, `DOC208`, `DOC302`, `DOC305`–`DOC307`, `DOC311`, `DOC351`, `DOC354`, `DOC355`, `DOC502`) не переиспользуются (`DOC314` выведен раньше и возвращён с новым смыслом). Сообщения на английском, каждое с подсказкой, как исправить. Уровень по умолчанию — из пресета `recommended`, меняется в `docc.json`.

| Код | Правило | Уровень | Что проверяет |
| --- | --- | --- | --- |
| **Синтаксис и схема** | | | |
| `DOC101` | `syntax/invalid-json` | error | файл не разбирается как JSON |
| `DOC102` | `syntax/duplicate-key` | error | повтор ключа в объекте |
| `DOC103` | `syntax/missing-title` | error | нет `title`, он пуст или из пробелов (схема вида о пустом `title` отдельно не сообщает) |
| `DOC104` | `syntax/invalid-id` | error | имя файла не подходит под `id` |
| `DOC105` | `syntax/document-schema` | error | документ не соответствует встроенной схеме: неверный тип служебного поля (`title`, `kind`, `status`, `parent`, `order`, `tags`, `body`, `notes`, `hidden`) или повтор элемента в `tags` (позиция на повторном элементе) |
| `DOC106` | `schema/violation` | error | нарушение схемы вида из `docs/schemas`, в том числе поле, которого схема не разрешает |
| `DOC107` | `schema/unregistered` | error | тег не из реестра `tags` (если реестр задан) |
| `DOC108` | `syntax/invalid-ignore` | error | `docIgnore` без причины, неверной формы или на правило, которое подавить нельзя |
| `DOC109` | `schema/missing-kind-schema` | error | нет `kind` или нет файла `docs/schemas/<kind>.json` для него; ядро |
| `DOC110` | `syntax/reserved-field-typo` | warn | свободное поле названо почти как служебное (`parnet`, `hiden`: одна правка или две переставленные буквы) и схема вида его не объявляет; в подсказке «Did you mean» |
| **Граф** | | | |
| `DOC201` | `graph/duplicate-id` | error | два документа с одним `id` |
| `DOC202` | `graph/broken-ref` | error | `parent` или `[[id]]` (в том числе в `notes`) ведут в никуда; в подсказке до трёх ближайших существующих `id` |
| `DOC203` | `graph/orphan` | error | документ недостижим от корня |
| `DOC204` | `graph/parent-cycle` | error | цикл по `parent` |
| `DOC205` | `graph/root-not-found` | error | корень из `roots` не существует |
| `DOC209` | `graph/suspect-link` | warn | цель ссылки (`[[id]]`, `[[id#поле]]`, `[[id#^якорь]]` или тег `docc:` в коде) изменилась после подтверждения в `docc.lock`: источник надо перечитать. Несколько ссылок одного документа на части одного документа-цели дают одну диагностику (на первой из них); в подсказке для ссылки на документ целиком совет сослаться на якорь или поле |
| `DOC210` | `graph/link-to-hidden` | error | видимый документ ссылается на скрытый (`parent`, `[[id]]` вне `notes` или `{{id#поле}}`) |
| `DOC211` | `graph/bad-include` | error | вставка `{{id#поле}}` невозможна: нет документа или поля, цикл, значение не текст (строка или непустой массив строк) или служебное поле (`notes`, `docIgnore`, `hidden`) |
| `DOC212` | `graph/duplicate-anchor` | error | якорь `^имя` повторяется в документе или совпадает с якорем поля или раздела его страницы |
| `DOC213` | `graph/broken-file` | error | картинка `![](путь)` с относительным путём ведёт на файл, которого нет в `src`, который лежит вне `src` или не картинка (png, jpg, jpeg, gif, svg, webp) |
| `DOC214` | `graph/wrong-target-kind` | error | ссылка в поле, где схема вида задала `x-docc-target` (или в `parent`), ведёт на документ другого вида |
| **Содержимое** | | | |
| `DOC301` | `text/forbidden-words` | warn | запрещённые слова и фразы из списка |
| `DOC303` | `text/placeholder` | warn | заглушки: `TODO`, `TBD`, `FIXME`, `lorem`, `???`, `N/A`, «—», «см. выше», «работает корректно» и другие (Б4) |
| `DOC304` | `text/empty-field` | warn | пустая строка или строка из пробелов |
| `DOC308` | `markdown/unclosed-fence` | warn | незакрытый блок кода в поле |
| `DOC309` | `markdown/heading-in-field` | warn | строка `#` внутри поля ломает структуру вывода |
| `DOC310` | `markdown/raw-html` | warn | сырой HTML и `script` в тексте, ссылка `[x](javascript:…)` (также `vbscript:`, `data:`) |
| `DOC312` | `markdown/broken-anchor` | error | `[[id#поле]]`, `[[id#поле/подраздел]]` или `[[id#^якорь]]` указывает на несуществующее поле, раздел или якорь или на служебное поле |
| `DOC313` | `text/repeated-word` | warn | повтор слова подряд («в в») |
| **Стиль** | | | |
| `DOC314` | `style/manual-number` | warn | при `"numbering": true` заголовок документа или ключ раздела начинается с набранного вручную номера («2.1 Обзор»); номера ставит `docc` |
| `DOC352` | `style/hedging` | warn | «возможно», «как правило», «вероятно» |
| `DOC353` | `style/timeless-words` | warn | «сейчас», «недавно», «пока», «новый» |
| **Теги в коде, сборка, мета** | | | |
| `DOC401` | `trace/unknown-id` | error | плохой тег в коде: цель `docc:` не находится (документ, поле, раздел или якорь), регион `docc:begin` не закрыт, вложен или `docc:end` без начала |
| `DOC402` | `trace/code-changed` | warn | код региона `docc:begin` … `docc:end` изменился после подтверждения в `docc.lock`: документ надо перечитать |
| `DOC403` | `trace/uncovered` | warn | на видимый документ вида с `"x-docc-covered": true` нет тега `docc:` в коде |
| `DOC501` | `build/stale-output` | error | `out/` расходится с источниками или содержит лишние файлы; для чужого файла (не созданного `docc`) подсказка «убрать самому» |
| `DOC503` | `build/stale-lock` | error | `docc.lock` не совпадает со ссылками в источниках: ссылки не хватает или она лишняя, строка повторяется или испорчена (часто после merge), файла нет; проверяет `docc check` |
| `DOC901` | `meta/unused-ignore` | warn | подавление ничего не подавляет |
| **Пользовательские** | | | |
| `DOC800` | `custom/<имя>` | по правилу | правило из `customRules` в `docc.json` |

**Формат диагностики:** `файл:строка:колонка: уровень КОД сообщение`, следом строка `  hint: …`, позиция в исходном JSON. `--format json` выдаёт массив объектов `{code, rule, level, file, line, column, endLine, endColumn, message, hint}`; `endLine` и `endColumn` — конец диапазона, `endColumn` указывает на колонку сразу за последним знаком (если диапазона нет, совпадают с началом), в text-формате выводится только начало. Колонка считается в рунах; позиция внутри строки с экранированием (`\n`, `\"`, `\uXXXX`) вычисляется по исходному тексту токена. Порядок детерминирован: уровень (error раньше warn), путь (с `/`, по байтам), строка, колонка, код, имя правила.

**Сироты:** документ — сирота, если от `roots` до него нет пути по `parent` и ссылкам `[[…]]` в тексте (рёбра в обе стороны). Сам корень сиротой не считается. Скрытые документы в проверку не входят и путей через них нет; ссылки из `notes` достижимости не дают. Проверка достижимости проверяет форму, а не смысл связи.

**Текстовые правила** эвристические. Слова сравниваются по границам Unicode без учёта регистра после приведения к NFC, текст в обратных кавычках не проверяется (идентификаторы вроде `new` пишутся в обратных кавычках), записи точные («быстро»), префикс помечается звёздочкой («быстр*»), морфология не учитывается: формы слова перечисляются явно. Для правил есть список исключений `allow`. Словари `DOC301`, `DOC352`, `DOC353` встроены (русский и английский) и дополняются в `docc.json` (`words`, `allow`).

**Теги в коде:** `// docc: req-lockout#^limit, scenario-login` ищется построчно в файлах из `trace.scan`, без разбора языков (Б3); регион `// docc:begin <цели>` … `// docc:end` дополнительно хранит отпечаток своего кода в `docc.lock`. Если `trace.scan` не задан, `DOC401`–`DOC403` не работают.

**Уточнения к правилам**

- **Позиции:** строки делятся по `\n`, `\r\n` — один перевод строки, BOM не считается; колонка — число рун исходного текста от начала строки; внутри строки с экранированием позиция вычисляется по исходному токену. Пути в диагностике относительные, с `/`.
- **Диагностики без позиции в JSON:** `DOC201` — на каждом документе с занятым `id`, кроме первого по пути (в подсказке путь первого), позиция 1:1; `DOC203` — 1:1 документа; `DOC205` — позиция поля `roots` в `docc.json`, иначе 1:1; `DOC401`–`DOC403` — файл кода, строка и колонка тега; `DOC501` — файл в `out/`, 1:1 (для лишнего файла его путь); `DOC503` — строка `docc.lock` (испорченная, повторная или лишняя), иначе 1:1.
- `DOC209`, `DOC402`, `DOC503` работают по `docc.lock` (подраздел ниже).
- `DOC800` (пользовательские правила): правила из `customRules` (раздел 9) получают код `DOC800`, их имя (`custom/…`) выводится в поле `rule`; блоки кода и обратные кавычки пропускаются так же, как у остальных текстовых правил; подавляются по имени (`custom/…`) или все сразу кодом `DOC800`.
- **Вставки:** правила текста применяются к исходным строкам, `{{…}}` пропускается; `[[id]]` во вставленном тексте проверяется в документе-источнике и для документа-приёмника не считается ни ссылкой, ни достижимостью; вставка, занимающая весь элемент строки, разворачивается в абзацы по элементам цели, вставка внутри строки — в цель, соединённую пробелами.
- **Текстовые правила** (`DOC301`, `DOC303`, `DOC309`, `DOC310`, `DOC313`, `DOC352`, `DOC353`) пропускают блоки кода и строки в обратных кавычках.
- `DOC310`: только известные имена HTML-тегов; `<id>` тегом не считается.
- `DOC312`: «поле» — ключ верхнего уровня документа или путь `поле/подраздел/…` через вложенные разделы (раздел 6, «Вложенные разделы»); `body` даёт ссылку на страницу без якоря, служебные поля якорем быть не могут; `^имя` — якорь абзаца; если самого документа нет, выдаётся только `DOC202`.
- `DOC313`: одинаковые слова подряд через пробел без учёта регистра; исключения в `allow` («и и», «не не»).
- **Исправлений нет:** `--fix` не делается, агент правит источник сам по подсказке.

### Отслеживание изменений (`docc.lock`)

Связь между документами — ссылка в тексте; `docc.lock` помнит, в каком виде была цель, когда связь подтвердили, и сообщает, если цель с тех пор изменилась. Файл лежит рядом с `docc.json` и коммитится.

- **Формат:** одна строка на связь `<источник> <цель> <отпечаток цели> [<отпечаток кода>]`, строки отсортированы. Источник — `id` документа или путь файла кода; цель — как записана в ссылке (`b`, `b#statement`, `b#^limit`); пробелы и `%` в ней пишутся как `%20`, `%25`. Отпечаток — первые 8 шестнадцатеричных знаков SHA-256; отпечаток кода есть только у ссылок из регионов `docc:begin` … `docc:end`. Пример: `req-a adr-b#^limit 1f2e3d4c`.
- **Что входит в связь:** `[[…]]` в тексте и в `notes` всех документов (скрытых тоже) и теги `docc:` в коде; ссылки документа на себя и на несуществующие цели не записываются.
- **Отпечаток цели:** для всего документа — канонический JSON без `notes`, `docIgnore`, `hidden`, `order` и `parent` (перестановка документа в дереве связь не тревожит); для `#поле` и `#поле/раздел` — только это значение; для `#^якорь` — только текст абзаца без метки. Канонический JSON: ключи на всех уровнях по алфавиту (по байтам UTF-8), без пробелов, строки с минимальным экранированием (`\"`, `\\`, управляющие символы как `\u00XX`), числа как в исходном тексте, массивы в исходном порядке. Отпечаток кода — по строкам региона, обрезанным по краям и приведённым к NFC.
- **`docc build`** (если нет ошибок 1xx–2xx) записывает `docc.lock`: новые связи — с текущими отпечатками (новая связь считается подтверждённой), исчезнувшие связи убираются, у остальных сохраняются записанные отпечатки.
- **`docc validate`** сравнивает текущие отпечатки с записанными: изменилась цель — `DOC209` на ссылке (перечитать источник), изменился код региона — `DOC402` на теге (перечитать документ). Если `docc.lock` нет или он пуст, оба правила молчат.
- **`docc ack X…`** подтверждает связи, где `X` — источник, цель или документ цели (`docc ack adr-b` подтверждает и `adr-b#^limit`; `docc ack src/auth.go` — регионы файла); `docc ack --all` — все связи. Подтверждаются только изменившиеся связи (отпечаток отличается от записанного); `ack` печатает каждую подтверждённую связь («confirmed источник -> цель», в json — массив `links`) и итог, так что видно, какие источники подтверждены. Связь без изменений не трогается, повторный `ack` подтверждает 0 связей. Подтверждение — осознанное действие после проверки: `docc` сверяет только отпечатки.
- **`docc check`** дополнительно сверяет `docc.lock` с текущими ссылками и даёт `DOC503`, если файл расходится с тем, что записал бы `docc build` (лечится `docc build`; конфликт в `docc.lock` при merge решается так же).

## 8. Команды CLI

| Команда | Назначение |
| --- | --- |
| `docc init` | Создать `docc.json` (с `"maxWarnings": 0`: устаревшая ссылка `DOC209` и любое предупреждение блокируют `check`, хук и CI), `docs/schemas/page.json`, `docs/src/index.json`, дописать в `.gitignore` единые файлы сборки, в Git-репозитории без своего хука — `.git/hooks/pre-commit` с `docc check`; собрать `docs/out` и `docc.lock` |
| `docc validate` | Группы 1xx–4xx, 8xx и 9xx, в том числе изменения после подтверждения по `docc.lock` (`DOC209`, `DOC402`) |
| `docc build` | Собрать Markdown в `docs/out` и удалить из него лишние файлы; при ошибках групп 1xx и 2xx в источниках ничего не пишет и завершается кодом 1; с `--full` собирает полную версию для аудита в `docs/out-full` (раздел 10), не трогая `out/`; с `--single` и `--html` дополнительно пишет все страницы в один Markdown-файл (`docs/out.md`) и в один HTML-файл-приложение (`docs/out.html`) рядом с каталогом (раздел 10), а если такой файл уже есть и записан docc (Markdown начинается с метки, HTML содержит остров данных), пересобирает его и без флага, чужой файл не трогает и пишет об этом в stderr; записывает `docc.lock` (раздел 7) |
| `docc check` | Только чтение, для CI и хука перед коммитом: `validate` + актуальность `out/` (`DOC501`) и `docc.lock` (`DOC503`); при ошибках групп 1xx–2xx актуальность не проверяется, код выхода `1` |
| `docc ack <id, цель или файл кода>…`, `docc ack --all` | Подтвердить связи в `docc.lock` после проверки (раздел 7) |
| `docc explain <код, имя или группа>` | Описание правила, пример нарушения и исправления (код в любом регистре); группа (`graph`, `style`) — список её правил; неизвестное — код выхода 2 |
| `docc comments import [--internal] <файл\|->…`, `docc comments [--all]`, `docc comments done [--reply ТЕКСТ] <id>…`, `docc comments rm <id>…` | Замечания из HTML-файла: импорт в `docc.comments.json` из скачанного файла или из скопированного текста (`-` — стандартный ввод; без дублей по `id`, сдвинутый блок находится по цитате; `--internal` — замечания команды, в HTML не попадают), список необработанных с цитатой и текущим текстом блока (`--all` — все), отметка «обработан» с ответом, который читатель увидит под замечанием, удаление; `id` можно сократить до однозначного префикса (раздел 10) |
| `docc update` | Заменить бинарник новой версией с GitHub Releases (проверка SHA-256 по `checksums.txt`); `--check` только сообщает, есть ли новее; сборка `dev` не обновляется |
| `docc rules` | Список правил с кодом, группой и действующим уровнем (с учётом `docc.json`), включая пользовательские |
| `docc schema document` и `docc schema config` | Метасхема документа или `docc.json` (JSON Schema) |

Флаги: `--format text|json`, `--config`, `--full`, `--single`, `--html` (только для `build`), `--all` (только для `ack`), `--max-diagnostics N` (только для text, по умолчанию 20, ошибки выводятся раньше предупреждений, в конце баннер «показано N из M»; json без лимита), `--max-warnings N` (то же задаёт `maxWarnings` в `docc.json`). Формат по умолчанию — `text`. Общие флаги относятся ко всем командам проверки. **Коды выхода:** `0` чисто; `1` есть ошибки или число действующих предупреждений (не `off`, не подавленных) больше `--max-warnings`, флаг важнее `maxWarnings` из конфига; `2` ошибка использования или конфигурации, в том числе отсутствующий каталог `src`; пустой `src` даёт `DOC205`. Ошибки `docc.json` выводятся все сразу; при `--format json` вывод при коде `2` — тот же отчёт `{summary, diagnostics}` с диагностиками `code` `config`, `usage` или `error` (`--max-warnings` меньше `-1` — ошибка использования).

`docc build` не запускается внутри `check`; скилл вызывает по порядку `docc validate`, `docc build`, а хук конца хода — `docc build`, затем `docc check`.

## 9. Конфиг `docc.json`

Все поля необязательны, умолчания встроены. Формат — как у `biome.json`:

```json
{
  "src": "docs/src",
  "out": "docs/out",
  "schemas": "docs/schemas",
  "outFull": "docs/out-full",
  "roots": ["index"],
  "tags": ["draft"],
  "recommended": true,
  "numbering": true,
  "lang": "ru",
  "rules": {
    "text/forbidden-words": { "level": "warn", "words": ["быстро", "удобно", "и т.д."], "allow": [] },
    "style/hedging": "off",
    "markdown/raw-html": "off"
  },
  "customRules": [
    { "id": "custom/no-vague-quantity", "level": "warn", "kind": "requirement", "given": "/statement",
      "forbid": "(?i)(^|[^\\p{L}])несколько($|[^\\p{L}])", "message": "Replace «несколько» with a number", "hint": "State an exact value" }
  ],
  "trace": { "scan": ["tests/**", "src/**"] }
}
```

- `roots` — `id` корней, от которых считается достижимость; по умолчанию `["index"]`; корень, которого нет среди документов, — `DOC205`.
- `tags` — реестр допустимых тегов; поле не задано — реестра нет и `DOC107` не работает; пустой массив — ни одного допустимого значения. Реестра видов нет: вид существует, если есть его схема в `docs/schemas`.
- `numbering` — `true`: `docc` нумерует страницы (дети корней — 1, 2…, глубже — 9.1) и разделы `$sections` (9.1.1) в заголовках, дереве, навигации и тексте ссылок; якоря не меняются; по умолчанию `false`.
- `lang` — `"en"` (по умолчанию) или `"ru"`: язык постоянных надписей вывода (Parent, Referenced by, Covered by, дерево документов и т. п.).
- `recommended` — пресет по умолчанию; `false` отключает его целиком.
- Уровень правила: `"error"`, `"warn"`, `"off"` или объект `{ "level": …, параметры }`.
- `trace.scan` — маски от корня проекта: `*` не пересекает `/`, `**` пересекает; `tests/**` — каталог `tests` в корне, `src/**` — каталог `src` в корне, а не `docs/src`.
- `outFull` — каталог полной сборки для аудита (`docc build --full`); по умолчанию `docs/out-full`, в Git не коммитится.
- `maxWarnings` — предел числа предупреждений, после которого код выхода `1` (по умолчанию без предела).
- `changesSince` — ревизия Git (тег, ветка или коммит) версии, которую читатель получил последней: HTML-файл по умолчанию показывает изменения после неё, а истории до неё в файле нет (раздел 10). Неизвестная ревизия, ревизия вне истории `HEAD` или проект вне Git — ошибка при сборке HTML (код `2`, после обычного вывода диагностик); каталог вывода и `docc.lock` при этом собираются, не пишется только HTML-файл.
- `customRules` — пользовательские правила: `id` (с префиксом `custom/`), `level`, `message`, необязательные `hint` и `kind` (только для документов этого вида), `given` — JSON-указатель на строковое поле (`*` означает любой элемент массива или любой ключ объекта, например `/acceptance/*/then`) и ровно одно из `forbid` (регулярное выражение, совпадение которого — нарушение) или `require` (регулярное выражение, которое должно встретиться в поле; если поля нет, нарушение). Синтаксис регулярных выражений — Go (RE2) с Unicode; выражение и текст сравниваются после приведения к NFC; позиция диагностики — совпавший фрагмент (для `require` — всё поле). Границы слов в регулярных выражениях Go надо задавать через `[^\p{L}]`, а не `\b` (он понимает только ASCII). Если `given` не находит поле или значение не строка и не массив строк (массив проверяется поэлементно), правило для документа пропускается (для `require` отсутствие поля — нарушение); `*` на пустом массиве ничего не находит; блоки кода и обратные кавычки пропускаются и для `require`. Ошибкой конфигурации (код выхода `2`) считаются: ошибка в регулярном выражении, `forbid` и `require` сразу, повтор `id`, `id` не вида `custom/` + `a-z0-9-`.
- Параметры правил: `text/forbidden-words`, `style/hedging`, `style/timeless-words` — `words` (дополняет встроенный словарь, Б4) и `allow`; `text/repeated-word` — `allow`; у остальных правил параметров нет, лишний параметр — ошибка настроек. Объект правила без `level` берёт уровень из пресета (для `off` это «выключено»). При `"recommended": false` все правила выключены, кроме ядра, которое остаётся `error`.

## 10. Рендеринг и формат

- **Один универсальный рендер, шаблонов нет:** `title` — заголовок первого уровня, каждое поле — раздел второго уровня (имя поля с заглавной буквы, `_` и `-` заменяются пробелами). Под заголовком одна строка `kind · status · priority · tags` (пустые части пропускаются), затем `body`, затем свободные поля в порядке файла, в конце страницы разделы Parent, Referenced by (кто ссылается через `parent` или `[[…]]`) и Covered by (пути файлов кода с тегом `docc:` на документ, без номеров строк); раздела Links нет; `parent` выводится одной ссылкой; `[[id]]` превращается в относительную ссылку, `[[id#поле]]` — в ссылку на раздел (якорь по заголовку: строчные буквы, пробелы заменяются на `-`, буквы Unicode сохраняются), `[[id#^якорь]]` — в ссылку на `<a id>` абзаца. `body` выводится сразу под заголовком без собственного раздела, элементы массивов — абзацы, разделённые пустой строкой. Скрытые документы (`hidden: true`) страниц и записей в `_tree.md` не имеют. Вставка `{{id#поле}}` заменяется текстом поля (абзацы массива разделяются пустой строкой); относительные ссылки во вставленном тексте считаются от страницы, куда вставлено. Поля `docIgnore`, `notes`, `hidden` и `order` в обычной сборке в Markdown не выводятся.
- **Порядок и номера:** соседи по `parent` идут по `order` (числу), документы без него — после, по заголовку. С `"numbering": true` `docc` сам ставит номера страниц и разделов (раздел 9); номер, набранный вручную в начале `title` или ключа раздела, — `DOC314`.
- **Надписи:** постоянные надписи (Parent, Referenced by, Covered by, дерево документов, служебные разделы) выводятся на языке из `lang` (`en` по умолчанию, `ru`).
- **Картинки и сноски:** `![подпись](путь)` с относительным путём считается от папки документа; файл проверяется (`DOC213`), копируется в `out/` по тому же пути и встраивается в единый HTML как `data:`-адрес. Сноски Markdown (`[^1]`) в HTML выводятся сносками.
- **Полная сборка для аудита** (`docc build --full`) показывает всё, с чем работают агенты: скрытые документы (с пометкой «скрытый документ»), заметки `notes`, подавления `docIgnore` (правило, причина, путь; отдельными разделами с пометкой «служебное»), а вставки `{{id#поле}}` обрамляет комментариями `<!-- include id#поле -->` … `<!-- /include -->` (видны в исходнике Markdown, не в отображении). Страницы пишутся в `docs/out-full` по тем же путям, `_tree.md` включает скрытые документы. Полная сборка отказывается работать при тех же ошибках 1xx–2xx, что и обычная, и удаляет лишние файлы в `out-full`. Каталог `out/` полная сборка не меняет, `docc check` и `DOC501` её не проверяют; в Git её не коммитят.
- Страница документа лежит по пути источника: `docs/src/a/b.json` даёт `docs/out/a/b.md`. Дерево по `parent` выводится в `docs/out/_tree.md`. `docc build` удаляет в `out/` только то, что создал сам: страницы с меткой `GENERATED by docc`, копии картинок, чьё место есть в `src`, и мусор файловых менеджеров (`.DS_Store`, `Thumbs.db`, `desktop.ini`). Если в `out/` лежит что-то ещё, `build` отказывается работать (код 2), ничего не пишет и не удаляет и перечисляет эти файлы; `DOC501` в `check` называет их тоже.
- **Единые файлы** (`docc build --single`, `docc build --html`; флаги независимы и сочетаются с `--full`) пишутся рядом с каталогом вывода: имя каталога плюс `.md` или `.html` (`docs/out.md`, `docs/out.html`; с `--full` — `docs/out-full.md`, `docs/out-full.html`). Однажды созданный файл пересобирает каждый `docc build` и без флага, чтобы не отправить устаревший; файл, который docc не писал (Markdown без метки, HTML без острова данных), остаётся как есть с сообщением в stderr, заменить его можно явным `--single` или `--html`. Это дополнительный вывод для чтения: каталог Markdown собирается всегда как раньше, единые файлы в Git не коммитятся, `docc check` и `DOC501` их не проверяют. Файл пишется, только если изменилось содержимое; при ошибках 1xx–2xx не пишется ничего; путь, попадающий внутрь `src`, `schemas` или на конфиг, — ошибка использования (код 2). Страницы идут в порядке дерева (с учётом `order`): сначала корни и потомки по `parent`, затем документы без родителя. Ссылки между страницами — внутрифайловые якоря: страница `<id>`, поле `<id>--<якорь поля>`. Единый Markdown: комментарий-метка, дерево документов, затем страницы через `---`; для точных якорей перед страницей и перед каждым полем стоит `<a id="…"></a>`; строка про `_tree.md` не выводится. Единый HTML — одностраничное приложение в одном файле (запросов в сеть нет): Preact с htm (встроен, около 13 КБ, без сборки на Node), стили и JSON-остров с данными страниц внутри. Markdown каждого блока превращает в HTML библиотека goldmark (расширения GFM), сырой HTML из текста документов отбрасывается, сохраняется только `<br>` в ячейках таблиц. Приложение показывает одну страницу за раз (адрес `#<id>` или `#<id>--<поле>` открывает страницу и прокручивает к полю, `#<id>/<JSON Pointer>` — к абзацу с подсветкой; неизвестный адрес открывает первую страницу с сообщением «По этой ссылке ничего не найдено»; «Назад» браузера возвращает к месту чтения): слева дерево документов (заголовки страниц одного уровня стоят на одной вертикали, стрелка раскрытия лежит в отдельной полосе слева; свёрнуто, раскрыт только путь к текущей странице; длинные списки показывают окно вокруг текущего элемента и кнопки «ещё») и поиск (находит абзацы: все слова в абзаце или в названии его страницы; число найденного, первые 30, переход к абзацу; клавиши `/` и Ctrl+K), справа заголовки страницы; у страницы хлебные крошки по `parent`, бейджи вида, статуса, приоритета и тегов, однострочные поля собраны в список свойств, дочерние страницы — списком с началом текста (до 300 знаков), связи (Referenced by, Covered by; родитель уже в крошках) — компактными ссылками, внизу соседние страницы по порядку дерева; на узком экране дерево выезжает по кнопке и закрывается кнопкой «Закрыть», Esc или касанием вне его; на сенсорном экране действия абзаца видны всегда и не меньше 44 px. Статусы бейджей при `lang: ru` переводятся (draft — «черновик» и т. п.). Без скриптов показывается сообщение. Светлая и тёмная тема по настройке системы, печать — текущая страница. Вид один, шаблонов и своих стилей нет.
- **Блоки и история.** Блок — элемент документа: строка массива строк или значение другого поля или раздела целиком (таблица и список — один блок); адрес блока — `id` документа и JSON Pointer элемента (`/body/2`). Перед каждым блоком docc ставит маркер, по которому режет страницу; имя маркера выбирается так, чтобы его не было в тексте страницы. История берётся из Git при сборке (`git log --first-parent` по `src` и `git cat-file`; слияние — одно изменение основной линии): у блока — все коммиты, менявшие его текст (дата и разница по словам), последним идёт незакоммиченное состояние рабочей копии. Файл читает заказчик, поэтому в обычной сборке в истории нет скрытого (`notes`, `docIgnore`, `hidden`), авторов и сообщений коммитов; с `changesSince` нет и истории до этой ревизии: состояние на ней — первая версия, подписанная датой ревизии. Полная сборка (`--full`) хранит всё. Строки массива сопоставляются между версиями по равному тексту, затем по похожему (коэффициент Дайса по парам букв не ниже 0,3), поэтому вставка абзаца не сдвигает историю соседей; переименованное поле начинает историю заново. Переключатель «Показать изменения с» по умолчанию стоит на `changesSince` («отправленной версии от …»), без него выключен; выбор запоминается в браузере. В режиме изменений: сводка «Изменено абзацев: N · страниц: M» открывает список страниц с числом изменённых, новых и удалённых абзацев; стрелки ← → идут по изменениям через все страницы со счётчиком «k из N»; у страниц дерева — число изменений; изменённый абзац отмечен полосой слева и кнопкой «Что изменилось» («Было → стало»), новый — пунктирной полосой и меткой «новое»; удалённые абзацы перечислены внизу страницы. Тексты версий показываются для чтения: ссылки `[[id]]` — названиями, без разметки Markdown. «История страницы» перечисляет версии страницы с изменёнными, добавленными и удалёнными абзацами, место подписано началом текста абзаца. Вне Git-репозитория истории нет.
- **Замечания (комментарии).** Замечание пишется к абзацу текстом или голосом: кнопка «Надиктовать» включает распознавание речи браузера (Web Speech API; Chrome и Edge отправляют звук своему сервису), повторное нажатие выключает; без распознавания кнопки нет. Поле «От кого» заполнено прошлым именем и меняется (на созвоне можно записать замечание от другого участника). Своё замечание можно изменить и удалить, удаление отменяется кнопкой «Вернуть». Замечания хранятся в браузере (`localStorage`) с пометкой «не отправлено»; при закрытии страницы с неотправленными замечаниями браузер переспрашивает. Панель «Замечания» отправляет их двумя способами: «Скопировать для отправки» кладёт в буфер текст для мессенджера (список замечаний и в конце строка `docc-comments:<base64 файла>`; импорт берёт последнюю такую строку и терпит перенос base64 на несколько строк), «Скачать файлом» сохраняет `{"docc": "comments", "version": 1, "comments": [{id, doc, path, quote, text, author, created, build}]}`; после этого замечания отмечены отправленными. `docc comments import` принимает и файл, и скопированный текст (`-` — со стандартного ввода) и добавляет замечания в `docc.comments.json` в корне проекта (по строке на замечание, статус `open` или `done`, ответ `reply`, признак `internal`); файл коммитится, так импорт попадает в историю. `--internal` помечает замечания команды: в HTML-файл (кроме `--full`) они не попадают. `docc comments done <id> --reply "…"` сохраняет ответ команды. Блок комментария находится по адресу, а если там другой текст — по цитате (тот же текст в другом месте: «сдвинут»; похожий текст: «изменён»). Импортированные замечания видны в HTML на своих абзацах и в панели «Замечания» со статусом («команда разбирает» или «учтено») и ответом команды; замечание браузера, которое уже есть в файле, из браузера убирается. Сам docc текст по комментариям не меняет: агент читает `docc comments`, обсуждает правку с человеком и отмечает комментарий `done` или удаляет `rm`.
- **Экспорт.** Меню «Экспорт» скачивает текущую страницу в Markdown, все страницы одним Markdown-файлом или все страницы отдельными файлами в zip-архиве — тот же Markdown, что в каталоге вывода и в `out.md`.
- **Детерминизм:** стабильная сортировка, без меток времени, переводы строк только `\n`, UTF-8 без BOM (так же для единых файлов).

## 11. Windows, Git и скилл для агентов

- **Windows:** CRLF и BOM во входных файлах и в `out/` нормализуются при чтении и при сравнении (`DOC501`), поэтому `.gitattributes` не нужен. Файлы пишутся с `\n`. Регистронезависимые файловые системы: `id` и имена папок только строчные, зарезервированные имена Windows запрещены; пути сортируются как строки с `/`.
- **Git:** две ветки, создавшие файл с одним именем, дают конфликт «both added» (верный сигнал о занятом `id`). Конфликт в `out/` или `docc.lock` решается `docc build`. После merge CI запускает `docc check` на целевой ветке (лучше в очереди merge); расхождение `out/` и `_tree.md` без конфликта лечится `docc build`.
- **Скилл `docc` (лежит в репозитории `docc` как `skills/docc/SKILL.md`; ставится командой `npx skills add uxname/docc`):** формат документа (отсылает к `docc schema document`; схемы видов агент пишет в `docs/schemas` сам, скилл набор видов не навязывает), цикл «правка → `docc validate` → `docc build`», чтение JSON-диагностики и `docc explain <код>`, заметки `notes` (читать при правке; ссылки в них проверяются), скрытые документы, вставки `{{id#поле}}`, `docc build --full` для аудита, примеры трёх хуков Claude Code (запрет правок `docs/out`; после правки файла — только ошибки синтаксиса и схемы этого файла; в конце хода — `docc build` и `docc check --max-warnings 0`, чтобы пачка новых документов со ссылками друг на друга не блокировалась на полпути), пути хуков через `$CLAUDE_PROJECT_DIR`, пример шага CI (`docc check`), правила для агента: не подавлять ошибку через `docIgnore` вместо исправления, ссылаться только на существующие `id`, при `DOC209` и `DOC402` перечитать источник и подтвердить связь `docc ack` (читать все источники из списка, который печатает `ack`), коммитить только по просьбе пользователя. О формальной связи с `index` скилл только предупреждает: проверка достижимости проверяет форму, смысл связи остаётся ревьюеру. Как вернуть диагностику модели после правки, скилл описывает отдельно (для Claude Code это зависит от кода выхода хука). Хуки агента и CI `init` не создаёт (только Git-хук `pre-commit`).
- **Распространение:** готовые бинарники для Linux, macOS и Windows в GitHub Releases (`install.sh`, `install.ps1`, `docc update`); `go install`; скилл — `npx skills add uxname/docc`.

## 12. Архитектура на Go

Пакеты (`internal/`): `cmd/docc`, `config`, `loader` (свой рекурсивный разбор JSON около 250 строк: дерево узлов с указателем, смещениями и позициями, ключи с дублями; из него строится значение для схемы), `schema` (JSON Schema), `mdscan` (свой сканер блоков кода, заголовков, HTML-тегов и ссылок), `graph`, `rules` (реестр правил: код, имя, группа, уровень по умолчанию, признак ядра, текст для `explain`), `render`, `trace`, `report` (text, json); `docc.lock` ведёт пакет `engine`.

**Зависимости:** стандартная библиотека; `santhosh-tekuri/jsonschema` для схем; CLI на `flag` с подкомандами (`cobra`, если станет тесно). YAML-библиотек нет. Схема вида видит документ целиком, служебные поля для неё всегда разрешены (форму `docIgnore` проверяет `DOC108`, форму остальных служебных — `DOC105`); `$ref` в схемах разрешён только на другие файлы внутри каталога схем (удалённые и выходящие за каталог запрещены), некорректный файл схемы — ошибка настроек (код выхода `2`); ошибки схемы сопоставляются с позициями по таблице «указатель → позиция» (`required` — позиция объекта, `additionalProperties` — позиция ключа, `oneOf` и `anyOf` схлопываются в одну диагностику). `docc explain`, `docc rules` и скилл строятся из реестра правил, поэтому не расходятся с кодом.

**Принципы:** golden-тесты (вход → диагностики), чистое ядро, ввод-вывод на границах, стабильные коды.

## 13. Нефункциональные требования

- Один статический бинарник без сети.
- `docc check` на 1000 документов меньше секунды (цель). Замер: 1000 файлов по 5–20 КБ русского текста, холодный и тёплый кэш, Linux и Windows с антивирусом; загрузка, схемы, правила и сравнение `out/` измеряются отдельно.
- Детерминизм вывода и порядка диагностик на трёх ОС.
- Понятные сообщения с подсказкой, как исправить.

## 14. План реализации (один релиз, этапы без версий)

0. **Спайк:** позиции токенов JSON (строка и колонка в рунах, включая внутренность строк с экранированием), обнаружение дублей ключей, замер скорости на 1000 синтетических документов. Выход из этапа: позиции верны на тестовых строках с `\n`, `\uXXXX`, суррогатными парами, BOM и CRLF; дубли ключей находятся; замер выполнен, иначе цели скорости пересматриваются.
1. **Загрузка, граф, отчёт:** `DOC101`–`DOC105`, `DOC201`–`DOC205`, `DOC210`, `DOC211`; загрузка `docc.json` (пути, `roots`, реестры, `rules` с уровнями и параметрами, `recommended`); `validate` в text и json.
2. **Схемы и реестры:** `DOC106`–`DOC108`, `docc schema`.
3. **Содержимое, Markdown, стиль:** `DOC212`–`DOC214`, `DOC301`–`DOC314`, `DOC352`, `DOC353`.
4. **`build` (включая вставки, картинки, `order`, `numbering`, `lang` и `--full`), `check`, `docc.lock` и `ack`:** `DOC209`, `DOC501`, `DOC503`, `DOC901`.
5. **Механики:** `explain`, `rules` (с действующими уровнями), пользовательские правила (`DOC800`), `--max-diagnostics`, `--max-warnings`, теги в коде (`DOC401`–`DOC403`).
6. **Скилл `docc`** и сборка бинарников.

**Готово, когда:**

- на каждый код из таблицы раздела 7 есть golden-тест «красный» и «зелёный» (для `DOC800` — на правилах `forbid` и `require`);
- встроенная схема документа ловит повтор в `tags` (тест);
- схема вида без `additionalProperties` на верхнем уровне даёт код выхода `2`, лишнее поле в строгом виде — `DOC106` (тест);
- есть тесты на эталонные отпечатки `docc.lock`, на `docc ack`, на `endLine` и `endColumn`;
- `docc build --full` показывает скрытые документы, заметки, подавления и границы вставок и не меняет `out/` (тест);
- `docc build --single --html` пишет `docs/out.md` и `docs/out.html`: ссылки только внутрифайловые, порядок страниц как в дереве, скрытое только с `--full`, `<script>` из текста не попадает в HTML, `<br>` в ячейке таблицы сохраняется, повторная сборка не меняет файл, при ошибках 1xx–2xx файлов нет (тесты и golden);
- некорректный файл схемы и `$ref` вне каталога схем дают код выхода `2` (тест);
- позиции верны для строк с экранированием и многострочных значений (тест);
- `docc check` на 1000 синтетических документов укладывается в секунду на Linux и Windows (цель; если замер этапа 0 покажет иное, критерий пересматривается вместе с владельцем);
- два прогона `docc build` на трёх ОС дают побайтово одинаковый `out/`;
- `docc init` в пустом каталоге создаёт проект, проходящий `docc check`, а в Git-репозитории — хук `pre-commit`;
- сам проект `docc` описан своими документами и проходит `docc check` в CI;
- по скиллу агент исправляет не менее 9 из 10 синтетических ошибок за две итерации.

## 15. Метрики успеха

- Доля синтетических ошибок, исправленных агентом за две итерации, не ниже 9 из 10 (критерий готовности выше).
- Ошибки структуры и ссылок, которые ревьюер нашёл руками, а `docc` пропустил: 0.
- Доля подавлений через `docIgnore` среди всех исправлений агента (контроль).
- Время `docc check` на реальной документации.

## 16. Принятые решения и умолчания

**Решено владельцем (HTML-приложение, 2026-10-15):** HTML-сборка становится одностраничным приложением на Preact + htm без сборки на Node; история блоков из Git, блок — элемент JSON; нужны история блока, подсветка изменённого с выбранной версии и история страницы; комментарии к блокам текстом и голосом (Web Speech API, звук уходит в Google — допустимо), выгрузка в JSON, импорт в репозиторий со статусом «обработан / не обработан» и командой списка необработанных для агента; экспорт: страница, всё одним .md, всё в .zip; на звонке экран показывает один человек.

**Решено владельцем (единые файлы, 2026-10-04):** рядом с каталогом Markdown, не вместо него; флаги `--single` (один .md) и `--html` (один .html); не в Git и не под `check`; скрытое только с `--full`; единый .md для чтения человеком; HTML с деревом, поиском, тёмной темой и печатью; конвертер goldmark; имена из `out` и `outFull` без новых настроек.

**Решено владельцем (типы, связи, номера):** схемы обязательны и строги (как TypeScript): у каждого документа есть вид со схемой, схема явно говорит, разрешены ли лишние поля; связь — только ссылка в тексте (поля `links` нет); `docc.lock` вместо `reviewed`: изменения после подтверждения отслеживает файл рядом с `docc.json`, а не поле документа; номера ставит `docc` (`numbering`), вручную их не пишут; виды документов не навязываются скиллом: проект заводит свои виды сам; правила `nursery`, `--fix`, `overrides`, реестр `kinds`, `wordsFile` и `allowFile` убраны.

**Решено владельцем:** внутренний инструмент; единый финальный релиз; формат источников JSON; YAML нет; `id` = имя файла; корни `roots` (по умолчанию `["index"]`); сирота = недостижим от корня, смысл связи на ревьюере; схемы JSON Schema, правила текста с подавлениями, теги `docc:` в коде; гигиена связей, содержимого и стиль; пресет, `explain`, `rules`, вывод text и json; `init` создаёт `docc.json`, схему `page`, `index.json` и хук `pre-commit`; формат агенту даёт скилл и `docc schema`; `build` отдельной командой; без `--changed`; без шаблонов; без `context`, `mv`, миграции, переходов статусов, Mermaid, глоссария; Linux, macOS, Windows; имя `docc`; без `fmt`; повторы в `tags` ловит встроенная схема; отчётов `sarif` и `github` пока нет (решение откладывается до выбора CI). Решено также: поле `body` и текст массивом абзацев; скрытые заметки `notes`; скрытые документы `hidden`; вставка текста `{{id#поле}}`; общие части схем через `$ref`; полная сборка для аудита `docc build --full`. Сравнение с аналогами (Spectral, ESLint и Biome, Vale и markdownlint, Sphinx-Needs, StrictDoc, Doorstop, Backstage) готового решения не нашло: пишем своё на Go. Заимствовано: подозрительные ссылки (Doorstop), свои правила в конфиге (Spectral), конечная позиция ошибки (ESLint).

**Решения редакции 6 (после аудита продукта, 15 октября 2026):** `ack` подтверждает только изменившиеся связи и печатает их; `docc init` пишет `maxWarnings: 0`; `DOC209` объединяется по документу-цели; новое правило `DOC110` (предупреждение); `DOC202` называет ближайшие `id`; `build` не удаляет файлы, созданные не им, а отказывается работать; ошибки запуска и конфигурации в json — отчёт `{summary, diagnostics}`; `docc` — публичный проект с открытым кодом. Не делались: защита `out/` через файл-маркер и `--dry-run`, вынос скилла в несколько файлов, переупорядочивание диагностик по позиции (ошибки по-прежнему выводятся раньше предупреждений).

**Решения редакции 8 (после UX-аудита HTML-файла, 15 октября 2026):** HTML-файл отправляется заказчику, поэтому в обычной сборке в нём нет `notes`, `docIgnore`, `hidden`, авторов и сообщений коммитов, внутренних замечаний и истории до `changesSince`; точка отсчёта изменений задаётся сборкой (`changesSince`), а не выбором коммита; изменения обходятся по одному со счётчиком и сводкой по страницам, удалённое показано; замечания уходят текстом для мессенджера или файлом, импорт принимает оба вида, у замечания есть ответ команды и признак «внутреннее»; поиск находит абзацы, у абзаца есть адрес; `build` пересобирает существующие единые файлы. Не делались: стартовый экран-обзор согласования, режим чистого чтения, перевод видов документов, статическая разметка для просмотра без скриптов, отдельная модель адаптива для планшета.

**Умолчания, выбранные при написании PRD (можно заменить):** `roots` по умолчанию `["index"]` и `id` = имя файла (решены владельцем в первом раунде вопросов); достижимость считается по рёбрам в обе стороны; `_tree.md` сохраняется; `baseline` не делается (готовых документов нет); уровни по умолчанию для правил, которых владелец не называл: `DOC107`, `DOC214` и `DOC312` — error, `DOC209`, `DOC314`, `DOC352`, `DOC353`, `DOC402`, `DOC403` — warn; `DOC401`–`DOC403` не работают без `trace.scan`; повтор в `tags` — ошибка ядра `DOC105` (агент убирает повтор сам); новая связь при `docc build` считается подтверждённой; поле `tags`, `docIgnore.path`, `--max-diagnostics` 20 для text, встроенные словари на русском и английском, драфт JSON Schema 2020-12, `docs/schemas/<kind>.json`, содержимое скилла, `go install`, параметры правил по умолчанию, запрет подавлять и отключать ядро, сборка `out/` при `init` и удаление лишних файлов `build` выбраны при написании PRD; так же выбраны синтаксис вставки `{{id#поле}}`, поле `hidden`, `DOC210` и `DOC211` в ядре, правило «к заметкам текстовые правила не применяются», каталог `docs/out-full` для полной сборки, формат `docc.lock` и отпечатков, синтаксис `customRules`, ключ `maxWarnings`, цели «меньше секунды на 1000 документов» и «9 из 10 ошибок за две итерации» и поставка скилла в архивах релиза рядом с бинарниками.

**Проверяется при реализации (вопросов владельцу нет):** позиции токенов и скорость (этап 0), словари стиля на реальных документах.

## 17. Приложение: точные определения

Приложение уточняет разделы 5–11 там, где реализации иначе пришлось бы придумывать поведение.

### А1. Проект и файлы

- **Корень проекта** — каталог ближайшего `docc.json`: он ищется в текущем каталоге, затем в родительских, до первого найденного (как у git и biome, поэтому хук и агент могут запускать docc из подкаталога); если файла нет нигде, корнем остаётся текущий каталог и действуют умолчания; `--config <путь>` задаёт файл конфигурации без поиска, корнем проекта становится его каталог. `docc init` вверх не ищет и создаёт файлы в текущем каталоге. Все пути в конфиге и в диагностиках отсчитываются от корня проекта, в диагностиках записываются с `/`.
- В `src` читаются только файлы `*.json` (расширение строчными). Обход `src` рекурсивный; остальные файлы, а также каталоги и файлы с именем на точку и символические ссылки пропускаются. Имя каталога, не подходящее под `id`, даёт `DOC104` (один на каталог, позиция 1:1 на его путь), файлы внутри читаются как обычно.
- **Файл документа:** UTF-8 (BOM допускается и отбрасывается), строгий JSON по RFC 8259 (без комментариев и висящих запятых), корень — объект; иначе `DOC101`. Пределы: размер файла не более 5 МБ, вложенность не более 64; превышение — `DOC101`.
- **`docc.json`:** тот же строгий JSON, допускается ключ `$schema`; неизвестные ключи и неверные типы — ошибка настроек (код выхода `2`, сообщение в stderr вида `docc.json:3:5: config error: …`). Диагностики и вывод `rules`, `explain`, `schema` идут в stdout, ошибки использования и настроек — в stderr. Цвета (ANSI) не используются.
- В `rules` ключ — код (`DOC301`) или имя (`text/forbidden-words`); пользовательское правило переопределяется по имени `custom/…`; ключ группы (`text`, `style` и т. п.) задаёт уровень сразу всей группе.
- **`kind`** — строка из `a-z`, `0-9`, `-`, иначе `DOC105`. Если файла `docs/schemas/<kind>.json` нет, документ получает `DOC109` и проверяется только встроенной схемой. Ключевое слово `format` в схемах проверяется как утверждение.
- `docc init` не перезаписывает существующие `docc.json`, `docs/schemas/page.json`, `docs/src/index.json` и `.git/hooks/pre-commit` (пропускает с сообщением; чужой хук не трогает), затем всегда выполняет сборку. `docc --version` и `docc --help` работают как обычно.

### А2. Что проверяют текстовые правила

- **Какие строки:** значения `title`, `body` и всех свободных полей на любой глубине (элементы массивов, значения вложенных объектов). Не проверяются `kind`, `status`, `parent`, `order`, `tags`, служебные поля (`docIgnore`, `notes`, `hidden`) и ключи объектов. Строка делится на фрагменты вне блоков кода и обратных кавычек и приводится к NFC.
- **Слово** — максимальная последовательность букв Unicode, цифр, `_`, дефиса и апострофа внутри слова; сравнение без учёта регистра по границам слов, `быстр*` — префикс.
- `DOC303`: слова и фразы `TODO`, `TBD`, `FIXME`, `lorem`, `N/A`, «см. выше», «работает корректно», «по необходимости», «see above», «works correctly» и последовательность `???` без учёта регистра как отдельные слова; значение, состоящее только из тире («—», «–», «-»).
- `DOC304`: значение пусто или состоит из пробелов (для `title` действует `DOC103`).
- `DOC308`: открывающее ограждение (три и более обратных кавычек или тильд в начале строки) без закрывающего до конца значения.
- `DOC309`: строка вне блока кода, начинающаяся с 1–6 символов `#` и пробела.
- `DOC310`: открывающий тег с именем из списка элементов HTML5 или `script`, `style`, `iframe`.

### А3. Граф

- **Рёбра** для `DOC202` и `DOC203`: `parent`, `[[id]]`, `[[id#поле]]` и `[[id#^якорь]]` в видимых строковых значениях (не в `notes`, не в блоках кода). Для достижимости те же рёбра в обе стороны, кроме ссылок из `notes` и ссылок от скрытых документов и к ним.
- `DOC204`: диагностика на каждом документе цикла, позиция на значении `parent`; `parent` на самого себя даёт `DOC204`; `[[id]]` документа на себя в тексте не ошибка и в `docc.lock` не записывается.
- Корень, который скрыт или отсутствует, — `DOC205`.
- В `{{id#поле}}` и `[[id#поле]]` «поле» — ключ верхнего уровня или путь `поле/подраздел`; для вставки допустимо значение-строка или непустой массив строк.

### А4. Работа с файлами

- Каталог `out/` целиком принадлежит `docc`: `build` удаляет всё, что не создал сам, в том числе чужие файлы и папки.
- `DOC501` сравнивает ожидаемое содержимое каждого файла с фактическим после нормализации переводов строк и различает «отсутствует», «устарел», «лишний».

### А5. Дополнения

- **Корень проекта:** `docc.json` ищется в текущем каталоге и выше, берётся ближайший (А1). `roots` — непустой массив, пустой — ошибка настроек.
- **Ошибки использования и настроек** идут в stderr: `docc: error: …` (использование) и `docc.json:строка:колонка: config error: …` (настройки), не в JSON, код выхода `2`. `docc schema` без аргумента — ошибка использования (код `2`); `docc schema config` описывает `docc.json` с `additionalProperties: false`.
- **Ключи `rules`:** код, имя или группа (`syntax`, `schema`, `graph`, `text`, `markdown`, `style`, `trace`, `build`, `meta`, `custom`; другое — ошибка настроек). Приоритет: запись правила точнее записи группы, та точнее пресета. Запись группы ядро не меняет (молча пропускает); изменить уровень ядра прямой записью правила или записать одно правило и кодом, и именем — ошибка настроек (код `2`).
- **Файл документа:** пустой файл, не-UTF-8, корень не объект — `DOC101`. Файл `*.json`, имя которого без расширения не подходит под `id` (например `a.b.json`), — `DOC104`.
- **Каскад ошибок:** документ с `DOC101` остаётся в графе узлом без рёбер (его `id` занят) и не получает `DOC202` и `DOC203`; файл с неверным именем (`DOC104`) в граф не входит. При дубле `id` в граф входит первый документ по пути (по байтам), остальные получают `DOC201` и в граф не входят. Скрытые документы проверяются на `DOC202` и `DOC204` так же, как видимые. Поле с неверным типом (`DOC105`) при построении графа игнорируется, `hidden` неверного типа считается `false`.
- **Схемы:** все файлы `*.json` каталога схем загружаются при старте, любой некорректный — ошибка настроек. Ключевое слово `format` проверяется как утверждение (форматы библиотеки JSON Schema, в том числе `date`, `date-time`, `uri`, `email`; неизвестные игнорируются).
- **Ссылки `[[…]]`:** любое `[[…]]` вне блоков кода считается ссылкой; содержимое должно подходить под `id`, `id#поле` или `id#^якорь`, иначе `DOC202` с подсказкой о формате `id`. Ссылки ищутся в `title`, `body`, свободных полях (любая глубина) и `notes`; в `kind`, `status`, `tags`, `parent` и `docIgnore` не ищутся. Якорь строится как на GitHub (строчные буквы, пробелы в `-`, знаки препинания убираются).
- **Вставки** раскрываются только в `body` и свободных полях; в `title`, `kind`, `status`, `tags`, `parent`, `notes` запись `{{…}}` остаётся обычным текстом. Цель — поле верхнего уровня (в том числе `title`, `body`), значение — строка (пустая допустима) или непустой массив строк. Способа записать литерал `{{` нет, используется блок кода или обратные кавычки.
- **Подавление:** `path` подавляет диагностики с позицией внутри указанного значения; диагностики без позиции в значении подавляются только записью без `path`; несуществующий `path` ничего не подавляет (`DOC901`).
- **Словари:** в записи `words` `*` допустима только в конце слова.
- Постоянные заголовки в Markdown (`Document tree` / `Дерево документов`, `Without parent` / `Без родителя`, служебные разделы полной сборки) выводятся на языке из `lang` (по умолчанию английский); сообщения и подсказки диагностик на английском.

### Б1. Рендер значений

- Страница: первая строка `<!-- GENERATED by docc, DO NOT EDIT -->`, пустая строка, `# title`, затем `body`, затем разделы в порядке из раздела 10. Заголовок раздела — ключ поля: первая буква заглавная, `_` и `-` заменяются пробелами (`kind` → «Kind»).
- **Строка** — абзацы (переводы строк внутри как есть). **Массив строк** — абзацы через пустую строку (для всех полей, кроме `parent`, `tags`). **Число, `true`, `false`** — текстом. **`null`, пустая строка, пустой массив и объект** раздела не создают.
- `kind`, `status` — раздел со значением; `tags` — одна строка тегов в обратных кавычках через запятую; `parent` — одна ссылка; `order` не выводится.
- **Набор разделов** (объект с `"$sections": true`) — заголовки следующего уровня (`###`…`######`) с содержимым под каждым.
- **Объект** — маркированный список `- **ключ:** значение` (ключи в порядке файла); вложенные объекты и массивы — вложенные списки с отступом в два пробела; **массив объектов** — нумерованный список, элемент — вложенный список ключей; переводы строк внутри значения списка продолжаются с отступом.
- **Ссылка на документ:** `[title цели](относительный/путь.md)`, путь относительный от каталога страницы, с `/`; `[[id#поле]]` — `[title цели](путь.md#якорь)`, для `body` без якоря; `[[id#поле/раздел]]` — `[заголовок раздела](путь.md#якорь)`; `[[id#^якорь]]` — `[title цели](путь.md#якорь)`; текст `[[id]]` — `title` цели (с номером, если включён `numbering`). Ссылок на скрытые документы в обычной сборке не бывает (`DOC210`); в `--full` ссылки ведут на их страницы.
- **`_tree.md`:** заголовок `# Дерево документов`, вложенный маркированный список по `parent`: сначала корни из `roots` в порядке записи, затем раздел «Без родителя» (остальные документы без `parent`); потомки и документы раздела «Без родителя» сортируются по `order` (документы без него — после), затем по заголовку (без учёта регистра, числа по значению, латиница раньше кириллицы, правила Unicode без привязки к локали системы; при равных заголовках — по `id`); пункт — ссылка `[title](путь.md)`; документ, чей `parent` скрыт, попадает в «Без родителя»; корень из `roots` остаётся корнем, его `parent` игнорируется.
- **Полная сборка (`--full`):** служебные разделы называются «Notes (hidden)» и «Suppressions (docIgnore)» (с `"lang": "ru"` — «Заметки (скрыто)» и «Подавления (docIgnore)»); у скрытого документа сразу после заголовка строка `> Hidden document.` (`> Скрытый документ.`); в `_tree.md` скрытые документы помечены; вставка обрамлена `<!-- include id#поле -->` и `<!-- /include -->`.

### Б2. Вывод команд

- **text:** диагностики, затем итоговая строка `N errors, M warnings in K files` (и при нуле), где `K` — число файлов с диагностиками; баннер «показано N из M» стоит перед ней. Поля JSON-диагностики описаны в разделе 7. **json:** массив объектов (пустой — `[]`), итоговой строки нет.
- `docc rules`: text — таблица «код, имя, группа, уровень»; json — массив объектов с теми же полями.
- `docc explain <код или имя>`: text — заголовок (код, имя, группа, уровень по умолчанию), описание, пример нарушения, пример исправления; json — объект с теми же полями.
- `docc schema document|config`: JSON Schema (драфт 2020-12) в stdout; для документа лишние поля разрешены.
- `message` и `hint` — короткие английские предложения, `hint` в повелительном наклонении. Для каждого кода текст стабилен, но не входит в публичный контракт: контракт составляют код, имя правила и позиция.

### Б3. Теги в коде

- Грамматика: `docc:`, пробелы, цель (`id`, `id#поле[/раздел]` или `id#^якорь`), далее при необходимости запятая, пробелы и ещё цель. Тег считается, только если перед ним в строке лишь пробелы и знаки комментария (`//`, `#`, `--`, `/*`, `*`, `;`, `<!--`, `%`, `'`), поэтому `docc:` в строке кода тегом не является. В строке учитывается один тег.
- Регион: строка `docc:begin <цели>` открывает, `docc:end` закрывает; строки между ними (обрезанные по краям, NFC) дают отпечаток кода в `docc.lock`. Регион без конца, вложенный регион, `docc:end` без начала и неразрешимая цель — `DOC401`.
- Раздел Covered by страницы перечисляет пути файлов с тегами на документ, без номеров строк.
- Просматриваются текстовые файлы под масками `trace.scan` (от корня проекта). В Git-репозитории список файлов берётся из `git ls-files -co --exclude-standard` (учитывается `.gitignore`), иначе обходится дерево без `.git`, `node_modules` и `vendor`. Файлы с нулевым байтом и больше 1 МБ пропускаются, символические ссылки не открываются, каталоги `src`, `out`, `outFull` самого `docc` не просматриваются.

### Б4. Встроенные словари (начальные, дополняются в `docc.json`)

- `DOC301` (запрещённые): быстро, удобно, интуитивно, «и т.д.», «и т.п.»; fast, easy, intuitive, user-friendly, etc.
- `DOC352` (оговорки): возможно, вероятно, «как правило», «по-видимому», «в некоторых случаях», наверное, «скорее всего», несколько (и формы), некоторые (и формы), различные (и формы); maybe, probably, usually, might, perhaps, several, various.
- `DOC353` («временные»): сейчас, недавно, пока, «в настоящее время», скоро, «в будущем», новый, новая, новое, новые; currently, recently, soon, new, «at the moment».

### Б5. Тесты

Каждый тест — каталог `testdata/<код>/red` или `green` со своим `docs/src/`, при необходимости `docc.json`, и файлом `expected.json` (ожидаемый вывод `--format json`). Минимальная версия Go — актуальная стабильная на момент начала реализации.
