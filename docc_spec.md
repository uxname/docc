# docc — Light PRD

**Компилятор и линтер документации на Go** · имя `docc` · редакция 4 от 4 октября 2026 · **единый финальный релиз** (версий v0.1 и v0.2 нет: каждая возможность либо входит в релиз, либо не делается)

## 1. Суть

`docc` — утилита командной строки на Go. ИИ-агенты пишут документацию как **JSON-файлы**, а `docc` проверяет её **так же, как Biome проверяет код**: структуру по JSON Schema, граф ссылок, содержимое и стиль текста. Затем собирает из неё читаемый Markdown для людей.

Данные — источник истины, Markdown — генерируемый вывод. Инструмент универсальный: заметки, требования, решения, разделы бизнес-плана, проектная документация. Встроенных типов документов нет.

Первые пользователи — внутренние (ваша команда); рыночные цели не ставятся.

## 2. Проблема

- Код пишут и читают агенты, а людям нужна понятная документация уровня видения и бизнес-требований.
- Агенты в обычном Markdown ссылаются на несуществующие документы, плодят сирот, дублируют факты, оставляют заглушки, нарушают структуру.
- Нет «линтера и компилятора» для документации с проверкой в CI.

## 3. Цели и не-цели

**Цели**

1. **Строгая проверка как у кода:** невалидная документация не попадает в основную ветку.
2. **Опыт «как у Biome»:** правила с кодами и группами, уровни `error`/`warn`/`off`, пресет `recommended`, переопределения по папкам, автоисправления, `explain`, вывод в JSON для агентов и CI.
3. **Ядро:** нет битых ссылок, сирот, дублей `id` и циклов.
4. **Дружелюбие к агентам:** диагностика в JSON с подсказкой, команда `docc schema`, скилл `docc`.
5. **Детерминизм и один бинарник** на Linux, macOS и Windows.

**Не-цели**

- Wiki, редактор, генератор сайта, замена трекера задач.
- Ядро не вызывает LLM и не проверяет смысл: смысл и читаемость Markdown проверяет ревьюер. Согласованность с кодом (дрейф) вне ядра.
- Пользовательские шаблоны оформления (один универсальный рендер).
- Команды поиска для агента (`context`, `affected`), переименование `mv`, миграция готового Markdown, переходы статусов, граф Mermaid, глоссарий.
- Команда `trace` и обязательные теги у документов; `--changed`, `baseline`; правила, зависящие от истории git.
- Форматирование исходников (`docc fmt`); отдельные проверки повторов в списках (их ловит встроенная схема); отчёты `sarif` и `github` (добавятся, когда станет известно, где работает CI); подключение базового конфига (`extends`).

## 4. Пользователи и сценарии

| Пользователь | Что делает |
| --- | --- |
| **ИИ-агент** | Пишет и правит JSON-документы, запускает `docc validate` и `docc build`, читает диагностику в JSON, исправляет |
| **Человек** | Читает собранный Markdown, ревьюит смысл и читаемость |
| **CI** | `docc check` блокирует merge при ошибках или устаревшем выводе |
| **Аудитор** | Собирает `docc build --full` и читает всё, с чем работают агенты: скрытые документы, заметки, подавления |

**Главный сценарий:** человек ставит задачу словами → агент правит JSON → `docc validate` ловит ошибки → агент чинит по подсказке → `docc build` → человек читает Markdown и проверяет смысл → merge; CI запускает `docc check`.

**Ревью человеком:** ревьюер читает `out/` и проверяет смысл и читаемость. Правку вносит агент по замечанию ревьюера или человек в `src` (длинный текст — массивом абзацев, см. раздел 6), затем `docc validate` и `docc build`; `out/` руками не правится. Конфликт в `out/` решается пересборкой; конфликт в `src` с маркерами слияния даёт `DOC101`, сначала исправляется `src`. Рекомендация вне `init`: пометить `out/**` как сгенерированные (`linguist-generated`).

## 5. Как это работает

**Конвейер:** загрузка JSON → схема → граф ссылок → правила → рендер → проверка актуальности вывода.

```
docs/
├── src/            # ИСТОЧНИКИ (*.json), любая вложенность
├── schemas/        # необязательно: <kind>.json, схема для вида документов
├── out/            # СГЕНЕРИРОВАНО (не редактировать, коммитится)
└── out-full/       # полная сборка для аудита (docc build --full), не коммитится
docc.json           # конфиг, необязателен
```

`docc init` создаёт только `docc.json` и `docs/src/index.json` (`{ "title": "Index" }`) и собирает `docs/out`, чтобы первый `docc check` был зелёным. Хуки, шаг CI и инструкцию для агентов `init` не создаёт: их даёт скилл `docc` (раздел 11).

Сгенерированные файлы коммитятся, начинаются с комментария `<!-- GENERATED by docc, DO NOT EDIT -->`. Конфликт в `out/` при merge решается командой `docc build`. Точные определения (файлы и пределы, текстовые правила, граф, рендер, форматы вывода, словари, тесты) — в разделе 17.

## 6. Модель документа

Один документ — один файл `*.json` в `src`. **`id` = имя файла без расширения.** Допустимые символы: `a-z`, `0-9`, `-` (начало и конец — не дефис); зарезервированные имена Windows (`con`, `prn`, `aux`, `nul`, `com1`–`com9`, `lpt1`–`lpt9`) запрещены. Имена папок в `src` подчиняются тем же правилам (иначе `DOC104`). Два файла с одним именем в разных папках — ошибка `DOC201`.

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| `title` | да | непустая строка, заголовок |
| `kind` | нет | вид документа; по нему подбирается схема; допустимые виды можно задать реестром в `docc.json` |
| `status` | нет | строка, допустимые значения задаёт схема вида |
| `parent` | нет | `id` родителя (один) |
| `links` | нет | массив `id` связанных документов |
| `body` | нет | основной текст документа: строка или массив абзацев; выводится сразу под заголовком без собственного раздела |
| `tags` | нет | массив строк; допустимые теги можно задать реестром |
| `notes` | нет | скрытые заметки для агентов: массив строк, в Markdown не выводятся |
| `hidden` | нет | `true`: документ проверяется, но в `out/` не выводится и не требует достижимости от корня |
| `docIgnore` | нет | подавления, см. ниже |
| `reviewed` | нет | подтверждённые ссылки: `id` цели → отпечаток цели на момент проверки (см. `DOC209`) |
| `$schema` | нет | путь к схеме относительно файла для автодополнения в редакторе, игнорируется |
| любые другие | нет | свободные поля (например `statement`, `rationale`; других зарезервированных имён нет); проза хранится как Markdown-строки или массивы абзацев |

**Ссылки в тексте:** внутри строковых значений `[[id]]` и `[[id#поле]]` проверяются так же, как `parent` и `links`. Блоки кода и строки в обратных кавычках игнорируются. Длинный текст записывается массивом абзацев (по абзацу на строку файла): `"body": ["Первый абзац.", "Второй абзац."]`; внутри абзаца переводы строк пишутся как `\n`, рендер переносит их в Markdown как есть. Правила применяются к каждому элементу массива отдельно, путь вида `/body/1`.

**Скрытое и вставки.** `notes` — аналог комментариев в коде: агент видит их в исходнике, читатель в Markdown — нет. `[[id]]` и `[[id#поле]]` внутри заметок проверяются на существование (`DOC202`, `DOC312`), но не дают достижимости от корня и не требуют записи в `links`; правила `text/*`, `markdown/*`, `style/*` к заметкам не применяются (пользовательские — только если `given` указывает на `/notes`). Скрытый документ (`hidden: true`) проверяется как обычный, но страницы в `out/` и записи в `_tree.md` не имеет, не входит в проверку сирот и не даёт путей достижимости; видимый документ не может ссылаться на скрытый через `parent`, `links`, `[[id]]` вне заметок или вставку (`DOC210`). **Вставка** `{{id#поле}}` в строке заменяется при сборке текстом поля другого документа (элементы массива — абзацы через пустую строку), чтобы факт хранился один раз; исходник хранит только ссылку. Вставка пропускается в блоках кода и обратных кавычках и допускает вложенные вставки; `{{id}}` без `#поле`, несуществующая цель, цикл, значение не из текста и служебные поля — `DOC211`.

**Подавление:** в JSON нет комментариев, поэтому подавление — поле документа:

```json
"docIgnore": [{ "rule": "DOC301", "reason": "термин из ТЗ заказчика", "path": "/statement" }]
```

`rule` — код (`DOC301`) или имя (`text/forbidden-words`); `reason` обязателен (иначе `DOC108`); `path` (JSON-указатель) необязателен: подавляет диагностики внутри указанного значения вместе с вложенными, без него — во всём документе. Ядро (его нельзя ни подавить, ни отключить; остальные правила настраиваются, в том числе `DOC106`, `DOC107`, `DOC312`): `DOC101`–`DOC105`, `DOC108`, `DOC201`–`DOC205`, `DOC210`, `DOC211`, `DOC401`, `DOC501` (попытка даёт `DOC108`). Подавление, которое ничего не подавляет, или подавление выключенного правила даёт `DOC901`.

**Схемы:** если есть `docs/schemas/<kind>.json` (JSON Schema, драфт 2020-12), документы этого вида проверяются по ней (`DOC106`). Схема может ссылаться через `$ref` на другие файлы каталога схем. Метасхемы документа и `docc.json` выдаёт `docc schema`. Встроенная схема документа проверяет типы полей и запрещает повторы в `links` и `tags`; `reviewed` — объект «`id` → 8 шестнадцатеричных знаков» (ошибка `DOC105`), поэтому отдельных правил для повторов нет.

```json
{
  "$schema": "../schemas/requirement.json",
  "title": "Блокировка после пяти неверных паролей",
  "kind": "requirement",
  "status": "accepted",
  "parent": "goal-secure-login",
  "links": ["adr-lockout-policy"],
  "statement": "Когда пользователь вводит неверный пароль пять раз подряд, система должна заблокировать вход на 15 минут. См. [[adr-lockout-policy]]."
}
```

**Формат диагностики:** `файл:строка:колонка: уровень КОД сообщение`, следом строка `  hint: …`, позиция в исходном JSON. `--format json` выдаёт массив объектов `{code, rule, level, file, line, column, endLine, endColumn, message, hint, fixable}`, где `fixable` — `none`, `safe` или `unsafe`; `endLine` и `endColumn` — конец диапазона, `endColumn` указывает на колонку сразу за последним знаком (если диапазона нет, совпадают с началом), в text-формате выводится только начало. Колонка считается в рунах; позиция внутри строки с экранированием (`\n`, `\"`, `\uXXXX`) вычисляется по исходному тексту токена. Порядок детерминирован: уровень (error раньше warn), путь (с `/`, по байтам), строка, колонка, код, имя правила.

**Сироты:** документ — сирота, если от `roots` до него нет пути по `parent`, `links` и `[[id]]` (рёбра в обе стороны). Сам корень сиротой не считается. Скрытые документы в проверку не входят и путей через них нет; ссылки из `notes` достижимости не дают. Проверка достижимости проверяет форму, а не смысл связи.

**Текстовые правила** эвристические. Слова сравниваются по границам Unicode без учёта регистра, записи точные («быстро»), префикс помечается звёздочкой («быстр*»), морфология не учитывается: формы слова перечисляются явно. Для правил есть список исключений `allow`. Словари `DOC352`, `DOC353`, `DOC354` встроены (русский и английский) и дополняются в `docc.json`. Списки слов можно хранить и в файлах (`wordsFile`, `allowFile`, раздел 9).

**Теги в коде:** токен `@covers <id>[, <id>]` ищется построчно в файлах из `trace.scan`, без разбора языков. Если `trace.scan` не задан, `DOC401` не работает.

**Уточнения к правилам**

- **Позиции:** строки делятся по `\n`, `\r\n` — один перевод строки, BOM не считается; колонка — число рун исходного текста от начала строки; внутри строки с экранированием позиция вычисляется по исходному токену. Пути в диагностике относительные, с `/`.
- **Группа `nursery`:** правила со значением `off` в таблице (`DOC209`, `DOC302`, `DOC305`–`DOC307`, `DOC311`, `DOC351`–`DOC355`) выключены в пресете `recommended`, как у Biome, и включаются явно в `docc.json`: уровнем конкретного правила или сразу всей группы (`"nursery": "warn"` в `rules`).
- **Диагностики без позиции в JSON:** `DOC201` — на каждом документе с занятым `id`, кроме первого по пути (в подсказке путь первого), позиция 1:1; `DOC203` — 1:1 документа; `DOC205` — позиция поля `roots` в `docc.json`, иначе 1:1; `DOC401` — файл кода, строка и колонка тега; `DOC501` — файл в `out/`, 1:1 (для лишнего файла его путь).
- `DOC355`: аббревиатура — слово из заглавных букв длиной от двух символов; расшифровкой считается текст в скобках сразу после неё в том же документе, либо сама аббревиатура в скобках после расшифровки («искусственный интеллект (ИИ)»), либо запись в `allow`.
- `DOC209` (подозрительные ссылки): отпечаток цели — первые 8 шестнадцатеричных знаков SHA-256 от канонического JSON целевого документа без полей `reviewed`, `docIgnore`, `$schema` и `notes` (ключи на всех уровнях по алфавиту, сравнение по байтам UTF-8; без пробелов; строки с минимальным экранированием: `\"`, `\\` и управляющие символы как `\u00XX`; числа как в исходном тексте; массивы в исходном порядке; UTF-8; без перевода строки в конце). Когда правило включено, для каждого `id` из `links` и из ссылок в `notes` без записи в `reviewed` выдаётся «ссылка не подтверждена», при несовпадении отпечатка — «цель изменилась после проверки»; в подсказке указан ожидаемый отпечаток. Агент подтверждает ссылку, записывая его в `reviewed` после проверки цели. Если цель не существует или не разбирается, для этой ссылки `DOC209` молчит (её ловят `DOC202` и `DOC101`); `id` в `reviewed`, которого нет ни в `links`, ни в ссылках `notes`, игнорируется; вставки `{{id#поле}}` в `DOC209` не участвуют (текст в `out/` обновляется при сборке). `docc` проверяет только совпадение отпечатка, подтверждение остаётся осознанным действием.
- `DOC800` (пользовательские правила): правила из `customRules` (раздел 9) получают код `DOC800`, их имя (`custom/…`) выводится в поле `rule`; блоки кода и обратные кавычки пропускаются так же, как у остальных текстовых правил; подавляются по имени (`custom/…`) или все сразу кодом `DOC800`.
- **Вставки:** правила текста применяются к исходным строкам, `{{…}}` пропускается; `[[id]]` во вставленном тексте проверяется в документе-источнике и для документа-приёмника не считается ни ссылкой, ни достижимостью; вставка, занимающая весь элемент строки, разворачивается в абзацы по элементам цели, вставка внутри строки — в цель, соединённую пробелами.
- **Текстовые правила** (`DOC301`, `DOC303`, `DOC309`, `DOC310`, `DOC313`, `DOC351`–`DOC355`) пропускают блоки кода и строки в обратных кавычках.
- `DOC306`: сходство нормализованных заголовков (строчные буквы, один пробел) по триграммам, порог по умолчанию 0,85, исключения в `allow`.
- `DOC307`: строки вида ДД.ММ.ГГГГ и Д/М/ГГ; названия месяцев не проверяются; поля с `format: date` проверяет схема (`DOC106`).
- `DOC310`: только известные имена HTML-тегов; `<id>` тегом не считается.
- `DOC312`: «поле» — ключ верхнего уровня документа; `body` даёт ссылку на страницу без якоря, служебные поля якорем быть не могут; если самого документа нет, выдаётся только `DOC202`.
- `DOC313`: одинаковые слова подряд через пробел без учёта регистра; исключения в `allow` («и и», «не не»).
- **Исправления:** `--fix` применяет безопасное исправление `DOC208`, с `--unsafe` ещё небезопасные: `DOC206` убирает свой `id` из `links` или `parent`, `DOC313` удаляет повтор слова. Исправления накладываются патчем по смещениям исходного текста, остальное форматирование файла не меняется; все записи пишут `\n`. `DOC208` исправляется, только если `id` существует и он не свой; если поля `links` нет или оно пусто, оно создаётся, отступ берётся от соседних полей.

## 8. Команды CLI

| Команда | Назначение |
| --- | --- |
| `docc init` | Создать `docc.json` и `docs/src/index.json` и собрать `docs/out` |
| `docc validate` | Группы 1xx–4xx, 8xx и 9xx; с `--fix` применяет безопасные исправления правил 2xx и 3xx |
| `docc build` | Собрать Markdown в `docs/out` и удалить из него лишние файлы; при ошибках групп 1xx и 2xx в источниках ничего не пишет и завершается кодом 1; с `--full` собирает полную версию для аудита в `docs/out-full` (раздел 10), не трогая `out/` |
| `docc check` | Только чтение, для CI: `validate` + актуальность `out/` (`DOC501`); при ошибках групп 1xx–2xx актуальность `out/` не проверяется, код выхода `1` |
| `docc explain <код>` | Описание правила, пример нарушения и исправления; неизвестный код — код выхода 2 |
| `docc rules` | Список правил с кодом, группой, действующим уровнем (с учётом `docc.json`; с `--file <путь>` ещё и `overrides` для этого файла) и наличием fix, включая пользовательские |
| `docc schema document` и `docc schema config` | Метасхема документа или `docc.json` (JSON Schema) |

Флаги: `--format text|json`, `--config`, `--file <путь>` (только для `rules`), `--full` (только для `build`), `--fix`, `--unsafe` (с `--fix`: небезопасные исправления), `--max-diagnostics N` (только для text, по умолчанию 20, ошибки выводятся раньше предупреждений, в конце баннер «показано N из M»; json без лимита), `--max-warnings N` (то же задаёт `maxWarnings` в `docc.json`). Формат по умолчанию — `text`. `--fix` и `--unsafe` относятся только к `validate` (с `check` код выхода `2`); остальные флаги — ко всем командам проверки. **Коды выхода:** `0` чисто; `1` есть ошибки или число действующих предупреждений (не `off`, не подавленных) больше `--max-warnings`, флаг важнее `maxWarnings` из конфига; `2` ошибка использования или конфигурации, в том числе отсутствующий каталог `src`; пустой `src` даёт `DOC205`.

`docc build` не запускается внутри `check`; хук агента и скилл вызывают по порядку `docc validate`, `docc build`.

## 9. Конфиг `docc.json`

Все поля необязательны, умолчания встроены. Формат — как у `biome.json`:

```json
{
  "src": "docs/src",
  "out": "docs/out",
  "schemas": "docs/schemas",
  "outFull": "docs/out-full",
  "roots": ["index"],
  "kinds": ["note", "requirement", "decision"],
  "tags": ["draft"],
  "recommended": true,
  "rules": {
    "text/forbidden-words": { "level": "warn", "words": ["быстро", "удобно", "и т.д."], "allow": [] },
    "style/sentence-length": { "level": "warn", "max": 30 },
    "text/max-length": { "level": "warn", "max": 2000 },
    "markdown/raw-html": "off"
  },
  "overrides": [
    { "include": ["drafts/**"], "rules": { "text/placeholder": "off" } }
  ],
  "customRules": [
    { "id": "custom/no-vague-quantity", "level": "warn", "kind": "requirement", "given": "/statement",
      "forbid": "(?i)(^|[^\\p{L}])несколько($|[^\\p{L}])", "message": "Replace «несколько» with a number", "hint": "State an exact value" }
  ],
  "trace": { "scan": ["tests/**", "src/**"] }
}
```

- `roots` — `id` корней, от которых считается достижимость; по умолчанию `["index"]`; корень, которого нет среди документов, — `DOC205`.
- `kinds`, `tags` — реестры допустимых значений; поле не задано — реестра нет и `DOC107` не работает; пустой массив — ни одного допустимого значения.
- `recommended` — пресет по умолчанию; `false` отключает его целиком.
- Уровень правила: `"error"`, `"warn"`, `"off"` или объект `{ "level": …, параметры }`.
- `overrides` — другие уровни и параметры для файлов по маске (`*` не пересекает `/`, `**` пересекает; пути относительно `src` с `/`); применяются по порядку записи, более поздняя запись заменяет настройку правила целиком.
- `trace.scan` — маски от корня проекта (`tests/**` — каталог `tests` в корне, `src/**` — каталог `src` в корне, а не `docs/src`).
- `outFull` — каталог полной сборки для аудита (`docc build --full`); по умолчанию `docs/out-full`, в Git не коммитится.
- `maxWarnings` — предел числа предупреждений, после которого код выхода `1` (по умолчанию без предела).
- Правила из группы `nursery` (таблица раздела 7, уровень `off`) включаются здесь явно.
- `customRules` — пользовательские правила: `id` (с префиксом `custom/`), `level`, `message`, необязательные `hint` и `kind` (только для документов этого вида), `given` — JSON-указатель на строковое поле (`*` означает любой элемент массива или любой ключ объекта, например `/acceptance/*/then`) и ровно одно из `forbid` (регулярное выражение, совпадение которого — нарушение) или `require` (регулярное выражение, которое должно встретиться в поле; если поля нет, нарушение). Синтаксис регулярных выражений — Go (RE2) с Unicode; позиция диагностики — совпавший фрагмент (для `require` — всё поле). Границы слов в регулярных выражениях Go надо задавать через `[^\p{L}]`, а не `\b` (он понимает только ASCII). Если `given` не находит поле или значение не строка и не массив строк (массив проверяется поэлементно), правило для документа пропускается (для `require` отсутствие поля — нарушение); `*` на пустом массиве ничего не находит; блоки кода и обратные кавычки пропускаются и для `require`. Ошибкой конфигурации (код выхода `2`) считаются: ошибка в регулярном выражении, `forbid` и `require` сразу, повтор `id`, `id` не вида `custom/` + `a-z0-9-`, `kind` не из реестра `kinds` (если он задан).
- `wordsFile`, `allowFile` (для любого правила, у которого есть `words` или `allow`) — пути к текстовым файлам с одной записью на строку (формат записей тот же, что в `words`; пустые строки и строки с `#` игнорируются; UTF-8); списки из файла объединяются со списком в конфиге; пути отсчитываются от корня проекта; отсутствующий файл — код выхода `2`.
- Параметры по умолчанию: `text/forbidden-words` — `words` дополняет встроенный список (Б4), `allow`; `text/max-length` — `max` 2000 рун; `text/title-similar` — `threshold` 0,85; `style/sentence-length` — `max` 30; `style/hedging`, `style/timeless-words`, `style/ambiguous-pronoun` — `words` дополняет встроенные словари. Объект правила без `level` берёт уровень из пресета (для `off` это «выключено»). При `"recommended": false` все правила выключены, кроме ядра, которое остаётся `error`.

## 10. Рендеринг и формат

- **Один универсальный рендер, шаблонов нет:** `title` — заголовок первого уровня, каждое поле — раздел второго уровня (имя поля с заглавной буквы, `_` и `-` заменяются пробелами; порядок разделов: `kind`, `status`, `parent`, `links`, `tags`, затем остальные поля в порядке файла); `parent` выводится одной ссылкой, `links` — списком ссылок; `[[id]]` превращается в относительную ссылку, `[[id#поле]]` — в ссылку на раздел (якорь по заголовку: строчные буквы, пробелы заменяются на `-`, буквы Unicode сохраняются). `body` выводится сразу под заголовком без собственного раздела, элементы массивов — абзацы, разделённые пустой строкой. Скрытые документы (`hidden: true`) страниц и записей в `_tree.md` не имеют. Вставка `{{id#поле}}` заменяется текстом поля (абзацы массива разделяются пустой строкой); относительные ссылки во вставленном тексте считаются от страницы, куда вставлено. Поля `$schema`, `docIgnore`, `reviewed`, `notes` и `hidden` в обычной сборке в Markdown не выводятся.
- **Полная сборка для аудита** (`docc build --full`) показывает всё, с чем работают агенты: скрытые документы (с пометкой «скрытый документ»), заметки `notes`, подавления `docIgnore` (правило, причина, путь) и подтверждения `reviewed` (отдельными разделами с пометкой «служебное»), а вставки `{{id#поле}}` обрамляет комментариями `<!-- include id#поле -->` … `<!-- /include -->` (видны в исходнике Markdown, не в отображении). Страницы пишутся в `docs/out-full` по тем же путям, `_tree.md` включает скрытые документы. Полная сборка отказывается работать при тех же ошибках 1xx–2xx, что и обычная, и удаляет лишние файлы в `out-full`. Каталог `out/` полная сборка не меняет, `docc check` и `DOC501` её не проверяют; в Git её не коммитят.
- Страница документа лежит по пути источника: `docs/src/a/b.json` даёт `docs/out/a/b.md`. Дерево по `parent` выводится в `docs/out/_tree.md`. `docc build` удаляет в `out/` файлы, которым не соответствует источник; `DOC501` ловит и такие лишние файлы.
- **Детерминизм:** стабильная сортировка, без меток времени, переводы строк только `\n`, UTF-8 без BOM.

## 11. Windows, Git и скилл для агентов

- **Windows:** CRLF и BOM во входных файлах и в `out/` нормализуются при чтении и при сравнении (`DOC501`), поэтому `.gitattributes` не нужен. Файлы пишутся с `\n`. Регистронезависимые файловые системы: `id` и имена папок только строчные, зарезервированные имена Windows запрещены; пути сортируются как строки с `/`.
- **Git:** две ветки, создавшие файл с одним именем, дают конфликт «both added» (верный сигнал о занятом `id`). Конфликт в `out/` решается `docc build`. После merge CI запускает `docc check` на целевой ветке (лучше в очереди merge); расхождение `out/` и `_tree.md` без конфликта лечится `docc build`.
- **Скилл `docc` (лежит в репозитории `docc` как `skills/docc/SKILL.md` и копируется в проект вручную):** формат документа (отсылает к `docc schema document`; схемы видов агент пишет в `docs/schemas` сам), цикл «правка → `docc validate` → `docc build`», чтение JSON-диагностики и `docc explain <код>`, заметки `notes` (читать при правке; ссылки в них проверяются), скрытые документы, вставки `{{id#поле}}`, `docc build --full` для аудита, пример хука Claude Code (после правки `docs/src` — `docc validate`, `docc build`; запрет правок `docs/out`), пример шага CI (`docc check`), правила для агента: не подавлять ошибку через `docIgnore` вместо исправления, ссылаться только на существующие `id`. О формальной связи с `index` скилл только предупреждает: проверка достижимости проверяет форму, смысл связи остаётся ревьюеру. Как вернуть диагностику модели после правки, скилл описывает отдельно (для Claude Code это зависит от кода выхода хука). Хуки и CI `init` не создаёт.
- **Распространение:** готовые бинарники для Linux, macOS и Windows; `go install`; скилл `skills/docc/SKILL.md` входит в архивы релиза рядом с бинарниками.

## 12. Архитектура на Go

Пакеты (`internal/`): `cmd/docc`, `config`, `loader` (свой рекурсивный разбор JSON около 250 строк: дерево узлов с указателем, смещениями и позициями, ключи с дублями; из него строится значение для схемы), `schema` (JSON Schema), `mdscan` (свой сканер блоков кода, заголовков, HTML-тегов и ссылок), `graph`, `rules` (реестр правил: код, имя, группа, уровень по умолчанию, вид fix, текст для `explain`), `fixes`, `render`, `trace`, `report` (text, json).

**Зависимости:** стандартная библиотека; `santhosh-tekuri/jsonschema` для схем; CLI на `flag` с подкомандами (`cobra`, если станет тесно). YAML-библиотек нет. Перед проверкой схемой вида из документа убираются `$schema`, `docIgnore`, `reviewed`, `notes` и `hidden` (форму `docIgnore` проверяет `DOC108`, форму остальных — `DOC105`); `$ref` в схемах разрешён только на другие файлы внутри каталога схем (удалённые и выходящие за каталог запрещены), некорректный файл схемы — ошибка настроек (код выхода `2`); ошибки схемы сопоставляются с позициями по таблице «указатель → позиция» (`required` — позиция объекта, `additionalProperties` — позиция ключа, `oneOf` и `anyOf` схлопываются в одну диагностику). `docc explain`, `docc rules` и скилл строятся из реестра правил, поэтому не расходятся с кодом.

**Принципы:** golden-тесты (вход → диагностики), чистое ядро, ввод-вывод на границах, стабильные коды, идемпотентный `--fix`.

## 13. Нефункциональные требования

- Один статический бинарник без сети.
- `docc check` на 1000 документов меньше секунды (цель). Замер: 1000 файлов по 5–20 КБ русского текста, холодный и тёплый кэш, Linux и Windows с антивирусом; загрузка, схемы, правила и сравнение `out/` измеряются отдельно.
- Детерминизм вывода и порядка диагностик на трёх ОС.
- Понятные сообщения с подсказкой, как исправить.

## 14. План реализации (один релиз, этапы без версий)

0. **Спайк:** позиции токенов JSON (строка и колонка в рунах, включая внутренность строк с экранированием), обнаружение дублей ключей, замер скорости на 1000 синтетических документов. Выход из этапа: позиции верны на тестовых строках с `\n`, `\uXXXX`, суррогатными парами, BOM и CRLF; дубли ключей находятся; замер выполнен, иначе цели скорости пересматриваются.
1. **Загрузка, граф, отчёт:** `DOC101`–`DOC105`, `DOC201`–`DOC205`, `DOC210`, `DOC211`; загрузка `docc.json` (пути, `roots`, реестры, `rules` с уровнями и параметрами, `recommended`); `validate` в text и json.
2. **Схемы и реестры:** `DOC106`–`DOC108`, `docc schema`.
3. **Содержимое, Markdown, стиль:** `DOC206`, `DOC208`, `DOC209`, `DOC301`–`DOC313`, `DOC351`–`DOC355`.
4. **`build` (включая вставки и `--full`), `check`, `--fix`:** `DOC501`, `DOC901`.
5. **Механики:** `overrides`, `explain`, `rules` (с действующими уровнями и `--file`), пользовательские правила (`DOC800`), файлы словарей, `--max-diagnostics`, `--max-warnings`, `trace` (`DOC401`).
6. **Скилл `docc`** и сборка бинарников.

**Готово, когда:**

- на каждый из 40 кодов есть golden-тест «красный» и «зелёный» (для `DOC800` — на правилах `forbid` и `require`);
- встроенная схема документа ловит повтор в `links` и `tags` (тест);
- есть тесты на эталонные отпечатки `DOC209`, на `docc rules --file`, на `endLine` и `endColumn`, на `wordsFile`;
- `docc build --full` показывает скрытые документы, заметки, подавления и границы вставок и не меняет `out/` (тест);
- некорректный файл схемы и `$ref` вне каталога схем дают код выхода `2` (тест);
- позиции верны для строк с экранированием и многострочных значений (тест);
- `docc check` на 1000 синтетических документов укладывается в секунду на Linux и Windows (цель; если замер этапа 0 покажет иное, критерий пересматривается вместе с владельцем);
- два прогона `docc build` на трёх ОС дают побайтово одинаковый `out/`;
- `docc validate --fix` идемпотентен и не меняет форматирование файла вне исправленных мест;
- `docc init` в пустом каталоге создаёт проект, проходящий `docc check`;
- сам проект `docc` описан своими документами и проходит `docc check` в CI;
- по скиллу агент исправляет не менее 9 из 10 синтетических ошибок за две итерации.

## 15. Метрики успеха

- Доля синтетических ошибок, исправленных агентом за две итерации, не ниже 9 из 10 (критерий готовности выше).
- Ошибки структуры и ссылок, которые ревьюер нашёл руками, а `docc` пропустил: 0.
- Доля подавлений через `docIgnore` среди всех исправлений агента (контроль).
- Время `docc check` на реальной документации.

## 16. Принятые решения и умолчания

**Решено владельцем:** внутренний инструмент; единый финальный релиз; формат источников JSON; YAML нет; `id` = имя файла; корни `roots` (по умолчанию `["index"]`); сирота = недостижим от корня, смысл связи на ревьюере; схемы JSON Schema, правила текста с подавлениями, теги `@covers` (только проверка тегов); гигиена связей, содержимого и стиль; `--fix`, пресет, `overrides`, `explain`, `rules`, вывод text и json; `init` создаёт только `docc.json` и `index.json`; формат агенту даёт скилл и `docc schema`; `build` отдельной командой; без `--changed`; без шаблонов; без `context`, `mv`, миграции, переходов статусов, Mermaid, глоссария; Linux, macOS, Windows; имя `docc`; без `fmt`; повторы в `links` и `tags` ловит встроенная схема; отчётов `sarif` и `github` пока нет (решение откладывается до выбора CI). Решено также: поле `body` и текст массивом абзацев; скрытые заметки `notes`; скрытые документы `hidden`; вставка текста `{{id#поле}}`; общие части схем через `$ref`; полная сборка для аудита `docc build --full`. Сравнение с аналогами (Spectral, ESLint и Biome, Vale и markdownlint, Sphinx-Needs, StrictDoc, Doorstop, Backstage) готового решения не нашло: пишем своё на Go. Заимствовано: подозрительные ссылки (Doorstop), свои правила в конфиге (Spectral), словари в файлах (Vale), конечная позиция ошибки (ESLint).

**Умолчания, выбранные при написании PRD (можно заменить):** `roots` по умолчанию `["index"]` и `id` = имя файла (решены владельцем в первом раунде вопросов); достижимость считается по рёбрам в обе стороны; `_tree.md` сохраняется; `baseline` не делается (готовых документов нет); уровни по умолчанию для правил, которых владелец не называл: `DOC107` и `DOC312` — error, `DOC206` и `DOC208` — warn; правила `DOC209`, `DOC302`, `DOC305`–`DOC307`, `DOC311`, `DOC351`–`DOC355` в группе `nursery` выключены в пресете (причины: ложные срабатывания на русском и шум для агента; `DOC209` — потому что подтверждать ссылки нужно осознанно); порог длины предложения 30 слов, порог сходства заголовков 0,85; набор `--fix`: безопасный `DOC208`, небезопасные `DOC206`, `DOC313`; `DOC208` проверяет направление «текст → `links` или `parent`»; `DOC401` не работает без `trace.scan`; повтор в `links` и `tags` — ошибка ядра `DOC105` без автоисправления (агент убирает повтор сам); поле `tags`, `$schema`, `docIgnore.path`, `--max-diagnostics` 20 для text, встроенные словари на русском и английском, драфт JSON Schema 2020-12, `docs/schemas/<kind>.json`, содержимое скилла, `go install`, параметры правил по умолчанию, запрет подавлять и отключать ядро, сборка `out/` при `init` и удаление лишних файлов `build` выбраны при написании PRD; так же выбраны синтаксис вставки `{{id#поле}}`, поле `hidden`, `DOC210` и `DOC211` в ядре, правило «к заметкам текстовые правила не применяются», каталог `docs/out-full` для полной сборки, формат отпечатка `DOC209`, синтаксис `customRules`, ключ `maxWarnings`, цели «меньше секунды на 1000 документов» и «9 из 10 ошибок за две итерации» и поставка скилла в архивах релиза рядом с бинарниками.

**Проверяется при реализации (вопросов владельцу нет):** позиции токенов и скорость (этап 0), порог сходства заголовков, словари стиля на реальных документах.

## 17. Приложение: точные определения

Приложение уточняет разделы 5–11 там, где реализации иначе пришлось бы придумывать поведение.

### А1. Проект и файлы

- **Корень проекта** — текущий каталог, в котором ищется `docc.json` (вверх по дереву не ищется; если файла нет, действуют умолчания); `--config <путь>` задаёт файл конфигурации, корнем проекта становится его каталог. Все пути в конфиге и в диагностиках отсчитываются от корня проекта, в диагностиках записываются с `/`.
- В `src` читаются только файлы `*.json` (расширение строчными). Обход `src` рекурсивный; остальные файлы, а также каталоги и файлы с именем на точку и символические ссылки пропускаются. Имя каталога, не подходящее под `id`, даёт `DOC104` (один на каталог, позиция 1:1 на его путь), файлы внутри читаются как обычно.
- **Файл документа:** UTF-8 (BOM допускается и отбрасывается), строгий JSON по RFC 8259 (без комментариев и висящих запятых), корень — объект; иначе `DOC101`. Пределы: размер файла не более 5 МБ, вложенность не более 64; превышение — `DOC101`.
- **`docc.json`:** тот же строгий JSON, допускается ключ `$schema`; неизвестные ключи и неверные типы — ошибка настроек (код выхода `2`, сообщение в stderr вида `docc.json:3:5: config error: …`). Диагностики и вывод `rules`, `explain`, `schema` идут в stdout, ошибки использования и настроек — в stderr. Цвета (ANSI) не используются.
- В `rules` ключ — код (`DOC301`) или имя (`text/forbidden-words`); пользовательское правило переопределяется по имени `custom/…`; ключ `nursery` задаёт уровень сразу всей группе. `overrides[].include` — список масок, `overrides[].rules` — настройки в том же виде, что и верхнеуровневые `rules`.
- **`kind`** — строка из `a-z`, `0-9`, `-`, иначе `DOC105`. Если файла `docs/schemas/<kind>.json` нет, документ проверяется только встроенной схемой. Ключевое слово `format` в схемах проверяется как утверждение.
- `docc init` не перезаписывает существующие `docc.json` и `docs/src/index.json` (пропускает с сообщением), затем всегда выполняет сборку. `docc --version` и `docc --help` работают как обычно.

### А2. Что проверяют текстовые правила

- **Какие строки:** значения `title`, `body` и всех свободных полей на любой глубине (элементы массивов, значения вложенных объектов). Не проверяются `kind`, `status`, `parent`, `links`, `tags`, служебные поля (`$schema`, `docIgnore`, `reviewed`, `notes`, `hidden`) и ключи объектов. Строка делится на фрагменты вне блоков кода и обратных кавычек.
- **Слово** — максимальная последовательность букв Unicode, цифр, `_`, дефиса и апострофа внутри слова; сравнение без учёта регистра по границам слов, `быстр*` — префикс.
- **Предложение** (`DOC351`): граница — `.`, `!`, `?` или `…`, за которым пробел и заглавная буква либо конец строки; точки внутри чисел и сокращений (`т.д.`, `т.п.`, `т.е.`, `г.`, `п.`, `рис.`, `см.`, `e.g.`, `i.e.`) границей не считаются; считаются слова в предложении.
- `DOC302`: `max` — число рун в строковом значении (для массива — в каждом элементе).
- `DOC303`: слова `TODO`, `TBD`, `FIXME`, `lorem` и последовательность `???` без учёта регистра как отдельные слова.
- `DOC304`: значение пусто или состоит из пробелов (для `title` действует `DOC103`).
- `DOC305`: нормализованный `title` (строчные буквы, пробелы схлопнуты, края обрезаны) совпадает у двух документов одного `kind` (документы без `kind` — одна группа); сообщение на каждом документе, кроме первого по `id`.
- `DOC306`: сравниваются только документы одного `kind`; сходство — коэффициент Жаккара по триграммам символов нормализованных `title`; пара сообщается один раз, на документе с большим `id`; равные `title` ловит `DOC305`.
- `DOC307`: строки вида ДД.ММ.ГГГГ и Д/М/ГГ; поля с `format: date` в схеме проверяет схема (`DOC106`), не `DOC307`.
- `DOC308`: открывающее ограждение (три и более обратных кавычек или тильд в начале строки) без закрывающего до конца значения.
- `DOC309`: строка вне блока кода, начинающаяся с 1–6 символов `#` и пробела.
- `DOC310`: открывающий тег с именем из списка элементов HTML5 или `script`, `style`, `iframe`.
- `DOC311`: Markdown-ссылка `[текст](адрес)`, где текст — «здесь», «тут», «ссылка», «here», «link», «click here» (без учёта регистра), или голый адрес `http://`, `https://` вне ссылки.

### А3. Граф

- **Рёбра** для `DOC202` и `DOC203`: `parent`, элементы `links`, `[[id]]` и `[[id#поле]]` в видимых строковых значениях (не в `notes`, не в блоках кода). Для достижимости те же рёбра в обе стороны, кроме ссылок из `notes` и ссылок от скрытых документов и к ним.
- `DOC204`: диагностика на каждом документе цикла, позиция на значении `parent`; `parent` на самого себя даёт `DOC204` и `DOC206`; `[[id]]` документа на себя в тексте — `DOC206` без исправления.
- Корень, который скрыт или отсутствует, — `DOC205`.
- В `{{id#поле}}` и `[[id#поле]]` «поле» — ключ верхнего уровня; для вставки допустимо значение-строка или непустой массив строк.

### А4. Работа с файлами

- Каталог `out/` целиком принадлежит `docc`: `build` удаляет всё, что не создал сам, в том числе чужие файлы и папки.
- `DOC501` сравнивает ожидаемое содержимое каждого файла с фактическим после нормализации переводов строк и различает «отсутствует», «устарел», «лишний».

### А5. Дополнения

- **Корень проекта:** `docc.json` ищется только в текущем каталоге, вверх по дереву не ищется. `roots` — непустой массив, пустой — ошибка настроек.
- **Ошибки использования и настроек** идут в stderr: `docc: error: …` (использование) и `docc.json:строка:колонка: config error: …` (настройки), не в JSON, код выхода `2`. `docc schema` без аргумента — ошибка использования (код `2`); `docc schema config` описывает `docc.json` с `additionalProperties: false`.
- **Ключи `rules`:** код, имя или группа (`syntax`, `schema`, `graph`, `text`, `markdown`, `style`, `trace`, `build`, `meta`, `custom`, `nursery`; другое — ошибка настроек). Приоритет: запись правила точнее записи тематической группы, та точнее записи `nursery`, та точнее пресета. Запись группы ядро не меняет (молча пропускает); изменить уровень ядра прямой записью правила или записать одно правило и кодом, и именем — ошибка настроек (код `2`).
- **Файл документа:** пустой файл, не-UTF-8, корень не объект — `DOC101`. Файл `*.json`, имя которого без расширения не подходит под `id` (например `a.b.json`), — `DOC104`.
- **Каскад ошибок:** документ с `DOC101` остаётся в графе узлом без рёбер (его `id` занят) и не получает `DOC202` и `DOC203`; файл с неверным именем (`DOC104`) в граф не входит. При дубле `id` в граф входит первый документ по пути (по байтам), остальные получают `DOC201` и в граф не входят. Скрытые документы проверяются на `DOC202` и `DOC204` так же, как видимые. Поле с неверным типом (`DOC105`) при построении графа игнорируется, нестроковые элементы `links` пропускаются, `hidden` неверного типа считается `false`.
- **Схемы:** все файлы `*.json` каталога схем загружаются при старте, любой некорректный — ошибка настроек. Ключевое слово `format` проверяется как утверждение (форматы библиотеки JSON Schema, в том числе `date`, `date-time`, `uri`, `email`; неизвестные игнорируются).
- **Ссылки `[[…]]`:** любое `[[…]]` вне блоков кода считается ссылкой; содержимое должно подходить под `id` или `id#поле`, иначе `DOC202` с подсказкой о формате `id`. Ссылки ищутся в `title`, `body`, свободных полях (любая глубина) и `notes`; в `kind`, `status`, `tags`, `parent`, `links`, `docIgnore` и `reviewed` не ищутся. Якорь строится как на GitHub (строчные буквы, пробелы в `-`, знаки препинания убираются).
- **Вставки** раскрываются только в `body` и свободных полях; в `title`, `kind`, `status`, `tags`, `parent`, `links`, `notes` запись `{{…}}` остаётся обычным текстом. Цель — поле верхнего уровня (в том числе `title`, `body`), значение — строка (пустая допустима) или непустой массив строк. Способа записать литерал `{{` нет, используется блок кода или обратные кавычки.
- **Подавление:** `path` подавляет диагностики с позицией внутри указанного значения; диагностики без позиции в значении подавляются только записью без `path`; несуществующий `path` ничего не подавляет (`DOC901`).
- **`DOC354`:** проверяется первое слово каждого строкового значения (для массива — каждого элемента); наличие «пояснения» не анализируется, исключения задаются в `allow`. В записи `words` `*` допустима только в конце слова.
- **Теги в коде:** в строке учитываются все теги `@covers`.
- Постоянные заголовки в Markdown (`Дерево документов`, `Без родителя`, служебные разделы полной сборки) на русском; сообщения и подсказки диагностик на английском.

### Б1. Рендер значений

- Страница: первая строка `<!-- GENERATED by docc, DO NOT EDIT -->`, пустая строка, `# title`, затем `body`, затем разделы в порядке из раздела 10. Заголовок раздела — ключ поля: первая буква заглавная, `_` и `-` заменяются пробелами (`kind` → «Kind»).
- **Строка** — абзацы (переводы строк внутри как есть). **Массив строк** — абзацы через пустую строку (для всех полей, кроме `parent`, `links`, `tags`). **Число, `true`, `false`** — текстом. **`null`, пустая строка, пустой массив и объект** раздела не создают.
- `kind`, `status` — раздел со значением; `tags` — одна строка тегов в обратных кавычках через запятую; `parent` — одна ссылка; `links` — маркированный список ссылок.
- **Объект** — маркированный список `- **ключ:** значение` (ключи в порядке файла); вложенные объекты и массивы — вложенные списки с отступом в два пробела; **массив объектов** — нумерованный список, элемент — вложенный список ключей; переводы строк внутри значения списка продолжаются с отступом.
- **Ссылка на документ:** `[title цели](относительный/путь.md)`, путь относительный от каталога страницы, с `/`; `[[id#поле]]` — `[title цели](путь.md#якорь)`, для `body` без якоря; текст `[[id]]` — `title` цели. Ссылок на скрытые документы в обычной сборке не бывает (`DOC210`); в `--full` ссылки ведут на их страницы.
- **`_tree.md`:** заголовок `# Дерево документов`, вложенный маркированный список по `parent`: сначала корни из `roots` в порядке записи, затем раздел «Без родителя» (остальные документы без `parent`); потомки сортируются по `id`; пункт — ссылка `[title](путь.md)`; документ, чей `parent` скрыт, попадает в «Без родителя»; корень из `roots` остаётся корнем, его `parent` игнорируется.
- **Полная сборка (`--full`):** служебные разделы называются «Заметки (скрытые)», «Подавления (docc-ignore)» и «Подтверждения (reviewed)»; у скрытого документа сразу после заголовка строка `> Скрытый документ.`; в `_tree.md` скрытые документы помечены «(скрытый)»; вставка обрамлена `<!-- include id#поле -->` и `<!-- /include -->`.

### Б2. Вывод команд

- **text:** диагностики, затем итоговая строка `N errors, M warnings in K files` (и при нуле), где `K` — число файлов с диагностиками; баннер «показано N из M» стоит перед ней. Поля JSON-диагностики описаны в разделе 7. **json:** массив объектов (пустой — `[]`), итоговой строки нет.
- `docc rules`: text — таблица «код, имя, группа, уровень, fix»; json — массив `{code, name, group, level, fix}`.
- `docc explain <код или имя>`: text — заголовок (код, имя, группа, уровень по умолчанию), описание, пример нарушения, пример исправления, сведения об исправлении; json — объект с теми же полями.
- `docc schema document|config`: JSON Schema (драфт 2020-12) в stdout; для документа лишние поля разрешены.
- `message` и `hint` — короткие английские предложения, `hint` в повелительном наклонении. Для каждого кода текст стабилен, но не входит в публичный контракт: контракт составляют код, имя правила и позиция.

### Б3. Теги в коде

- Грамматика: `@covers`, пробелы, `id` (`a-z`, `0-9`, `-`), далее при необходимости запятая, пробелы и ещё `id`; остальной текст строки игнорируется.
- Просматриваются текстовые файлы под масками `trace.scan` (от корня проекта); файлы с нулевым байтом и больше 1 МБ пропускаются, символические ссылки не открываются, каталог `.git` и каталоги `src`, `out`, `outFull` самого `docc` не просматриваются.

### Б4. Встроенные словари (начальные, дополняются в `docc.json`)

- `DOC301` (запрещённые): быстро, удобно, интуитивно, «и т.д.», «и т.п.»; fast, easy, intuitive, user-friendly, etc.
- `DOC352` (оговорки): возможно, вероятно, «как правило», «по-видимому», «в некоторых случаях», наверное, «скорее всего»; maybe, probably, usually, might, perhaps.
- `DOC353` («временные»): сейчас, недавно, пока, «в настоящее время», скоро, «в будущем», новый, новая, новое, новые; currently, recently, soon, new, «at the moment».
- `DOC354` (начало поля без пояснения): Это, Он, Она, Оно, Они, Данный, Данная, Данное, Данные, Такой, Такая; This, It, They, These, That.

### Б5. Тесты

Каждый тест — каталог `testdata/<код>/red` или `green` со своим `docs/src/`, при необходимости `docc.json`, и файлом `expected.json` (ожидаемый вывод `--format json`). Минимальная версия Go — актуальная стабильная на момент начала реализации.
